> 文档性质：**解决方案建议，不是实施授权。**
>
> 起因：推荐定额 L3「正式编号原生输入」长期无法写入选中的目标单元；2026-08-21 一天内累计 9 次修复提交仍未解决。
>
> 结论先行：**仓库里已有三条经过实机验证的写入路径，而当前 L3 走的是第四条自研路径。** 建议按本文分层改造，并顺带修正两条已被实机证据推翻的 `AGENTS.md` 规则。

## 2. 两条必须修正的 `AGENTS.md` 假事实

### 2.1 「`BeginEdit(true)` 返回 false 且不会产生 `EditingControl`」——错

原文（2026-08-20 加入）：

> `dataGridViewDE` 是自定义 `RecoNet.DataGridViewDe`，表格、定额编号列和单元格均为只读，`BeginEdit(true)` 返回 false 且不会产生 `EditingControl`

**反证**：`RecoQuotaRecommend.log` 2026-08-20 05:22:43

```
Inline quota native single-enter submitted: QY-39 row=7 filled=True
  beginEditMs=124 enterMs=913 elapsedMs=1038
  data=code=QY-39|name=基坑回填 原土|unit=10m3|price=140.8|compiler=谢刚
```

`beginEditMs=124` 证明 `BeginEdit(true)` **成功返回并产生了 `EditingControl`**，宿主随后补齐了名称、单位、单价、编制人。

**真实条件**：该结论只在**宿主窗体不是当前活动窗口**时成立。跨窗口调用 `grid.Focus()` 不会真正取得键盘焦点——Windows 的焦点跟随活动窗口。参考定额池之所以成功，是因为它经 `mainForm.BeginInvoke` 延迟到宿主自身的双击事件结束后执行，此时宿主窗体是活动窗口（`RecoReferenceQuotaPoolFeature.cs:487` 注释已明确写出这一点）。

### 2.2 「不得使用宿主右键菜单/批量粘贴；该路径可返回却不生成定额行」——错

**反证**：2026-08-21 用户实机截图，`ExecuteAgentInsertGroup` 用的正是剪贴板 + 宿主粘贴菜单，`LY-146` 成功插入并由宿主补齐单价与单重。

该路径失败更可能源于：未先导航到目标条目、未把光标移到末尾新行、剪贴板不是宿主期望的 TSV 列格式，或未等待宿主落库。

> **这两条假事实固化在项目规则里，会持续把后续工作推向自研键盘链。建议优先修正。**

## 3. 建议方案：按可靠性分层

### 首选：L3 改为「结构模板克隆 + SQL 插入」，彻底取消原生输入

**做法**与现有 L2 完全一致（`TemplateFillFeature.BuildSmartFillL2Row:1195`），只是元数据来源不同：

| 字段 | 辅助码（现有 L2） | 正式定额（本方案） |
|---|---|---|
| 名称、单位 | 学习库 `target_name`/`target_unit` | **标准定额库**（`RecoData2020`/`RecoData2024`，与宿主打编号时读的是同一个源） |
| 单价 | 学习到的 `unit_price`，可改 | **留 0，由「重算」补齐** |
| 数量 | 预览项 `QuantityText`（Excel 现场换算） | 同左 |
| 其余列 | 克隆同条目结构模板，费用列置 0 | 同左 |

**为什么成立**

1. **L1 已证明** SQL 直插的 `定额输入` 行是有效业务行；
2. **L2 已证明** 「克隆结构模板 + 覆盖身份字段」可行，已实现并有离线测试；
3. **智能指令「替换定额」已证明** 直接改 `定额输入.定额编号` 后靠重算补齐造价是宿主的既定模型（`plan.NeedsRecalc = true`）；
4. `定额输入` 行到定额库的绑定是**按定额编号 + 项目级已勾选书号、在计算时解析**，**没有必须正确的行级书号字段**——`AGENTS.md:109` 明确记载：未勾选书号时表现为「计算单价为 0 / 无法找到定额消耗数据」，勾选后原生查询、输入、计算即可使用。

**收益**

| 现状 | 改后 |
|---|---|
| 整条键盘链：焦点争夺、`SendKeys`、`WM_KEYDOWN/UP`、32 位参数兼容 | 全部删除 |
| L3 状态机：9 态、250ms 轮询、10s 超时、定点补偿、`Indeterminate` | 全部删除 |
| 非事务路径，需补偿语义 | 并入同一 SQL 事务，「一次 Apply 全回滚」真正成立 |
| 依赖窗口焦点，用户 alt-tab 即可能把按键发错窗口 | 完全不碰 UI |
| 每条约 1 秒（实测 `beginEditMs=124` + `enterMs=913`） | 毫秒级 |
| **只能写入宿主当前显示的单元** | **任意单元** |

最后一行即用户反馈的原始问题：**因为不再依赖任何 UI 状态，跨单元写入自然成立。**

**附带收益**：智能指令的「1 替换多」目前因新增行靠主程序粘贴而被硬限制在当前单元（`AgentExecutor.cs:1647-1660` 显式抛异常要求先切单元）。同一改法可一并解除该限制。

**必须实机验证的一步**：插入一条已知正式定额 → 点「重算」→ 核对单价/合价与手工输入完全一致。这是本方案唯一的真实风险点。

### 次选：复用路径 B（剪贴板 + 宿主粘贴菜单）

若首选方案在实机验证中发现重算无法补齐某字段，直接复用 `ExecuteAgentInsertGroup` 的完整序列，**不要另写**：

```csharp
HashSet<long> before = LoadAgentItemQuotaIds(conn, itemNo);   // ① 按条目查库取基线
TryNavigateToAgentItem(mainForm, conn, itemNo);               // ② 先导航到目标条目
WaitAgentUiIdle(800);                                         // ③ 等宿主刷新完
// ④ TSV：编号 \t \t \t 数量 \r\n，多条拼成多行一次贴完
Clipboard.SetText(text);
grid.Focus();
MoveAgentGridToNewRow(grid);                                  // ⑤ 光标移到末尾新行
if (!TryInvokeAgentPasteMenu(mainForm)) SendKeys.SendWait("^v");  // ⑥ 调宿主自身粘贴命令
WaitAgentUiIdle(1200);
HashSet<long> after = LoadAgentItemQuotaIds(conn, itemNo);    // ⑦ 差集确认，不看提示字符串
```

关键点：**TSV 多列一次给编号和数量**、**先导航后粘贴**、**调宿主自己的粘贴菜单**、**按条目查库做差集**。当前 L3 这四点全都不同。

### 兜底：复用路径 C（`BeginEdit` + 直接赋值）

若必须走单元格编辑，**照抄**已验证序列，并补上跨窗口焦点处理：

```csharp
mainForm.Activate();                       // ① 先激活宿主窗体——跨窗口 Focus() 不生效，这是根因
Application.DoEvents();
grid.Focus();                              // ② Focus 在设 CurrentCell 之前
grid.ClearSelection();
grid.CurrentCell = grid.Rows[r].Cells[c];
grid.Rows[r].Selected = true;
bool ok = grid.BeginEdit(true);
var edit = grid.EditingControl as TextBoxBase;
edit.Text = code;                          // ③ 直接赋值，不要逐字符模拟按键
edit.SelectionStart = edit.TextLength;
grid.NotifyCurrentCellDirty(true);         // ④ 当前实现缺此步，宿主不认脏就不提交
SendKeys.SendWait("{ENTER}");              // ⑤ 不要手工拼 WM_KEYDOWN/UP
Application.DoEvents();
```

整段经 `mainForm.BeginInvoke` 排到宿主 UI 线程，等插件窗口的点击处理结束后再执行（参考定额池即如此，`RecoReferenceQuotaPoolFeature.cs:487`）。

## 4. 元数据变更的影响（用户提问）

需要区分三个不同的数据源：

| | 是什么 | 谁在用 | 被改动时的影响 |
|---|---|---|---|
| **标准定额库** | `RecoData2020`/`RecoData2024` 的定额定义（编号→名称/单位/消耗），全项目共用 | 宿主打编号时补齐；**本方案取名称/单位的来源** | 定额被删或书号取消勾选 ⟹ 重算后单价 0、「无法找到定额消耗数据」。**对原生输入写的行完全一样**，非本方案新增风险 |
| **另一个项目的 `定额输入`** | 别的项目的业务行 | **L1** 整行复制的来源 | 已有防护：`IsSmartFillSourceIdentityMatch` 读出后二次核对编号/名称/单位；`SourceCandidates` 有序候选列表，最新失效自动退到较早候选 |
| **`RecoLearning`** | 只存绑定关系，不存定额行 | 推荐排序 | 与写入无关 |

**要点**：写进 `定额输入` 的名称/单位是写入时刻的**快照**——宿主原生输入同样是快照。真正的绑定在**重算时按定额编号解析**。智能指令「替换定额」只改编号、不改名称，正是这一模型的既有实例。

**建议收紧**：名称/单位应从**项目连接直读标准定额库**，而非 `quota-index*.jsonl` 缓存，以消除缓存过期造成的与宿主取值不一致。

**推论**：采用本方案后，正式定额即使所有跨库候选都失效，仍可从标准定额库构造写入，**不会因其他项目被修改而写不进去**。L1 对正式定额降为「省一次重算」的优化项；对辅助码（`SH`/`ZLF`/`LF`/`TLF`）L1/L2 仍然必要——它们不在定额库中，无处可查。

## 5. 其余相关行为（用户提问）

| 问题 | 结论 |
|---|---|
| `SF` 会自动放到设备购置费吗 | 会，已实现。同级（段数相同、除末段外逐段相同）唯一的「设备购置费」条目才用，零个或多个均整组阻断。`SF` 属辅助码走 L2，**不受本方案影响** |

| 数量会用 Excel 表里的数量吗 | 会。`工程数量输入 = item.QuantityText`，来自框选的 Excel 目标行，并按当前 Excel 单位与当前版本定额单位**现场换算**（不复用历史表达式中的 `/1000`、`*1.05`） |

## 6. 建议执行顺序

1. **先改两条 `AGENTS.md` 假事实**（§2），否则后续工作会继续被误导；
2. 实施首选方案：L3 改为结构模板克隆 + SQL 插入，元数据直读标准定额库；
3. **实机验证**：插入已知正式定额 → 点「重算」→ 核对单价/合价与手工输入一致；
4. 验证通过后删除整条自研键盘链与 L3 状态机，把 L3 目标并入单一 Apply 事务；
5. 回归：现有 L1/L2 用例保持绿；新增「跨单元写入」与「重算后单价正确」两条；
6. 可选：同一改法解除智能指令「1 替换多」的当前单元限制。

> 若第 3 步失败，退次选路径 B（复用 `ExecuteAgentInsertGroup`），仍不成立再退兜底路径 C。三条都有实机证据，不必再自研第四条。

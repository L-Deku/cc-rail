### 0.E 运行环境事实(2026-08-05 只读实测,v2.9 新增;v2.10 改唯一编号)

**使用范围**:

- **只有本机安装并使用这两个插件**。同事会运行 2020/2024 软件,但**未安装插件**,
  因此只影响业务库(`RecoData2020`/`RecoData2024`),**不会写入 `RecoLearning`**。
- ⟹ W0 及各入口的进程门禁**只需检查本机**的 `RejjNet2020`、`ReJJGSNet2024`、`ReJJQDNet2024`;
  **不需要、也无法**检查同事机器,更不需要为本次窗口协调同事停工。
- ⚠️ 若业务库与 `RecoLearning` 同在 `192.168.2.213`,窗口内的备份与一次性测试库会占用该机磁盘与 IO,
  建议与同事的使用高峰错开。

**数据库与账号**:

| 项 | 实测值 |
|---|---|
| 版本 | **Microsoft SQL Server 2008 R2 (SP3) 10.50.6000.34 Enterprise Edition (64-bit)** |
| 登录/用户 | `Reco` / `dbo` |
| 角色 | `sysadmin`=1、`dbcreator`=1、`db_owner`=1、`db_backupoperator`=1 |
| 关键权限 | `BACKUP DATABASE`=1、`BACKUP LOG`=1、`ALTER`=1、`CREATE ANY DATABASE`=1、`VIEW SERVER STATE`=1 |
| `master.dbo.xp_fileexist` | **存在**(1) |
| `sys.dm_os_file_exists` | **不存在**(0) —— SQL Server 2008 R2 不支持;该 DMF 从 SQL Server 2017 才引入 |

两条推论:

1. §7.5 的备份方案(`BACKUP DATABASE ... WITH COPY_ONLY, CHECKSUM` +
   `RESTORE VERIFYONLY/HEADERONLY`)**确实可执行**,不必退化为人工备份;
   `CREATE ANY DATABASE` 也使 T24 的一次性测试库可在同服务器创建。
2. **⚠️ 2008 R2 的 T-SQL 限制,写迁移脚本时必须遵守**:
   - **没有 `THROW`**(2012+)—— 用 `RAISERROR(...) WITH NOWAIT` 或 `RAISERROR` + `RETURN`;
   - **没有 `TRY_CONVERT` / `TRY_CAST`**(2012+);
   - **没有 `OFFSET ... FETCH`**(2012+)—— 用 `TOP` + 子查询;
   - **没有序列对象 `SEQUENCE`**(2012+);
   - **没有 `CONCAT` / `IIF` / `FORMAT`**(2012+);
   - `sp_addextendedproperty` 在库级可用,§7.5 的 `RecoLearningSchemaVersion` 扩展属性方案成立。

   这些在开发机上按新版本语法写通常不报错(客户端不校验),**到窗口当天连上 2008 R2 才会失败**。

## 4. 设计

### 4.1 分区口径(最终)

| 层 | 分区键 | 依据 |
|---|---|---|
| 普通定额关系 `SignatureBoxMap` | `software_partition` ∈ {`2020`,`2024`} | §3.1;30/101 共享 |
| 条目证据 `SignatureEntryMap`、`EngineeringTemplate` | `(software_partition, method_no)` | §3.3 |
| 数量公式 `QuantityFormulaRule`(+Operand) | `(software_partition, method_no)`,且进 `rule_hash`;**公式必须带条目** | §3.3 + 公式身份含 `entry_code` |
| 定额候选排序 | **不按办法过滤**,30/101 并列排序 + 下拉改选 | §3.2 |
| 条目候选 | 先按当前 `method_no` 过滤;仍多义 ⟹ 展开为可选组合,**必须人工选择** | §4.7 |

读取规则:

- 2024 软件**只**读 `software_partition='2024'`;2020 软件**只**读 `'2020'`。
- `software_partition` 为空或不可识别 ⟹ 不参与任何自动推荐。
- 2020 内部 30 号文与 101 号文估算**共享普通定额关系池**;条目证据与公式按 `method_no` 隔离。

### 4.1.1 两类证据必须分开过滤(复审 8.3,修正 v2.2 的过度收紧)

v2.2 §4.3⑫ 要求 `SelectSmartLocalRowsForMethod` 按 `(software_partition, method_no)` 过滤,
**这与已确认的业务口径冲突** —— 2020 内部 30 号文与 101 号文的普通"工程量名称 → 组件框"关系
本来就该共用,按 `method_no` 硬过滤会把它们互相隔断。

**正确口径**:

| 证据类型 | 过滤键 | 涉及对象 |
|---|---|---|
| **普通组件关系** | **只按 `software_partition`** | `SignatureBoxMap`、`QuotaBox`/`QuotaBoxTarget`、`QuantityAlias`、本地 `mapping-boxes.jsonl` 的框与样本行 |
| **条目上下文** | **必须精确按 `(software_partition, method_no)`** | `SignatureEntryMap`、`EngineeringTemplate` |
| **数量公式** | **必须精确按 `(software_partition, method_no)`** | `QuantityFormulaRule` / `Operand`,含 `rule_hash` |

补充规则:

1. D4 反导的记录、以及只有普通关系证据的历史记录,**允许 `method_no` 为空** ——
   但该记录**绝不能**贡献条目或公式证据(与 §5.3 降级矩阵一致)。
2. 同一普通关系若有多个办法来源,**在关系层去重/聚合**(按 `(software_partition, signature, box_id)`),
   **不得**把某一办法的条目证据顺带到另一办法。
3. **这不是恢复"空值跨分区回退"**。`software_partition` 仍是硬边界:空分区或其他分区的记录
   一律不参与推荐。放宽的只是**同一分区内部**的 `method_no` 维度,且只对普通关系放宽。

### 4.2 两个新维度的定义(对应复审 P0 3.1 建议模型)

| 字段 | 来源 | 值域 | 可为空 |
|---|---|---|---|
| `SoftwarePartition` | **只由实际运行进程产生**(§4.4) | `2020` / `2024` | 否(未知即拒写) |
| `MethodNo` | 由项目**原始**编制办法文号产生 | `30号文` / `101号文估算` / `TB 10801—2024` | 历史数据可为空,新数据不可 |
| `method`(旧) | `项目信息.编制办法文号` 归一化 | `2020` / `2024` / `''` | 保留作兼容与审计,**不再作为新关系的真实分区键** |

新增归一化函数 `NormalizeLearningMethodNo(rawMethod)`,口径与
`ResolveSmartMethodRoute`(`SmartFillFeature.cs:181-223`)的 `MethodNo` 完全一致:

```
含 "101号文" 或 "101-estimate"                    → "101号文估算"
含 "TB10801" 或 "2024"                            → "TB 10801—2024"
含 "国铁科法" / "30号文" / "2020"                  → "30号文"
其余                                               → ""(视为未知,新数据按拒写处理)
```

> 判定顺序必须"101 优先",与 `ResolveSmartMethodRoute` 一致 —— 101 号文文本中同时含 `2020` 字样时
> 不能被 `30号文` 分支抢走。该顺序须有单元测试锁定。

### 4.4 分区判定与未知进程处置(复审意见 4 + P1 4.2)

新增 `ResolveLearningSoftwarePartition()`,规则**只有一条**:

```

当前进程名 / 主模块文件名 含 "rejjgsnet2024" 或 "rejjqdnet2024"    → "2024"
其余一律                                                          → 未知
```

**明确禁止**:禁止复用 `RecoQuotaRecommend/SearchIndexStore.cs:1002-1003` 的
`has2020Executable`/`has2024Executable` 目录 EXE 兜底分支(该兜底可继续服务索引路径解析,
**不得用于学习分区**);禁止用 DLL 目录、配置文件、连接串推断。

**未知进程的处置(复审要求 5 —— 为什么以后重放不会被错误归类)**:

1. **时序**:分区解析发生在**写本地 `mapping-boxes.jsonl` 之前**,也在入 Outbox 之前。
2. 未知 ⟹ **不写本地学习行、不写 SQL、不进普通重试 Outbox**。
   理由:进程未知是**永久性缺少来源证据**,不是数据库瞬时故障;放进普通 Outbox 后
   会在另一软件进程中重放,从而被打上**重放时**的分区。
3. 直接进入 **dead-letter/隔离**,记录:批次 ID、源操作(`source`)、当时进程名、主模块文件名、
   拒写原因、时间戳。
4. **重放只能使用批次创建时已保存的 `software_partition`**;禁止在重放时重新推断。
   反序列化读不到分区的旧批次 ⟹ 立即隔离,只能靠批次内已有的可靠历史字段回填。

### 4.6 公式哈希必须同时含 `software_partition` 与 `method_no`(复审 P0 3.2,要求 3)

现状(**本地实测**),两侧各算一次且都只含归一化 `method`:

```csharp
// C# LearningDbFeature.cs:1109-1125  BuildLearningFormulaRuleHash
raw = signature + "|" + kind + ":" + CODE + "|" + NormalizeExcelLinkUnit(unit) + "|"
    + formulaTemplate + "|" + NormalizeLearningDbMethod(group.Method) + "|" + entryCode
    + 每个操作数: "|" + operandSig + "@" + operandUnit
```

```powershell
# PS Rebuild-Aggregates.ps1:278-295
$formulaMethod = Get-LearningMethodPartition ([string]$row.method)
$ruleRaw = $sig + '|' + $kind + ':' + $code.ToUpperInvariant() + '|'
         + $targetUnit.Trim().ToLowerInvariant() + '|' + $template + '|'
         + $formulaMethod + '|' + [string]$row.entry_code
$ruleRaw += '|' + $operandSig + '@' + $operandUnit.Trim().ToLowerInvariant()   # 每个操作数
```

由于 30 号文与 101 号文估算都归一为 `2020`,而公式身份含 `entry_code`,§3.3 的
165 个同编号异义条目会在**同一软件分区内**碰撞:

```
2020 + 30号文     + 条目 0101-01-01-02(二)泥结碎石路
2020 + 101号文估算 + 条目 0101-01-01-02(二)非等级公路      ← 同 rule_hash
```

**v2.1 规定的新 `ruleRaw` 布局(两侧必须逐字一致)**:

```
<signature>|<kind>:<CODE>|<unit>|<template>|<software_partition>|<method_no>|<entry_code>
  [|<operandSig>@<operandUnit>]...
```

即在原 `method` 位置**替换**为 `software_partition`,并在其后**新增**一个 `method_no` 字段,
其余分隔符与顺序不变。配套要求:

- C# `BuildLearningFormulaRuleHash` 与 PS `Rebuild-Aggregates.ps1` 同批修改。
- 公式读取按 `(software_partition, method_no)` 精确过滤,**无 `OR` 兜底**。
- 本地公式行(`mapping-boxes.jsonl` 的 `formula_*` 字段)与 Outbox 公式字段也必须保存 `method_no`。
- 跨语言一致性测试必须包含:**同一输入只改 `method_no`,哈希必须变化**(§9.2 测试 4)。

**公式必须带条目(用户拍板,v2.2 新增全局规则)**:

> **`entry_code` 为空的公式一律不生成** —— 写入端、增量聚合、全量重建三处统一。

推论与收益:

- 公式与条目从此是**一对一绑定**关系,不存在"游离公式"。
- 因此"公式需要 `method_no`"成为**无例外**的结论 —— 不必再为 `entry_code` 为空的公式
  讨论是否开通道(v2.1 §11 问题 3 因此关闭)。
- 现有 42 行 `QuantityFormulaRule` 中若存在 `entry_code=''` 的行,全量重建后自然消失;
  DryRun 报告须单列该数量供核对。
- 写入端在 `WriteBindingEventsToLearningDb`(`LearningDbFeature.cs:217-231`)组装
  `formula_*` 字段处增加判定:`GetMappingFeedbackTargetEntryCode(group, target)` 为空
  ⟹ 不写 `formula_rule_hash` 等字段,不产生公式行(绑定本身仍正常写入)。

**单位归一化必须本批统一(复审 P1 8.8,v2.3 修正)**:

v2.2 把 C#/PS 单位归一化差异当作"独立缺陷、本批不动",**这个判断是错的**。
两侧现状确实不一致 —— C# 用 `NormalizeExcelLinkUnit(unit)`(有较完整的单位转换规则),
PS 公式哈希路径用 `$targetUnit.Trim().ToLowerInvariant()`(只去空格转小写);操作数单位同样如此。

只要差异存在,**同一条公式在增量写入与全量重建后会得到不同哈希**,T4 的"增量/全量一致"
根本无法稳定成立。而本批公式哈希已经因加入分区与办法号**整体换代**,旧哈希本来就要全部失效
——**这正是统一口径的切换点,不属于额外重构**。

> **定案**:B6 内定义**唯一一套单位归一化规则**,由 C# 与 PowerShell 各实现一份,
> 并加**对照测试**(同一组单位样本两侧输出逐字相同)。以 C# 现有 `NormalizeExcelLinkUnit`
> 为基准口径,PS 侧补齐;样本集必须覆盖 `10m3`、`hm`、`10套`、`km`、`正线公里`、
> 空单位、含全角字符与前后空白等边界。

**旧 `formula_rule_hash` 必须无条件失效(复审 P0 8.5,v2.3 新增)**:

现状(**本地实测**,`Rebuild-Aggregates.ps1:294-295`):

```powershell
$ruleHash = Get-ExtraText $extra 'formula_rule_hash'
if ($ruleHash -eq '' -or $formulaMethod -ne ([string]$row.method).Trim()) { $ruleHash = Get-Md5Hex $ruleRaw }
```

即**优先信任历史事件里已存的哈希**,只在为空或办法归一化发生变化时才重算。
旧事件里的哈希既不含 `software_partition` 也不含 `method_no`,继续信任等于把跨软件、
跨办法的公式碰撞原样带进新库。

> **定案:全量重建时无条件按新布局重算所有哈希**,删除对 `extra.formula_rule_hash` 的信任分支。
>
> **不引入 `formula_hash_version`**。理由:`QuantityFormulaRule` 仅 42 行(§3.5),
> 无条件重算成本为零;引入版本字段会增加一个需要长期维护的状态维度,收益不匹配。

测试要求(T4 扩展):**不能只比较新旧辅助函数的输出**。必须准备一条
`extra.formula_rule_hash` 已存旧值的**真实历史事件**,走完整重建流程,
断言它被替换为新版哈希,而不是被沿用。

### 4.9 `MappingStore` 运行时整文件重写(复审 P0 8.2,v2.3 新增)

**这是本轮发现的最危险缺口。** 即使迁移工具生成了完全正确的分区文件,
用户在推荐窗口里"接受"或"扶正"**一次**,整份文件就会被重写回旧格式。

代码事实(**本地实测**):

| 位置 | 行为 |
|---|---|
| `MappingStore.Accept`(`MappingStore.cs:170`) | 接受推荐 → 改内存 → `Save()` |
| `MappingStore.Correct`(`214`) | 扶正 → 改内存 → `Save()` |
| `MappingStore.Save`(`459-470`) | 取互斥锁 → `MergeFromDisk()` → `WriteFile()` |
| `MappingStore.WriteFile`(`489-537`) | **整文件重写**,逐行按**固定字段集**输出 |

`WriteFile` 输出的字段是写死的 13 个 + 可选 `entry_codes`:

```
record_type, box_id, target_kind, target_code, target_name, target_unit,
quantity_name, quantity_unit, weight, accepted_count, corrected_count,
rejected_count, last_used_at [, entry_codes]
```

内存模型 `MappingBox` / `MappingTarget` / `MappingSample`(`MappingStore.cs:~780-838`)
**没有任何位置承载未知字段**,所以 `software_partition`、`method_no`、目标条目、
公式等新字段在一次 Accept 后即被抹掉。下一次按分区读取时,这些记录会被判为空分区而隔离或丢失。

**v2.3 要求(Task B9)**:

1. `Accept` / `Correct` / `Save` / `WriteFile` 全部纳入分区改造链。
2. **写入前先确定当前软件分区**(`ResolveLearningSoftwarePartition()`,§4.4);
   未知进程**不得**落入正式文件(与 §4.4 一致)。
3. **内存模型(v2.7 最终口径)**:采用 §4.11 的双 `record_type` + §4.11.2 双层保存。
   `MappingStore` 只把当前分区 `mapping_box` 放入既有合并/重生成模型；
   对可识别 `mapping_context` 只建身份定位索引，不进入 `CanonicalizeBoxes`；
   其他分区/办法、未知记录、空行和坏行由原文层保留原始字节。
   `MappingBox`/`MappingTarget`/`MappingSample` 显式新增 `SoftwarePartition`，
   保存时按 §4.11.2 确定性 splice，不能再用全文件字典重序列化。

   > **v2.3 的"显式字段 + `Extra` 透传"(方案 i)已作废。** 复审 9.3 指出并经本地核实:
   > `ParseFile`(`MappingStore.cs:334-342`)按 `box_id` 合并 → `CanonicalizeBoxes`(`403`)
   > 按目标集合再合并 → `WriteFile`(`489-537`)重生成笛卡尔积。三层之后
   > **原始平面行的字段对应关系已经不存在**,对象级 `Extra` 无法还原"哪个字段属于哪一行"。
   > 只有把上下文抽成独立记录、且不进入合并管线,才能保证无损往返。
4. **保存其他分区/其他办法的行时必须原样保留**,不得先跨分区合并再过滤。
5. 回归用例(T17,v2.4 扩为多行):同一框、同一目标、同一工程量分别预置 30 号文与 101 号文
   两条上下文(条目、公式、未知字段各不相同)⟹ 一次 `Accept` + 一次 `Correct` 后,
   **两行仍分别存在且字段对应关系不变**。单行未知字段测试不足以证明方案安全。

### 4.11 本地文件行级模型(复审 P0 9.3,用户拍板"拆两种 `record_type`")

**问题**:现有平面行一行同时装着三类语义 —— 普通关系字段(框、目标、工程量样本、权重)、
办法上下文字段(`method_no`、`entry_code`、`entry_name`)、公式字段(`formula_*`)。
这些字段实际属于"目标 + 工程量样本 + 办法"的**具体行**,不能安全提升到
Box / Target / Sample 任一单独对象。

**定案:拆成两种 `record_type`**。

| `record_type` | 承载 | 身份键 | 谁写 | 谁读 |
|---|---|---|---|---|
| `mapping_box`(沿用现名) | 普通关系:`box_id`、`target_kind/code/name/unit`、`quantity_name/unit`、`weight`、三个计数、`last_used_at`、**新增 `software_partition`**。**不再携带 `entry_codes`**(v2.5) | `(software_partition, box_id, target_identity, quantity_signature)` | `ExcelLinkFeature`、`MappingStore` | 三个读取端,**只按 `software_partition` 过滤**(§4.1.1) |
| `mapping_context`(**新增**) | 办法上下文与公式:`method_no`、`entry_code`、`entry_name`、`formula_*` | 见下方 **v2.7 身份键** | `ExcelLinkFeature` **+ `MappingStore.Accept/Correct`**(v2.5 修订) | 仅条目/公式消费方,**按 `(software_partition, method_no)` 精确过滤** |

**`mapping_context` 身份键(v2.6 补维度,v2.7 统一条目规范化)**:

```
无公式 context:
  (software_partition, method_no, box_id, quantity_signature, target_identity, entry_code)

含公式 context:
  (software_partition, method_no, box_id, quantity_signature, target_identity, entry_code,
   formula_rule_hash)
```

其中 `entry_code` 必须先经过 §4.11.3 的 `NormalizeLearningEntryCode`；任何写入端、读取端、
`EntryScope.Tag` 和身份键不得自行实现另一套口径。

补 `entry_code` 的理由(复审 11.2):同一软件、同一办法、同一组件框、同一工程量、同一目标,
**允许在多个不同条目下分别接受**。`MappingStore.EntryCodes` 是 `HashSet<string>`
(`MappingStore.cs:640`)本身就证明一个普通关系可累积多个条目标签。
按 v2.5 的键执行时:条目 A 接受 → 条目 B 再接受 → 两者键相同 → B 覆盖 A → 回到条目 A 时学习丢失。

再补 `formula_rule_hash` 的理由(复审 11.4,**采纳推荐的方案一**):
`SmartFillFeature` 以 `formula_rule_hash` 建立公式规则,SQL `QuantityFormulaRule` 也允许
同一关系存在不同公式哈希。只补 `entry_code` 时,同一条目下形成过两个不同参数公式,
后一次仍会覆盖前一次。**含公式的 context 才带该段;无公式的 Accept/Correct context 不带**,
两者因此不会互相覆盖。这与 SQL 聚合和现有 `SmartFillFeature` 的规则哈希模型一致。

**必须满足的五条**(复审 9.3):

1. **30 号文与 101 号文的上下文行可以同时存在**,任何一方写入**不得删除或覆盖**另一方。
2. **普通关系聚合的权重与计数口径写死**:同一 `(software_partition, box_id, target_identity,
   quantity_signature)` 若有多行(理论上不应有),取 `weight`/各计数的 **`MAX`**、
   `last_used_at` 取 **最大值**;不写含糊的"去重/聚合"。
3. `EntryScope.Tag` 至少包含 `software_partition + method_no + entry_code`(见下)。
4. **D4 生成的 `method_no=''` 普通关系行不得获得任何条目或公式字段** ——
   即 D4 只产出 `mapping_box` 记录,不产出 `mapping_context`。
5. `MappingStore` 保存其他分区/其他办法的行时**原样保留**,不得先跨分区合并再过滤。

**必须修的两处现有覆盖行为**:

- **`ExcelLinkFeature.UpsertMappingBoxGroup`(`ExcelLinkFeature.cs:2601-2605`)**
  当前按 `box_id + method + quantity signature` 定位旧行:

  ```csharp
  String.Equals(GetFlat(row, "box_id"), boxId, ...) &&
  String.Equals(GetFlat(row, "method").Trim(), groupMethod, ...) &&
  String.Equals(NormalizeForSignature(GetFlat(row, "quantity_name")) + "|", signature, ...)
  ```

  匹配键**不含 `method_no`**,而 30 号文与 101 号文的 `method` 都会归到 `2020`
  (§2.5),后一次写入会命中同一批行并覆盖前一办法的条目与公式。
  **改法**:普通关系行按 §4.11 表中的 `mapping_box` 身份键定位;
  上下文行按 `mapping_context` 身份键**独立定位**,两套办法各自成行、互不覆盖。
  > 补充实测:本地文件里 `method` 既有 `30号文`(原文)又有 `2024`(归一值),
  > 口径本身就混乱,更不能作为定位键。

- **`ChapterLibraryStore.EntryScope.Tag`(`RecoQuotaRecommend/ChapterLibraryStore.cs:38-41`)**
  当前是 `Method + ":" + MatchedEntryCode`。30 号文与 101 号文条目编号相同时标签相同,
  **达不到按 `method_no` 隔离**。改法见 §4.12(v2.5 单列,因为涉及分区来源的可靠性)。

### 4.11.1 `mapping_context` 的写入所有权(复审 P0 10.3,v2.5 修订)

**v2.4 说"`mapping_context` 仅由 `ExcelLinkFeature` 写"与现有代码冲突。** 实测:

```csharp

// MappingStore.cs:519-521(WriteFile)

```

即推荐窗口的接受/扶正**本来就在产出条目范围学习**,并把它写进 `mapping_box` 行。
两种走法都不可接受:保留 ⟹ 办法上下文继续混在普通关系行里,双 `record_type` 设计失效;
直接删掉 ⟹ 推荐窗口形成的条目范围学习消失,是功能倒退。

**v2.5 定案(采纳复审推荐方案)**:

1. **`MappingStore.Accept/Correct` 成为 `mapping_context` 的合法写入端。**
2. 没有公式时,context 只写:`software_partition`、`method_no`、`entry_code`/`entry_name`、
   `box_id`、工程量签名、目标身份。**不写 `formula_*`**。
3. `MappingStore` 改为**从当前 `(software_partition, method_no)` 的 context 构造可用条目标签**,
   **不再**把上下文写入 `mapping_box.entry_codes`;`WriteFile` 删除 `entry_codes` 输出。
4. 它**只能新增或更新自己精确身份键对应的 context**;其他办法、其他分区与未识别记录
   **继续逐字节透传**。
5. **D4 仍只生成 `mapping_box`,不生成 context**(§6.4 第 6 步不变)。
6. `mapping_box` 中**不得再出现任何未分区的条目上下文字段**。
7. **公式多规则并存**:同一条目、同一目标、同一工程量下若形成过多个不同参数公式,
   按 §4.11 的身份键(含 `formula_rule_hash`)**各自成行并存**,不互相覆盖。

**读取拼接规则（拆 record type 后必须显式实现）**:

1. `mapping_box` 是普通关系、目标名称/单位、权重和计数的**唯一来源**；
   `mapping_context` 单独存在时不得创建推荐关系、目标或权重。
2. 先按当前 `software_partition` 载入并聚合 `mapping_box`，再按
   `(software_partition, box_id, quantity_signature, target_identity)` 把 context 挂到已有关系。
3. 条目/公式消费时，在上述关联结果上再精确过滤当前 `method_no`；无精确 context 即无条目/公式，
   **禁止**读其他办法、空办法或孤儿 context 兜底。
4. context 找不到对应 `mapping_box` 时视为孤儿：忽略并记录诊断，不得反向创建普通关系。
5. `MappingStore.BoxAllowedByScope` 只有在同一
   `(software_partition, method_no, entry_code, box_id, quantity_signature)` 下，
   该 box 的**全部 quota 目标**都有精确 context 时，才可把该条目视为整框已接受；
   否则只能继续走当前项目精确定额池逐目标校验，不能把单个目标 context 提升为整框标签。
6. `SmartFillFeature` 的本地回退/待同步叠加同样先建普通关系再挂 context；
   `mapping_context` 的默认 `weight=1` 绝不能参与 `MAX(weight/count)`。

### 4.11.2 两个正式写入端统一的双层保存与 splice 算法(复审 P0 11.3 + 12.2/P1 12.7,v2.8 闭合失败恢复)

**适用范围不是只有 `MappingStore`。** `mapping-boxes.jsonl` 的两个正式运行时写入端：

1. `RecoQuotaRecommend/MappingStore.Accept/Correct/Save/WriteFile`；
2. `RecoExpandPanel/ExcelLinkFeature.RecordMappingGroupsToStore/UpsertMappingBoxGroup`
   （包括 Excel 绑定、名字驱动回流和复用该入口的训练写入）；

同名 Mutex 实际还有**第三个持有者**:
`tools/ChapterQuotaLibrary/ChapterQuotaLibrary.cs:1402/1464` 的旧命令 `TagMappingBoxes`。
它按旧语义整文件重写,**不是**分区文件的合法写入端。
本文“两个正式写入端”的前提**只有在 Task B10 实现且 T26 通过后才成立**:该旧命令的写入模式
必须在本批**永久禁用**,仍须先取得同名 Mutex
并在锁内重新读取目标文件用于生成准确提示,随后无条件拒绝修改,原文件哈希不变;
发现任一可识别行含 `software_partition` 时必须明确提示“该工具尚未分区感知”。
在 B10 保护尚未实现或未验证前,禁止对分区后的 `mapping-boxes.jsonl` 运行该命令。

必须遵守**同一保存契约**。任何一侧继续“全部解析成字典 → 全部重新序列化”都会破坏另一侧
已经保存的 context，因此 B8 与 B9 必须同批完成，不能只改其中一个 DLL。

**双层模型**:

| 层 | 内容 |
|---|---|
| **第一层:原文层** | 按字节读取并记录 BOM/编码、每行原始字节、每行结束符与原始顺序；空行、无法解析的行、未知 `record_type` 也必须占一个原始槽位。这是写回基准 |
| **第二层:索引层** | 只为可识别的 `mapping_box` 和 `mapping_context` 建立“身份键 → 原始槽位列表”的定位索引；context 不进入 `CanonicalizeBoxes`，也不参与 box 的目标×样本重生成 |

新文件不存在时统一创建为 **UTF-8 BOM + CRLF**；已有文件必须沿用检测到的 BOM/编码，
新插入/替换行使用该文件的主行结束符。未被本次操作命中的原始槽位直接复制原始字节，
不得经过 JSON 反序列化/再序列化。

**context 写入规则（两个写入端完全相同）**:

1. 当前精确身份键无匹配 ⟹ 在文件末尾追加一行。
2. 恰好一条匹配 ⟹ 只替换该槽位；替换采用**字段级合并**：本写入端只更新自己拥有的
   标准字段，原行未知字段的键、值及与该行的对应关系必须保留，不得用新字典覆盖整行后丢失扩展字段。
3. 出现多条匹配 ⟹ **中止本次整个本地文件写入**，原文件哈希不变；日志写出身份键、
   命中行号和来源操作。禁止静默取第一条、批量覆盖或只写普通 box 后跳过 context。
4. 其他 context、其他分区、其他办法、未知记录、空行和无法解析行原始字节/相对顺序不变。

**`mapping_box` 确定性 splice 规则（解决行数增减）**:

1. 只对**当前 `software_partition`** 的 `mapping_box` 建模和重生成；其他分区及空/未知分区行
   作为非目标原始槽位保留，不参与当前进程合并。
2. 重生成行按完整身份键
   `(software_partition, box_id, target_identity, quantity_signature)` 升序固定排序。
3. 某身份键已有一个或多个旧槽位：聚合仍按 §4.11 第 2 条取 MAX；新行写入该组**最早槽位**，
   其余重复旧槽位删除。最早槽位上的未知字段做字段级保留；若多个重复槽位对同一未知字段
   保存了不同值，视为歧义并中止整个本地写入，禁止任选一个。
4. 旧身份键不再出现在重生成结果（例如样本被裁剪）⟹ 删除其全部当前分区 box 槽位。
5. 新身份键没有旧槽位 ⟹ 按固定排序插入“最后一个当前分区 box 原始槽位”之后；
   文件原本没有当前分区 box 时追加到文件末尾。多个新行一次成块插入。
6. 删除/插入只改变 box 槽位数量；所有非 box 原始槽位的**字节内容和彼此相对顺序**不变。

**样本上限与 context 清理**:

- `TrimMappingRows` 必须先筛 `record_type='mapping_box'` + 当前 `software_partition`，再按框统计最多 30 个样本；
  禁止继续按旧 `method + box_id` 把所有 record type 混在一起裁剪。
- 样本被裁掉时，只删除同一当前分区、同一 `box_id`、同一 `quantity_signature`、
  同一目标身份的关联 context；其他分区/办法/样本的 context 不动。
- 对应 context 若存在重复精确身份键，仍按上面的冲突规则中止整个本地写入，不得借裁剪静默清洗。

**冲突必须可见且可恢复(v2.8,对应 Claude P1-1)**:

### 4.12 `EntryScope` 必须有独立的分区来源(复审 P0 10.2,v2.5 新增)

**问题**:v2.4 要求 `EntryScope.Tag` 改为

if (processProbe.Contains("rejjnet2020")) return "2020";               // ← 唯一可信的一层

| 段 | 步骤 | 内容 |
|---|---|---|
| **第一段** | 3a | DDL-1:只给 `BindingLog` 与相关表**增加可空列**(`software_partition`、`method_no`),**保留旧聚合主键不动** |
| | 3b | 回填并校验 `BindingLog`(§5.2、§5.3),输出分区分布与隔离清单 |
| **第二段** | 3c | `-Finalize -RunId` 完成进程/备份/库身份/行数快照校验后，在事务内**截断派生聚合表**(`SignatureBoxMap`、`SignatureEntryMap`、`EngineeringTemplate`、`QuantityFormulaRule`/`Operand`、`QuotaBox`/`QuotaBoxTarget`/`QuantityAlias`、`SheetTemplateRow`) |
| | 3d | **同一事务内**执行 DDL-2:截断后删除旧主键 → 把新键列改为 `NOT NULL` → 建立新主键与索引；任一步失败整笔回滚 |
| | 3e | `-DryRun` → 人工核对 → 正式重建 |

> 顺序要点:**先截断、后改主键**。表空了就不会有重复键,`NOT NULL` 也不会因存量空值失败。

**回滚动作(逐步骤明确,不能只写"已有备份")**:

| 失败点 | 回滚 | 恢复后状态 |
|---|---|---|
| 3a DDL-1 失败 | 无需回滚(加可空列是幂等的);删除已加的列即可 | 与迁移前完全一致 |
| 3b 回填失败/校验不通过 | `UPDATE ... SET software_partition='', method_no=''` 清空新列(既有列从未改动) | 与迁移前完全一致 |
| 3c/3d 事务内任一步失败 | `-Finalize` 自动回滚整个事务；表数据、旧主键和旧列状态一并恢复。若 SQL Server 事务本身发生不可恢复故障，才使用已验证备份恢复 | 可用同一未消费 `run_id` 修正后重试 |
| **D1 任一 DLL/任一目录部分部署失败** | 保持三个宿主进程为 0;先按 W3 清单恢复**全部已触碰目标**的旧 DLL 并逐项验哈希。若可在窗口内修复,仍用同一暂存产物重新部署;不能修复则执行下方“整套回滚” | 禁止启动混合版本 |
| 3e DryRun 计数异常 | 事务回滚(脚本已在事务内);不进入正式重建 | 停在 3d 之后,表为空但主键已就绪 |
| 3e 正式重建失败 | 保持停机,修正后从完整 `BindingLog` 重跑;若无法在窗口内恢复则整套回滚 | 可重试或回滚 |
| **D4 反导失败/验收不通过** | 不解冻、不启动正式使用;可从确定性输入重跑 D4。若无法修复则整套回滚 | 不允许留下空本地框上线 |

**Finalize 提交后的整套回滚(v2.10)**:

1. 软件继续关闭,停止所有迁移/重建/部署脚本;核对 run_id、W3 产物清单、旧 DLL 备份哈希、
   C3 归档文件哈希和 SQL 备份 HEADERONLY 摘要。
2. 先把 D1 已触碰的所有目标 DLL 恢复为 W3 备份并验证哈希;任何单项恢复失败立即停止,
   不得启动软件或用更宽范围复制补救。
3. 把 C3 之后产生的目标文件移动为本次 run 的 `.failed-cutover` 证据,再从精确归档恢复原
   `mapping-boxes.jsonl`;禁止覆盖无法识别的新文件。
4. 从 `master` 查询目标库活动会话。存在不属于本次脚本的会话时停止并报告,不得自动
   `KILL`/`SINGLE_USER WITH ROLLBACK IMMEDIATE`;确认只剩本次维护连接后,使用已验证备份恢复
   `RecoLearning` 并再次核对库名、结构指纹、`BindingLog`/派生表行数与备份摘要。
5. 只有数据库、两个运行目录 DLL 和两份本地文件全部恢复并通过哈希/行数校验后,
   才把本地 run 原子标为 `rolled_back`;任一层未恢复都保持 W0,等待人工处理。

**关键保障**:`BindingLog` 只新增/回填新列，既有列与 `event_hash` 不改，是唯一的真相源；
3c+3d 不再暴露“已手工截断但尚未切键”的外部中间状态。所有派生聚合表仍可由
`BindingLog` 重建。`Finalize` 事务内故障先依赖事务回滚；`Finalize` 已提交后若 DLL、本地文件、
重建、反导或验收无法在窗口内修复，则必须按上面的整套回滚使用已验证备份恢复数据库，
不能只恢复其中一层。

### 7.5 DDL 的脚本边界(复审 P1 10.4,v2.5 新增)

**问题**:v2.4 定了 DDL-1 → 回填 → 截断 → DDL-2 的顺序,但没说**谁来执行**。
实测 `tools/RecoLearning/Initialize-RecoLearning.ps1:13-14`:

```powershell
$schema = Get-Content "$PSScriptRoot\schema.sql" -Raw -Encoding UTF8
[void](Invoke-RecoNonQuery -Sql $schema)
```

**无条件读取并一次性执行整个 `schema.sql`**。若把 DDL-1 与 DDL-2 都写进这个普通初始化入口,
日后有人重跑初始化,就可能在**未完成回填、未截断**的库上误触发第二阶段。

**v2.7 定案 —— 普通初始化与显式迁移彻底分开**:

| 工具/模式 | 允许做 | **禁止做** |
|---|---|---|
| `tools/RecoLearning/schema.sql` | 新库直接建立最终目标结构；旧库只执行非破坏性 DDL-1（加可空列/索引） | ❌ 截断任何表 ❌ 切换存量主键 |
| `Initialize-RecoLearning.ps1` | 建库 + 调用 `schema.sql` | ❌ 生成迁移 run ❌ 备份 ❌ 隐式进入 Finalize |
| `Migrate-LearningPartitionSchema.ps1 -Prepare -TargetDatabase <db>` | 即时进程检查；幂等执行 DDL-1；生成唯一 `run_id` 和 `prepared` 状态文件 | ❌ TargetDatabase 默认正式库 ❌ 截断 ❌ DDL-2 ❌ 自动选用旧 run |
| `... -RecordBackup -TargetDatabase <db> -RunId <id> -BackupPath <server-path>` | 即时进程检查；创建/验证本次 SQL Server 原生备份；把状态推进到 `backed_up` | ❌ 人工填写 `verify_state=true` ❌ 覆盖已存在备份文件 |
| `... -RecordDeploymentPreflight -TargetDatabase <db> -RunId <id> -ArtifactManifest <path>` | 验证暂存产物、目标白名单和回滚备份；推进到 `deployment_ready` | ❌ 编译或部署 DLL ❌ 接受清单外文件 |
| `... -Backfill -TargetDatabase <db> -RunId <id>` | 即时进程检查；事务内只回填/校验 `BindingLog` 新列；推进到 `backfilled` | ❌ 改既有列/event_hash/行数 ❌ 使用默认连接 |
| `... -Finalize -TargetDatabase <db> -RunId <id>` | 即时进程检查；验证同 run/同库/备份/产物/行数；**事务内执行 3c+3d** | ❌ 不带 RunId/TargetDatabase ❌ 自动选择“最新标记” ❌ 要求用户预先手工清空表 |
| `... -Abort -TargetDatabase <db> -RunId <id>` | 仅在未提交 Finalize 时把 run 标为 `aborted`，保留已有备份供审计 | ❌ 删除备份 ❌ 回滚已经提交的 schema |

**目标库强制路由(v2.10,P0)**:

1. B15 的 `Prepare`/`RecordBackup`/`RecordDeploymentPreflight`/`Backfill`/`Finalize`/`Abort` 都必须显式接收
   `-TargetDatabase`;任何写模式缺参立即拒绝,不得使用 `Common.ps1` 的默认 `RecoLearning`。
2. 入口只创建一次不可变的目标连接工厂;所有标量查询、DataTable、事务、BulkCopy、备份、
   扩展属性和状态指纹都必须接收该工厂或它创建的显式连接。禁止任一内层 helper 再调用
   无 `-Database` 参数的 `Get-RecoConnectionString`/`Invoke-Reco*`。
3. 正式模式只接受精确数据库名 `RecoLearning`;测试模式只接受 T24 在本次进程内生成的
   `RecoLearning_MigTest_<RunId>`。两种模式都必须核对服务器身份与 `db_identity_sha256`,
   测试模式还须核对当前 run 写入的数据库所有权扩展属性。
4. 每个破坏性事务在开始后、执行第一条写语句前,都用**同一连接和事务**断言
   `DB_NAME()` 等于精确 TargetDatabase、run 所有权/状态一致;不一致即回滚并拒绝。
5. 数据库标识只允许内部生成或严格白名单后使用 `QUOTENAME`;备份路径使用 SQL 参数,
   不得把调用者字符串直接拼入动态 SQL。日志/状态只保存数据库身份哈希,不得输出连接串或认证材料。

状态文件固定放在工作区内 `tools/RecoLearning/migration-state/partition-<run_id>.json`，
并加入 `.gitignore`；不得写连接串、账号、密码或原始服务器地址。数据库身份写成：

```text
db_identity_sha256 = SHA256(CanonicalDataSource + "|" + CanonicalInitialCatalog)
```

脚本只在内存中从现有连接配置取得两个值并计算哈希，状态文件只保存哈希。

**状态机与命令接口**:

1. `-Prepare -TargetDatabase ...`
   - 三个目标进程任一非 0 即拒绝；
   - 若同一数据库已有 `prepared`/`backed_up`/`deployment_ready`/`backfilled` 的活动 run，拒绝再开新 run；
   - 执行 DDL-1 后写 `state=prepared`、`run_id`、`db_identity_sha256`、
     `prepared_at`、DDL-1 后结构指纹；把 run_id 和状态文件路径明确输出给操作者。
2. `-RecordBackup -TargetDatabase ... -RunId ... -BackupPath ...`
   - RunId 必填，状态必须为 `prepared`，数据库身份和结构指纹必须一致；
   - `BackupPath` 是 **SQL Server 主机侧绝对路径**，必须包含 run_id；先通过 SQL Server 侧
   `master.dbo.xp_fileexist` 检查首次执行时不得已存在(§0.E 实测该扩展存储过程存在;
   SQL Server 2008 R2 不支持 2017 才引入的 `sys.dm_os_file_exists`);
   该唯一探针不可用时停止并报告,禁止猜测不存在；
   - 通过同一数据库连接执行 `BACKUP DATABASE ... WITH COPY_ONLY, CHECKSUM`；
   - 随后执行 `RESTORE VERIFYONLY ... WITH CHECKSUM` 与 `RESTORE HEADERONLY`，核对
     数据库名、备份完成时间、Position、BackupSize/CompressedBackupSize、FirstLSN/LastLSN；
     **禁止用客户端本地 `Test-Path` 代替 SQL Server 侧验证**；
   - 备份前后分别读取 `BindingLog` 与全部派生表行数，任一变化即不推进状态；
   - 若备份已成功但本地状态原子更新失败，允许同一 `prepared` run 以同一含 run_id 路径恢复：
     必须重新执行 VERIFYONLY/HEADERONLY，确认数据库名、备份完成时间不早于 `prepared_at`、
     当前行数仍等于 Prepare 快照；不得覆盖、追加或重新创建已存在备份；
   - 验证通过后原子更新为 `state=backed_up`，保存服务器侧路径、HEADERONLY 摘要、
     完成时间、结构指纹和各表行数快照。
3. `-RecordDeploymentPreflight -TargetDatabase ... -RunId ... -ArtifactManifest ...`
   - RunId 必填且只接受 `backed_up`;校验 B18 产物清单、暂存 DLL 实际哈希、精确运行目录白名单、
     旧 DLL 备份与本地文件当前哈希,全部通过后状态推进为 `deployment_ready`;
   - W3 证据固定为 **2 个批准运行目录 × 2 个白名单 DLL = 4 个完整路径目标**，按规范化完整路径去重；
     每个目录必须各有且只有一个 `RecoQuotaRecommend.dll` 和一个 `RecoExpandPanel.dll`。
     另有两条 `mapping-boxes.jsonl` 路径/存在性/哈希证据；缺项、第三目录、多余目标、跨目标回滚副本均拒绝；
   - 清单和备份只允许写入工作区内本次 run 的目录,不得触碰运行目录 DLL 或本地学习文件。
4. `-Backfill -TargetDatabase ... -RunId ...`
   - RunId 必填且只接受 `deployment_ready`；即时复核进程、库身份、备份、产物清单、结构指纹和
     Outbox，任一变化拒绝；
   - 在单一数据库事务内按 §5.2/§5.3 只更新 `BindingLog` 新列，所有查询/临时表/BulkCopy 都走
     同一目标连接工厂；第一条写入前再次断言 `DB_NAME()` 与 run 所有权；
   - 断言行数、既有列与 `event_hash` 不变，输出永久隔离审计清单；校验通过才提交并原子推进为
     `backfilled`，失败整笔回滚且保持 `deployment_ready`。
5. `-Finalize -TargetDatabase ... -RunId ...`
   - RunId 必填且只接受 `backfilled`；重新计算数据库身份、结构指纹并再次即时检查进程；
   - 再次执行 `RESTORE VERIFYONLY/HEADERONLY`，结果必须与状态文件摘要一致；
   - `BindingLog` 与派生表当前行数必须仍等于备份快照，Outbox 必须仍为空；
   - 通过后在一个 SQL 事务内按外键顺序执行 3c 全部 TRUNCATE，再执行 3d DDL-2；
   - 同一事务写入数据库扩展属性 `RecoLearningSchemaVersion='partition-v1'` 与
     `RecoLearningPartitionRunId=<run_id>`；任一步失败全部回滚，状态仍为 `backfilled`，
     修正原因后允许用**同一个 run_id**重试；
   - 提交成功后原子更新本地状态为 `consumed`。若仅本地状态更新失败，重试时必须先读取
     数据库扩展属性；只在其 run_id 与本次完全一致时补记 consumed，禁止再次 TRUNCATE。
6. `-Abort -TargetDatabase ... -RunId ...` 只接受未提交 Finalize 的活动 run；新 `-Prepare`
   只能在没有活动 run 时创建，`consumed`/`aborted` 的旧状态永不复用。

**执行授权边界**：`BackupPath` 会在工作区外的 SQL Server 主机写入备份文件。
正式执行 `-RecordBackup` 前，必须向用户说明并取得对**精确服务器侧路径、写入内容和原因**的明确同意；
设计评审和脚本实现本身不构成该外部写入授权。若当前数据库账号没有 BACKUP/RESTORE VERIFY 权限，
脚本必须停止并报告，禁止退化为“只写一个已验证标记”或跳过备份。

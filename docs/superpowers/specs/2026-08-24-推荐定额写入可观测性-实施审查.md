## 4. 发现

### 4.1 🔴 跨单元写入仍然做不到——拦截点换了，目标没达成

**实机现象**（用户 2026-08-24 复现，截图 + 日志双证据）：预览后在左侧树点击**另一个单元**下的条目再写入，弹出

> 项目或当前单元已切换，请重新预览

日志同步记录：

```
02:41:05 Smart fill apply rejected: 上下文不可写 项目或当前单元已切换，请重新预览
02:41:18 Smart fill apply rejected: 上下文不可写 项目或当前单元已切换，请重新预览
```

**根因（源码核对，两层）**：

**第一层：写入目标单元根本不来自树选中项。**

`TryResolveCurrentSmartEntry`（`TemplateFillPanel.cs:476-557`）解析出的条目**序号/编号/名称取自树选中节点**，但

```csharp
UnitId = selection.CurrentUnitId,     // TemplateFillPanel.cs:550
```

`selection` 来自 `CaptureAgentSelection(mainForm)`，即**宿主当前显示的单元**。所以 `entry.UnitId` 永远等于宿主当前单元，从来不是"树上点中的那个条目所属的单元"。用户点 B 单元的条目时，宿主会跟着切到 B，于是它其实变成了"同单元写入"，只是预览过期了。

**第二层：预览失效判定把"单元"算了进去。**

```csharp
// TemplateFillPanel.cs:2206-2213
if (!Object.ReferenceEquals(context.ProjectConnection, entry.ProjectConnection) ||
    !String.Equals(context.ProjectConnectionIdentity, entry.ProjectConnectionIdentity, ...) ||
    context.CurrentUnitId != entry.UnitId ||
    (!String.IsNullOrWhiteSpace(context.CurrentUnitCode) &&
     !String.Equals(context.CurrentUnitCode, entry.UnitCode, ...)))
{
    error = "项目或当前单元已切换，请重新预览";
    return false;
}
```

`context.CurrentUnitId` 是**建预览那一刻**宿主的当前单元（`:1263-1264` 捕获）。于是实际规则变成：**一次预览只能在建预览时的那个单元里写，换单元必须重新预览。**

**这个限制没有技术依据——预览内容与单元完全无关：**

| 证据 | 结论 |
|---|---|
| `SmartFillFeature.cs` 全文 `UnitId` 出现 **0 次** | 预览构建链路不读单元 |
| `LoadProjectQuotas`（`TemplateFillNameMatch.cs:1152-1183`）的 SQL 无 `总概算序号` 过滤 | 项目内定额身份是全项目口径，非按单元 |
| `context.CurrentUnitId` / `CurrentUnitCode` 在全仓**只被 `:2208-2210` 这一处读取** | 摘掉不影响其他逻辑 |
| 写入侧 `LoadSmartFillStructuralRow(conn, targetUnitSeq, itemSeq)`（`TemplateFillFeature.cs:1125`）本就按**目标单元**取结构行，三级兜底（目标条目 → 同单元 → 全表） | 换单元后仍能构造出正确业务行 |

且这与 2026-08-08 的拍板决定 2「**预览与左侧树选中完全解耦**」直接冲突——单元校验把二者又绑回去了。

**建议修复（改动很小，但要按顺序做）：**

1. **摘掉单元校验**：`:2206-2213` 只保留 `ProjectConnection` 引用相等与 `ProjectConnectionIdentity` 比对（跨项目防护必须留），删掉 `CurrentUnitId` / `CurrentUnitCode` 两个条件；`SmartPreviewContext` 里这两个字段随之退役。
2. **保持写入目标解析不变**：目标单元继续取临写入前重新解析的 `currentSmartEntry.UnitId`（宿主当前单元），`AGENTS.md:171` 要求的"事务开始前重新核对"照旧。改完后的实际效果是：**预览一次 → 在宿主里切到任意单元 → 直接写，不必重新预览**，`begin`/`ok` 日志的 `unit=` 会如实记录每次落点。
3. **不要**在本批引入"在推荐窗口里显式选择目标单元"。那是另一种交互（真正意义上的"宿主停在 A、向 B 写"），涉及树解析与条目唯一性的额外校验，应另立一批并单独验收。

**验证方法**（改完后一次点击即可）：预览 → 切到单元 B 的条目 → 写入 → 日志 `begin`/`ok` 的 `unit=` 为 B，`plan` 的 `entries=` 为 B 的条目编号 → 库内 `select … where 总概算序号=@B and 条目序号=@X` 核对 → 确认单元 A 未被误写。

### 4.2 🟡 补充 SF 后不重算 SF 双向约束，整组阻断要到点写入才暴露

`RefreshSmartSfEntryState()` 只在 `RefreshCurrentSmartEntry`（`TemplateFillPanel.cs:577`）里调用；右键绑定收尾走的 `RefreshTargetGroupInGrid`（`:1493`）只重画行、不重算 `SfEntryBlocked`。

于是在**没有唯一同级设备购置费条目**的条目上使用"补充"：

- 界面不标红、写入按钮照常可点；
- 点写入才收到「未找到唯一同级设备购置费条目，所选组件整组未写入」；
- 而且是**整组**被挡——`IsNameQuotaGroupSafeForWrite`（`TemplateFillFeature.cs:1052-1057`）只要任一成员 `SfEntryBlocked` 即判整组不安全，**原本可写的普通定额被一起挡住**。

不是数据风险（阻断方向正确，且有日志），是白做一次操作。

**建议**：`if (appendToExisting)` 之后补一次 `RefreshSmartSfEntryState()`；更好的是在弹「替换/补充」对话框**之前**先探测同级设备购置费条目，没有就当场告知，别让用户补完才发现整组写不了。

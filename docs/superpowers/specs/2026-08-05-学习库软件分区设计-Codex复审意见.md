# 学习库软件分区设计 Codex 复审意见

日期：2026-08-05  
评审对象：`docs/superpowers/specs/2026-08-05-学习库软件分区与跨版本同编号异义-design.md` v2.0  
代码基线：`0c97368`  
评审结论：**v2.0 暂不通过执行评审；完成本文阻断项并修订为 v2.1 后再复审。**

> 本文件仅记录审查意见。评审过程中没有修改原设计、代码、SQL、学习数据或部署文件。

## 1. 已确认的业务口径

1. 2024 软件只使用在 2024 软件中形成的学习关系。
2. 2020 软件只使用在 2020 软件中形成的学习关系。
3. 2020 软件内，30号文与101号文估算可以共享普通定额关系。
4. 条目放置证据不能共享，必须按 `method_no` 区分30号文、101号文估算和 `TB 10801—2024`。
5. `SH`、`SQ`、`ZLF`、`LF`、`SF` 等辅助代码继续使用“完整编号 + 规范化名称 + 规范化单位”识别，本批不引入标准名称门禁。

## 2. 总体评价

v2.0 已正确吸收上一轮大部分意见，以下方向可以保留：

- 删除按 2026-08-05 时间点回填历史流水的方案；
- 删除 `method=''` 兼容回退；
- 将专业范围改成硬限制，不再退回全部学习库；
- 把本地 `mapping-boxes.jsonl`、Outbox、SQL聚合和两个推荐读取端纳入分区链路；
- 使用实际运行进程判定软件分区，禁止根据目录内存在的EXE推断；
- 把聚合重建改成冻结绑定写入的维护窗口；
- 将标准名称体系、残留索引删除和101号文 `ChapterEntry` 补齐移出本批；
- 保持组件框原子性，任一成员失败时整组不得自动写入。

但当前仍有两个P0级结构缺口。若按v2.0直接实施，2020内部条目仍可能在30号文和101号文之间串用，并且条目相关公式也可能跨办法复用。

## 3. P0阻断项

### 3.1 `method_no` 没有进入原始流水链路

v2.0 在目标聚合表中增加了 `method_no`，但没有说明它从哪里来、如何持久化。

当前代码事实：

- `MappingFeedbackGroup` 只有 `Method`，没有 `MethodNo` 和 `SoftwarePartition`；
- `PrepareLearningGroupsForOutbox` 会把项目办法归一化成 `2020` 或 `2024`；
- 30号文和101号文估算都会被归一为 `2020`；
- 当前 `BindingLog` 没有 `method_no` 列；
- 当前Outbox和本地 `mapping-boxes.jsonl` 也没有可靠的 `method_no` 字段；
- 因此全量重建读取 `BindingLog` 时，已经无法判断一条2020条目证据来自30号文还是101号文估算。

#### 必须修改

新增并贯穿以下字段：

```text
项目原始编制办法
  -> MappingFeedbackGroup.MethodNo
  -> mapping-boxes.jsonl
  -> LearningDbOutboxBatch / 组级字段
  -> BindingLog.method_no
  -> SignatureEntryMap / EngineeringTemplate / 条目相关公式
  -> SmartFill精确读取
```

建议模型：

- `SoftwarePartition`：只由实际运行进程产生，值域为 `2020`、`2024`；
- `MethodNo`：由项目原始编制办法产生，规范化为 `30号文`、`101号文估算`、`TB 10801—2024`；
- 旧 `method`：暂时保留作兼容和审计，不再作为新关系的真实分区键。

#### 历史数据处置

- `method='2024'` 的历史流水可回填：
  - `software_partition='2024'`
  - `method_no='TB 10801—2024'`
- `method='2020'` 的历史流水只能可靠确定软件分区为2020，不能仅凭该字段判断30号文或101号文。
- 无可靠 `method_no` 的2020历史流水：
  - 可以生成 `software_partition='2020'` 下共享的普通定额关系；
  - 不得生成 `SignatureEntryMap`、`EngineeringTemplate` 或条目相关公式证据；
  - 原始流水必须保留，等待可靠来源或人工确认后再补充条目证据。
- `method=''` 且没有其他可靠来源的流水继续隔离，不得自动归类。

### 3.2 条目相关公式必须同时按 `method_no` 隔离

v2.0 只要求在 `QuantityFormulaRule.rule_hash` 中加入 `software_partition`，仍不充分。

现有公式身份包含 `entry_code`，说明公式与目标条目有关。30号文与101号文存在同编号异义条目；若公式哈希没有 `method_no`，同一个软件分区内仍可能发生以下碰撞：

```text
2020 + 30号文 + 条目0101-...
2020 + 101号文估算 + 同编号但异义的条目0101-...
```

#### 必须修改

- `QuantityFormulaRule` 增加 `software_partition` 和 `method_no`；
- C#与PowerShell两侧 `ruleRaw` 同时包含这两个字段；
- 公式读取同时按 `(software_partition, method_no)` 过滤；
- 本地公式行和Outbox公式字段也必须保存 `method_no`；
- 跨语言哈希一致性测试必须增加“同一输入只改变 `method_no`，哈希必须变化”的断言。

## 4. P1必须补齐项

### 4.1 条目歧义只有标红，没有可操作的人工选择入口

v2.0 要求条目不唯一时设置：

```text
Selected=false
NeedExactNameConfirmation=true
```

这只能阻止自动勾选，不能让用户选择正确条目。

当前候选下拉以组件框为单位，候选键主要是 `smart:<box_id>`。同一个组件框内存在多个条目证据时，现有代码会把它们折叠成一个结果，而不会生成多个可选条目。

#### 必须二选一并写入设计

推荐方案：

- 将候选展开为“组件框 + 各目标条目组合”；
- 候选键至少包含 `box_id + target entry_code集合`；
- 继续复用现有下拉控件显示完整组件与目标条目；
- 用户选择后才能勾选整组。

保守方案：

- 条目不唯一时不提供可确认推荐；
- 明确提示“条目不唯一，请手工放置”；
- 不允许通过点击复选框默认接受排序第一项。

### 4.2 未知进程不能进入普通重试Outbox

进程未知属于永久缺少来源证据，不是数据库临时连接失败。若将这种批次放入普通Outbox，之后可能在另一软件进程中重放，从而被错误标记为重放时的软件分区。

#### 必须修改

- 在写本地 `mapping-boxes.jsonl` 之前解析 `SoftwarePartition`；
- 未知进程不得写本地学习关系，也不得进入普通重试Outbox；
- 直接进入隔离/dead-letter，记录批次ID、源操作、当时进程名、主模块文件名和拒写原因；
- 重放时只能使用批次创建时已经保存的分区，禁止根据重放进程重新推断；
- 旧Outbox若缺少分区，只能按批次中已有的可靠历史字段回填，无法确认的立即隔离。

### 4.3 旧本地 `mapping-boxes.jsonl` 的处理必须拍板

当前活动文件只读统计：

| 活动文件 | 总行数 | `software_partition`缺失 | `method`分布 |
|---|---:|---:|---|
| 2024运行目录 | 266 | 266 | `2024=128`、`30号文=80`、空值58 |
| 2020运行目录 | 182 | 182 | 空值182 |

按v2.0 B5“旧行全部隔离”执行后，两边本地组件框都会暂时归零，直接影响模板铺量和本地推荐插件。

#### 必须明确选择

方案A：接受全部隔离并重新积累。

- 在设计和上线提示中明确影响；
- 验收必须确认SQL分区关系仍可提供预期推荐；
- 不得把推荐骤降误判为代码故障。

方案B：制定一次性本地回填。

- 只能使用行内可靠 `method`、可核对的SQL流水或人工确认；
- 不得在运行时仅依据目录名自动推断；
- 目录归属若用于一次性迁移，必须作为人工确认后的迁移输入，而不是通用程序规则；
- 回填后输出原行数、各分区行数、隔离行数和逐行差异清单。

### 4.4 阶段B、C、D不能以不兼容的中间状态上线

若先部署阶段B的新读取逻辑，而历史数据尚未完成阶段C回填和阶段D重建，现有关系会因分区为空而全部不可见。若还有旧版插件运行，又会继续写入没有新字段的数据。

#### 必须增加切换顺序

建议将以下操作放入同一个维护窗口：

1. 关闭2020和2024目标软件，冻结两侧绑定写入；
2. 备份数据库或至少备份 `BindingLog`、受影响表结构和迁移前统计；
3. 执行幂等DDL；
4. 完成 `software_partition` 与可靠 `method_no` 回填；
5. 部署同时支持新schema的两侧插件；
6. 执行 `Rebuild-Aggregates.ps1 -DryRun`；
7. 人工核对后执行正式重建；
8. 完成双软件交叉验收后再解冻写入。

如果不采用一次维护窗口，则必须增加数据库schema版本或功能开关：在回填、重建和两侧插件升级全部完成前，不允许启用新的分区读取条件。

阶段A可以不占用数据库维护窗口，但部署DLL仍需关闭对应软件，标题应写成“无数据库停机/无DDL”，不能让人理解为软件运行中也可覆盖插件。

## 5. 对v2.0开放问题的明确意见

### 5.1 `SignatureBoxMap` 主键是否保留 `method`

建议目标主键使用：

```text
(software_partition, signature, box_id)
```

原因：普通定额关系按软件分区共享，30号文和101号文不需要在该表继续拆分；当前 `method` 已被归一为 `2020/2024`，与新分区字段实质重复。

旧 `method` 列可暂时保留用于兼容、审计和迁移核对，但不再作为新主键的一部分。若决定继续保留在主键中，必须增加一致性约束并证明不会产生 `software_partition='2020', method='2024'` 等矛盾组合。

### 5.2 758条2024历史流水的判定依据

已重新查询确认：758条的直接判据就是2026-08-05之前 `BindingLog.method='2024'`。

来源分布：

| 来源 | 行数 |
|---|---:|
| `import:excel-links` | 494 |
| `import:mapping-boxes` | 37 |
| `plugin:excel-bind-batch` | 169 |
| `plugin:name-match` | 58 |
| 合计 | 758 |

因此v2.0 §5.2优先级1已覆盖这758条，§11中对应问题可以关闭。

空 `method` 的265条也重新确认仍由以下来源组成：74 + 125 + 13 + 53。

### 5.3 `SheetTemplateRow` 是否增加分区

建议本批不修改 `SheetTemplateRow`。

该表目前是预留原料，没有插件读取者。为了本次推荐定额软件分区而单独修改它会扩大迁移范围，但不能解决当前用户问题。

如果以后启用该表，由于它保存 `entry_code`，应同时设计 `software_partition + method_no`，不能只增加软件分区。

### 5.4 `QuotaBox` / `QuotaBoxTarget` 是否保持共享

本批可以保持不变，但必须补充正向回归：

- 相同编号在2020分区推荐时，展示和换算使用2020当前定额元数据；
- 相同编号在2024分区推荐时，展示和换算使用2024当前定额元数据；
- 即使两个分区共享同一 `box_id`，后写入的 `QuotaBoxTarget.target_name/target_unit` 也不得影响当前版本最终名称、单位、数量换算和可写性判断；
- 伪代码仍按名称和单位形成不同身份。

除v2.0已有测试外，至少增加以下断言：

## 8. v2.2 第二次复审（追加）

### 8.1 复审结论

v2.2 相比上一版有明显改进，以下方向已经基本正确：

- `MethodNo` 已纳入端到端模型；
- 公式身份已加入 `software_partition + method_no`，并明确公式必须具备条目证据；
- 未知进程改为在本地学习文件和 Outbox 写入前直接隔离；
- 候选组件组合、候选数量上限和人工确认边界已有说明；
- 迁移改为单一维护窗口，并补充了历史数据降级矩阵；
- 明确旧本地学习文件在迁移后废弃，不再和 SQL 结果混合使用；
- `SignatureBoxMap` 主键方案已明确。

但本轮代码对照发现，v2.2 仍遗漏多个实际写入端和反向导出语义，且“2020 软件内 30号文与101号文共用普通绑定关系”的业务规则与当前本地过滤设计仍有冲突。因此，**当前版本仍不具备执行条件，应先修订为 v2.3 后再评审**。

### 8.2 P0：遗漏 `RecoQuotaRecommend/MappingStore.cs` 这个运行时写入端

设计在“本地读取端”中提到了 `MappingStore.cs`，但没有把它作为写入链的一部分处理。实际代码中：

- `MappingStore.Accept`、`MappingStore.Correct` 会调用 `Save()`；
- `MappingStore.WriteFile` 会整文件重写 `mapping-boxes.jsonl`；
- 当前写出字段只包含旧版框、目标、名称、单位、权重和计数字段，不能保留新增的 `software_partition`、`method_no`、目标条目、公式等字段。

这意味着即使迁移工具生成了正确的分区文件，只要用户在运行时接受或扶正一次推荐，整份文件中的新字段就可能被抹掉；下一次按分区读取时，这些记录会被隔离或丢失。

v2.3 必须补充：

1. 把 `MappingStore.Accept/Correct/Save/WriteFile` 纳入完整写入链；
2. 写入前先确定当前软件分区，未知进程不得落入正式文件；
3. 内存模型必须承载新字段，或者改为能够保留未知字段和富字段的安全局部更新，不能继续用旧模型整文件覆盖；
4. 增加回归用例：接受、扶正后，分区、办法、条目、公式及其他扩展字段均保持不变。

### 8.3 P0：普通绑定关系不应再按 `method_no` 硬过滤

v2.2 的本地 JSON 方案要求保存 `method_no`，并在 `SelectSmartLocalRowsForMethod` 中同时按 `(software_partition, method_no)` 过滤。但已经确认的业务规则是：

- 2024 软件只使用 2024 软件形成的关系；
- 2020 软件只使用 2020 软件形成的关系；
- 2020 软件内的 30号文与101号文，普通“工程量名称 → 组件框”关系可以共用；
- 条目证据和公式仍必须按具体办法隔离。

因此应把两类证据拆开：

1. **普通组件关系**：只按 `software_partition` 选择；
2. **条目上下文和公式**：必须精确按 `method_no` 选择；
3. D4 或历史关系只有普通关系证据时，允许 `method_no` 为空，但该记录绝不能贡献条目或公式证据；
4. 同一普通关系若存在多个办法来源，应在关系层去重或聚合，不能把某一办法的条目证据带到另一办法。

这里不是恢复“空值跨分区回退”。`software_partition` 仍然是硬边界，任何空分区或其他分区记录都不能参与推荐。

### 8.4 P0：D4 的 SQL → 本地文件反向导出规则不完整

v2.2 仅说明由 `SignatureBoxMap + QuotaBoxTarget`，必要时再带条目数据导出本地文件，但这些表不能单独还原现有 JSON 消费端所需语义：

- `SignatureBoxMap` 没有原始 `quantity_name`；实际本地检索会用 `quantity_name`、单位及计数构造样本；
- 原始工程量名称和单位应来自 `QuantityAlias`，同一签名可能对应多个别名；
- `QuotaBoxTarget.target_name/target_unit` 是全局共享字段，同编号在 2020、2024 含义不同时，可能被后写入的软件版本覆盖；
- `MappingStore` 的本地推荐会直接使用文件中的目标名称和单位，不能假定所有消费端都会在运行时重新查当前定额库。

v2.3 应把反向导出定义为确定性流程：

1. 按 `software_partition` 分别导出；
2. 通过 `QuantityAlias` 还原工程量名称和单位，可为同一签名输出多个名称样本；
3. 权重和接受/纠正计数从 `SignatureBoxMap` 读取；

## 1. 总体结论

v2.1 已关闭上一轮的大部分方向性问题，但**仍不能直接进入源码实施**。当前只适合执行“阶段 0：纯文档修订”。Claude 应先把设计修订为 v2.2，并完成本文件所有 P0 阻断项和内部一致性检查，再申请进入编码。

本轮最重要的架构纠正是：

1. `SF`、`SH`、`ZLF`、`LF`、`TLF` 等辅助代码不是宿主可检索补齐的正式编号，**禁止按“编号 + 数量”走原生粘贴**；
2. `SF` 必须取得字段完整、来源明确的历史业务记录，然后以“项目业务表 SQL 完整行复制”写入设备购置费条目；
3. 当一个组件的全部目标都有完整源行时，普通行、`SF` 行及 marker 必须在当前项目的**同一个 SQL 事务**内写入；
4. 原生粘贴只保留给宿主能按编号完整补齐的正式定额和有正式编号的材料，并明确属于独立的非事务兜底路径；
5. “项目业务表 SQL 写入”和“学习库 SQL 回流”是两条不同链路。只有整个组件完整写入成功后，才允许向 `RecoLearning` 写 `apply-accept`。

因此，v2.1 中“SF 走原生粘贴”“先原生粘贴、后 SQL 提交”“SF 导航后恢复条目”等设计基础已经失效，必须删除或重写，不能只在验收标准里打补丁。

## 2. 用户已确认的业务事实

以下是本次设计的上位事实，不是待 Claude 再拍板的建议。

### F1. 宿主原生输入的能力边界

- 宿主只能根据**正式定额编号**和**有正式编号且宿主可检索的材料编号**补齐完整信息。
- `SF`、`SH`、`ZLF`、`LF`、`TLF` 等辅助代码不是宿主可检索补齐的正式编号。
- 只粘贴 `SF + 数量` 不能补齐名称、单位、价格及必要业务字段；之后点击“计算”也不能把它补成完整业务行。
- 因此所有辅助代码都禁止退回“只粘贴编号”的原生输入路径。

### F2. 原生粘贴与“计算”的含义

- 原生粘贴动作本身就会触发新增记录落库，不需要点击“计算”才保存。
- “计算”只负责刷新单价、合价、费用、小计和项目汇总等派生结果。
- 文档不得再把“点击计算”写成原生输入落库的前置条件，也不得用“计算成功”替代新增行数据库确认。

### F3. 模板铺量的主写入路径

默认路径是“项目业务表 SQL 完整行复制”：

1. 从当前项目已有的 `定额输入` 行，或来源明确的历史项目数据库中读取完整记录；
2. 修改目标单元、目标条目序号、顺号和当前工程数量；
3. 直接插入当前项目 `定额输入` 表；
4. 只有无法取得完整源行、但编号又确实能被宿主原生识别并完整补齐的正式定额或正式材料，才允许原生粘贴兜底。

### F4. `SF` 的唯一允许写入方式

- `SF` 必须取得字段完整、来源明确的历史业务记录；
- 将完整 `SF` 记录复制到当前项目合法的“设备购置费”条目；
- 修改目标单元、目标条目序号、顺号和当前工程数量；
- 找不到完整 `SF` 源行时，整个组件组阻断；
- 阻断时不得写同组普通行，不得产生 marker，不得产生 `apply-accept`。

### F5. 两种 SQL 必须使用不同名称

设计全文必须固定区分：

| 名称 | 写入对象 | 作用 |
|---|---|---|
| **项目业务表 SQL 复制写入** | 当前项目的 `定额输入` 及本批 marker | 把完整业务记录写进当前项目 |
| **学习库 SQL 回流** | `RecoLearning.BindingLog` 及相关增量聚合 | 在整个组件完整成功后记录接受反馈 |

不得再用“SQL 写入”“SQL 侧”混指这两条链路。

## 3. P0：实施前必须修正

### P0-1. 删除所有“SF 原生粘贴”设计，重建写入路径分类

v2.1 的 §0.6、§4.10.1.1、§4.10.3、§4.10.4、阶段 4/5、验收 31、风险 7.3 和关闭表仍反复要求：

- 先原生粘贴库内定额/`SF`；
- 为 `SF` 导航到设备购置费条目；
- 恢复原树节点；
- 原生成功后再提交 SQL；
- 原生部分成功时执行补偿。

这些内容与 F1、F4 冲突，必须从设计中清除。不能保留为“备用方案”或只改措辞。

v2.2 应只保留三类路径：

#### A. 完整源行事务路径——默认路径

适用于组件内每个目标都能取得完整源行的情况，包括普通定额、正式材料和 `SF/SH/ZLF/LF/TLF` 等辅助目标。

执行顺序：

1. 写入前完成整组预检；
2. 为每个目标解析完整源行及来源身份；
3. 确定普通目标条目和 `SF` 的设备购置费目标条目；
4. 在当前项目连接上开启一个项目业务表 SQL 事务；
5. 在同一事务内复制全部业务行并写入本批 marker；
6. 任一行、任一 marker 或顺号分配失败，整个事务回滚；
7. 提交成功后形成带项目连接身份的 undo 记录；
8. 整个组件确认完整成功后，才执行学习库 SQL 回流。

混合组件中的普通行和 `SF` 行即使落到两个不同条目，只要都有完整源行，也必须属于同一个项目业务表 SQL 事务。

#### B. 正式编号原生兜底路径——独立非事务路径

只适用于无法取得完整源行，但宿主能按编号完整补齐的正式定额或正式材料。任何辅助代码都不得进入该路径。

如果一个组件需要此路径，设计必须明确它不具备数据库事务原子性，不能继续使用“同一 SQL 事务完成整组”的表述。必须完整定义：

- 原生写入前的项目连接、当前单元和目标条目确认；
- 写入前后的 `定额输入` 行集合差异；
- 预期行数与实际新增行数核对；
- 延迟落库的等待、再次读取和最终超时口径；
- 部分成功时对本批已确认新增行的定点补偿；
- 补偿失败时，异常返回前压入带连接对象与 `DataSource|Database` 身份的撤销记录；
- 原生失败、部分成功或补偿状态不确定时，禁止 marker 成功确认和学习回流；
- 不得依靠提示字符串判断成功，应返回结构化的新增 ID、预期数、确认数和失败状态。

如果一个组件同时含“有完整源行的目标”和“需要原生兜底的正式目标”，整个组件都应标记为**非事务执行计划**。建议固定顺序为：先执行并确认全部正式编号原生目标，再用一个项目业务表 SQL 事务写入其余完整源行和全部 marker；任一原生目标失败时补偿此前已确认的原生行，后续 SQL 不启动；后续 SQL 事务失败时先回滚事务，再补偿已确认的原生行。补偿未完全成功时必须进入可撤销的部分失败状态，且始终不学习。不得把其中的 SQL 子集成功误称为“整个组件事务原子”。

最简单安全的执行策略是：**有任一辅助目标却缺完整源行时直接整组阻断；只有全部缺源行目标都是正式可识别编号时，组件才可能进入原生兜底分支。**

#### C. 学习库回流路径——成功后的独立步骤

学习库 SQL 回流不是项目业务事务的一部分，也不能反过来决定项目业务写入是否成功：

- 只有组件全部业务行和 marker 完整成功，才能生成 `apply-accept`；
- 项目业务写入失败、原生部分成功、补偿中或最终状态不确定时，均不得学习；
- 学习库写入失败不得回滚已经成功的项目业务写入，但必须提示“业务写入成功、学习回流失败”；
- `BindingLog` 仍按每个 target 一行、同一 `group_key` 的既有口径写入。

### P0-2. 重新定义事务、marker 与撤销边界

v2.2 必须明确：

1. 完整源行路径的一次组件写入只有一个项目业务表 SQL 事务；
2. 事务覆盖普通行、跨条目 `SF` 行和本批全部 marker；
3. 任一目标失败即回滚，回滚后应为 0 新业务行、0 marker、0 `apply-accept`；
4. marker 数量必须写死。建议每个本批实际写入的目标条目写 1 条 marker，并与同批 undo 绑定；混合普通/`SF` 跨两个条目时应明确预期为 2 条，而不是继续使用含糊的“整批 1 条”；
5. SQL 事务失败不应产生撤销记录，因为没有已提交行；提交成功后才产生完整批次 undo；
6. 原生兜底路径的 undo 必须按实际确认新增 ID 建立，并处理补偿失败场景；
7. undo/redo 均保存并复核预览时的宿主连接对象引用、`DataSource|Database`、当前单元、软件分区和办法号。

原审查中关于“SF 原生粘贴后恢复树节点”“SF 导航重入抑制”的建议随 F4 一并作废。本设计不得为 SQL 完整行复制而主动切换宿主树节点；`TryNavigateToAgentItem` 等方法可能仍被其他功能使用，但不能因本批而全局删除。

### P0-3. 整组阻断必须在集合构建时真正实现

v2.1 §4.10.1 仍使用逐行 `Where(... !i.SfEntryBlocked ...)`。这会排除被阻断的 `SF` 行，却让同组普通行继续写入，与“整组阻断”冲突。

必须改成：

1. 先按 `TargetRow` 建立完整组件组；
2. 对组内每个目标执行状态、数量、单位、来源、目标条目、`SF` 完整源行等预检；
3. 任一目标不安全，整组不进入执行集合；
4. 全组通过后才展开为事务写入行或正式编号原生兜底计划。

`IsNameQuotaGroupSafeForWrite` 如继续复用，也必须取消旧的“必须含主定额或纯 SF”限制，避免误伤纯 `SH/ZLF/TLF` 组件。

### P0-4. 项目身份门禁必须覆盖整个执行窗口

v2.1 已加入预览时连接身份保存，但 Apply 比较项仍不完整，而且原生路径中的 `Application.DoEvents` 可能在执行中允许项目或单元切换。

v2.2 应定义 `SmartPreviewContext`，至少保存：

- 宿主 `SqlConnection` 对象引用；
- 不含密码的 `DataSource|Database`；
- 当前单元身份；
- `software_partition`；
- `method_no`；
- 当前专业范围选择及生成时间/版本。

门禁要求：

- Apply 在任何 marker、导航或业务写入前比较全部身份；
- 完整源行事务路径在事务开始前再次比较；
- 原生兜底路径在每组执行前及确认完成后比较；
- 项目、单元、软件分区或办法变化后旧预览立即失效；
- 预览失败时清空旧 `SmartPreviewContext`，不得让按钮重新启用旧计划；
- undo/redo 使用其记录的连接对象和身份，禁止作用于新切换项目。

### P0-5. 纯辅助开放还有第三道学习范围门禁

v2.1 只计划修改：

- `IsSmartTargetSetRecommendable`；
- `IsLearningGroupRecommendable`。

但 `EngineeringTemplate` 增量写入还经过 `IsEngineeringScopeLearningTarget`：

- `ExcelLinkFeature.cs:2850-2854`；
- `LearningDbFeature.cs:1146-1152`。

如果不修改，纯 `SH/ZLF/TLF` 即使产生 `BindingLog` 和聚合，也不会建立专业范围。阶段 6 必须把第三道门禁及测试列入修改清单。

同时，现有以下测试断言的是旧行为，不能再要求“不改且保持绿”：

- `Test-LearningDbIncrementalAggregate.ps1:348`；
- `Test-QuantityFormulaLearning.ps1:368`；
- `Test-SmartFill.ps1:299`。

现行 `AGENTS.md` 也仍禁止纯辅助普通推荐。用户已经决定开放后，规则修订必须前移到阶段 0，在源码修改之前完成。

### P0-6. 公式范围过滤与合并仍没有可实现的数据模型

v2.1 要求“先按专业范围过滤，再合并样本数”，但合并对象只保存 `EntryCodes` 集合。集合无法保留各条目分别贡献的 `SampleCount` 和 `LastSeen`。

当前 `LoadSmartLearningSnapshot` 又不接收范围，`snapshot.SelectedScope` 是加载完成后才赋值。

建议只保留一种简单实现：

1. 快照保存不可变的原始公式分片；
2. 每个分片至少保存 `EntryCode`、`SampleCount`、`LastSeen`、目标单位、公式模板和有序操作数；
3. `SelectContextualSmartFormulaRules` 先在副本中按当前范围过滤分片；
4. 再对过滤后的分片合并和排序；
5. 明确 `EntryCode` 规范化与空值语义；空值不得默认为跨专业通配符。

### P0-7. 节点判定仍可能写错条目

v2.1 正文要求 `SelectedNode.Tag` 优先和三方核对，但新 helper `IsAgentTreeStandingOnItem` 又调用旧 `ResolveChapterNo`。如果旧属性表滞后，它可能误判“已站在目标条目”。

另外，`章节表 where 条目编号=@bh` 恰好一行只证明编号唯一，不能证明当前节点是可输入定额的叶节点。

必须：

- 所有当前节点判断复用同一个“Tag 优先、节点/数据库/宿主状态一致”的解析结果；
- 给出宿主可写叶节点的可靠证据，不能以 SQL 唯一行数代替；
- 覆盖父级节点、懒加载节点、属性表滞后和快速切换节点；
- `SF` 完整行 SQL 复制只使用解析后的目标条目序号，不为写入而导航宿主树。

### P0-8. UI 禁用状态和布局方案不闭合

SQL 学习快照不可用时设计要求禁用写入，但当前 `SetBusy(false)` 会无条件重新启用 Apply。应使用持久状态和统一入口，例如：

- `smartPreviewReady`；
- `smartLoadStatus`；
- `currentEntryWritable`；
- `SmartPreviewContext`；
- `RefreshApplyEnabled()`。

预览熔断、项目身份变化、节点不可写或整组全部阻断时，Apply 必须保持禁用。

布局方面，现有 grid 是 `DockStyle.Fill`，顶部控件却是绝对定位。不能把 grid 直接加入整个窗体，否则会覆盖工具栏。应增加工具栏下方的 `gridHost Panel`，或保留并折叠现有 `SplitContainer`。

## 4. P1：执行计划与验收门禁

### P1-1. 真实 UI 验收必须发生在新 DLL 受控部署之后

v2.1 在阶段 3、4 就要求真实 UI 点击，但阶段 8 才构建和部署。此时软件仍加载旧 DLL，顺序不可执行。

应改为：

1. 修改源码和自动测试；
2. 复核任务文件差异；
3. 提交/确认任务提交；
4. 从确认提交生成干净源码快照并 `BuildOnly`；
5. 建立隔离测试运行目录并让全部反射测试指向同一新 DLL；
6. 受控部署单个 `RecoExpandPanel.dll`；
7. 用户执行真实 UI 验收，代理只读核对；
8. 若失败则回到修改、提交、构建、部署循环；
9. UI 全部通过后才更新工作区内发布包。

### P1-2. 阶段 8 必须改为单 DLL 发布

本批声明只修改 `RecoExpandPanel`，但普通 `RecoQuotaRecommend/build.ps1` 会复制多个插件、Harmony、图标和 `RecoQuotaData`；`BuildColleaguePluginRelease.ps1 -Force` 会删除并重建整套发布包。

这与项目规则“仅更新 `RecoExpandPanel.dll` 时不得重建或复制其他 DLL、RecoQuotaData”冲突。

v2.2 必须定义验证过的单 DLL 流程，至少包括：

- 从确认提交构建 `RecoExpandPanel.dll`；
- 定向提升到仓库 `bin`；
- 确认宿主进程关闭后，只同步目标运行目录的该 DLL；
- 只更新发布包中对应的首次安装和 `90-后续更新文件` DLL；
- 重算并验证 `文件清单-SHA256.txt`；
- 核对 `bin`、运行目录、首次安装包、后续更新包的 SHA256；
- 用 marker/时间戳确认软件实际加载本次 DLL；
- 明确旧 DLL 备份和回滚路径；
- 不触碰 `D:\AI文件\同事模拟目录`。

### P1-3. 所有真实写入都可能永久改变学习库

v2.1 的污染清单漏掉了阶段 4 三批写入、验收 23 双批写入和验收 32 写入后撤销。这些操作同样可能产生 `apply-accept`；业务撤销不会自动删除 `BindingLog` 或回滚聚合。

“使用一次性唯一工程量名称”只是隔离永久测试记录，不是避免污染。所有真实写入用例必须统一规定：

1. 代理只读记录业务表和学习库基线；
2. 用户明确同意后，在软件界面主动点击；代理不得代点；
3. 代理只读核对业务表、marker、`BindingLog` 和聚合增量；
4. 优先使用独立测试学习库；
5. 若只能使用正式学习库，必须事前列明预计永久新增记录并取得用户明确同意；
6. “撤销业务行”不得描述成“学习库恢复干净”。

### P1-4. 自动测试必须给出可复制执行的矩阵

v2.2 应列出：

- 源码快照和编译命令；

## 6. v2.2 必须增加或重写的验收用例

### 6.1 用户确认的原生输入与计算语义

1. **正式定额原生落库**：粘贴宿主可识别的正式定额编号和数量后，不点击“计算”，只读查询已经出现新增 `定额输入` 行。
2. **计算只刷新派生结果**：在用例 1 基础上点击“计算”，核对单价、合价、费用、小计和项目汇总刷新；新增行身份不应以“计算”才出现。
3. **裸 SF 不算成功**：只原生粘贴 `SF + 数量`，即使宿主出现残缺行或之后点击计算，也不得认定为组件完整写入成功，不得 marker 成功确认，不得 `apply-accept`。

### 6.2 `SF` 完整行复制与事务原子性

4. **完整 SF 源行成功**：取得来源明确的完整 `SF` 业务记录，复制到当前项目设备购置费条目，核对名称、单位、数量、目标单元、目标条目、顺号、价格及设计列明的其他必要业务字段完整。
5. **SF 缺源整组阻断**：找不到完整 `SF` 源行时，同组普通行也不写；业务新增 0、marker 0、`BindingLog apply-accept` 0。
6. **普通 + SF 同事务**：两类目标都有完整源行时，在一个项目业务表 SQL 事务中完成全部业务行和 marker。
7. **事务任一行失败全部回滚**：分别在普通行、`SF` 行、marker 写入点注入失败，最终新增业务行 0、marker 0、undo 新记录 0、学习流水 0。
8. **跨两个目标条目的 marker 口径**：按文档最终选定的数量精确核对，并证明撤销只影响本批。

### 6.3 正式编号原生兜底

9. 写入前后数据库集合差确认准确；
10. 不点击计算也能确认新增行已落库；
11. 第一个正式目标成功、第二个失败时，已确认新增行按本批 ID 补偿；
12. 检测 0 行后模拟延迟落库，不能提前报告“未写入且无需补偿”；
13. 补偿失败时，在返回前产生带项目连接身份的可撤销记录；
14. 原生失败、部分成功、补偿中或结果不确定时，学习流水始终为 0；
15. 辅助代码永远不能进入原生兜底计划。

### 6.4 原有安全门禁

16. 项目 A 预览后切换项目 B，Apply 为 0 业务写入、0 marker、0 学习流水；切换单元、软件分区或办法同理。
17. 一个组件中任一行 `SfEntryBlocked`、缺完整源行、单位/公式/数量不安全时，整组不得被逐行过滤拆开。
18. 初次预览 `ClearSelection()` 后，用户选中组数为 0；局部候选更新不得扩大选择。
19. 父级节点、懒加载节点、属性表滞后节点均拒绝写入。
20. 公式分片先按当前专业过滤，再合并范围内 `SampleCount`；其他专业样本不进入当前排序。
21. 纯 `SH/ZLF/TLF` 可按完整身份推荐、接受并形成自身 `EngineeringTemplate` 范围；旧测试同步改写。
22. SQL 学习快照不可用时不生成推荐、Apply 保持禁用；SQL 正常但专业范围为空时才允许显示当前分区全部学习关系。
23. `BindingLog` 按目标数写多行、共享一个 `group_key`；普通目标 `entry_source=user-selected`，`SF` 目标 `entry_source=sf-sibling-redirect`。
24. 连续两批撤销按 LIFO；撤销业务行不伪称已撤销学习流水。

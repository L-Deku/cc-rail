## 4. 发现

### 4.1 🔴 重复写入无防护——实机已真实发生

**证据**：18:39:35 与 18:54:04 两批写入高度重复，**同一条目 `0309-01-03-06`**：

```
18:39:35  BC00-4 BC00-6 PY-415 BC00-8 QY-214 QY-215*9 PY-238 BC00-10
          PY-425 PY-430 PY-435 SY-153 SY-153 ZLF×2                 = 15 条
18:54:04  完全相同的 15 条 + PY-387                                  = 16 条
```

另有 18:39:01 单独写过一次 `PY-415`，故 `PY-415` 可能已写入三次。

**无法从日志判断是有意重写还是误触**（用户可能是为了追加 `PY-387` 而重选整组）。但无论哪种，当前实现都**没有任何机制阻止或提示重复**：

- 写入成功后预览行、勾选状态、滚动位置全部保留（这是 `ec2c0bb` 的有意设计，符合「预览一次、分批写多个条目」的工作流）；
- 但**界面零变化**——已写行没有任何视觉标记；
- `FillPreviewItem.WrittenQuotaSequence`（`TemplateFillFeature.cs:129`）**只写不读**，从未用作拦截条件；`TemplateFillPanel.cs` 中一次都没有引用。

⟹ 用户无从分辨哪些行已写过，再点一次「写入当前条目」即产生重复业务行。

**建议**（最小改动，保住分批写多条目的工作流）：写入成功后

1. **取消已写组的勾选**；
2. 状态列标注「已写入 `<条目编号>`」；
3. 需要再写时由用户重新勾选，形成一次明确的二次确认。

不建议直接禁止重写——同一定额写入不同条目是合法场景。

### 4.2 🟡 写入路径已无任何日志——本次引入的可观测性缺口

`TemplateFillFeature.cs` 全文仅剩 5 处 `Log()`，且全部位于无关路径的失败分支（`:505` 工作簿跳过、`:862` 章节名加载、`:1040` 隐藏列、`:1331`/`:1558` 学习回流失败）。

**`ApplyFillToSelectedEntry` 主写入路径成功与失败都不写日志。**

旧 L3 实现原有大量诊断（`Smart native key dispatch`、`Smart native single-enter submitted`、`Smart native insert result` 等），随原生链一并删除，未补回等价日志。

**后果**：本次审查无法从 `RecoExpandPanel.log` 判断实机写入是否成功，只能改从学习库 `BindingLog` 间接取证；而学习回流仅在**完整成功**时产生——**一旦写入失败或整组阻断，将不留任何痕迹**，现场排障将失去依据。

**建议**补回结构化日志（无需恢复原生链）：

- 进入写入：目标条目编号/序号、单元、组件组数、目标条数、各目标选定层（L1/L2）；
- 结果：成功条数、marker 条数、undo 批次、耗时；
- 失败：整组阻断原因、事务回滚点、异常信息。

### 4.3 ⚪ 跨单元写入尚未取得验证证据

本次改造的原始动机是「推荐定额一直无法写入选中的目标单元」。

实机三批写入均落在同一条目 `0309-01-03-06`，`BindingLog` 不含单元字段，**无法证明曾在宿主停留于单元 A 时向单元 B 写入**。

理论上该问题已因不再依赖任何 UI 焦点而消解，但**建议补一次显式验证**：宿主停在单元 A → 推荐定额选中若干组 → 在左侧树点击**单元 B** 下的条目 → 写入 → 确认落库到 B。

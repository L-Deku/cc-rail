# 推荐定额人工选条目——Codex 独立审核意见

> 文档性质：**独立评审意见，不是原设计文档，也不是可直接执行的实施清单。**
>
> 被审核文件：`2026-08-11-推荐定额人工选条目-design.md`
>
> 审核方式：只读核对设计正文、当前源码落点、项目 `AGENTS.md` 约束、现有测试与当前 Git 状态；未修改原设计、源码、数据库、运行目录或发布包。
>
> 审核基线：2026-08-16；原设计 SHA256：`E318C629EE45FDEA32D6E990D314AC473215E5354A31E1B44149D6E1B858A981`；当前 `HEAD=8b0a0f4`，`origin/main=1062a0d`，本地 `main` 领先 2 个文档提交。

## 1. 总体结论

原设计的核心方向是合理的：

1. 不再让推荐系统自动推理目标条目，改由用户在宿主左侧章节树选择写入条目；
2. 推荐预览范围由“推荐学习库”专业下拉控制，与当前树节点解耦；
3. 保留 SQL-only 学习关系、软件分区/办法隔离、单位与公式安全门禁；
4. 普通目标与 `SF` 可以保存各自真实写入条目，继续形成专业范围证据；
5. 不改数据库结构、不重跑迁移、不重建聚合的边界正确。

当前源码中也能找到大部分对应入口，因此方案**不是不可实施**。但原设计当前版本还不应直接执行。至少有 3 个阻断级矛盾、若干高风险实现缺口和多处已过期状态。若不先修订，最严重可能导致：

- 旧项目的预览被写入新切换的项目；
- 一个组件框只写入部分目标；
- SQL 学习库不可用时界面给出不真实的“全部学习库”提示；
- 混合组件写入一半成功、一半失败，且无法形成正确学习回流；
- 测试按错误的 `BindingLog` 行数或撤销语义得出误判。

建议先完成一次**纯设计修订**，解决本文 R1–R3，再进入编码。

## 2. 阻断级问题

### R1. 预览到执行缺少项目连接身份门禁

**原设计位置**：§4.9.2、§4.10.1、验收 16。

原设计只要求：

- 构造窗口时监听树节点；
- `OnApply()` 时重新读取当前条目；
- 借用当前宿主连接，不 `Close/Dispose/ChangeDatabase`。

这不足以防止用户在“预览完成后、点击写入前”切换项目。旧预览中的定额、单位、公式和目标元数据可能被写进新项目；只要新项目恰好存在同编号条目，“条目恰好一行”的查询也无法拦截。

这与 `AGENTS.md` 的明确要求冲突：预览、执行、撤销、重做必须同时保存并核对连接对象引用和不含密码的 `DataSource|Database` 身份，项目切换后拒绝旧计划。

**必须补充的设计**：

1. `BuildPreview_SmartFill` 成功时保存：
   - `ExpectedProjectConnection`；
   - `ExpectedProjectConnectionIdentity`；
   - 预览时 `CurrentUnitId/CurrentUnitCode`；
   - 当前软件分区和办法号。
2. `OnApply` 在任何条目打戳、树导航、数据库写入之前重新取得宿主连接并核对：
   - `Object.ReferenceEquals(current, expected)`；
   - `GetProjectConnectionIdentity(current) == expectedIdentity`；
   - 当前单元仍与预览时单元一致。
3. 任一不一致时拒绝写入，提示“项目或当前单元已切换，请重新预览”。
4. 模板写入生成的 `AgentUndoRecord` 必须同时写入 `ProjectConnection` 与 `ProjectConnectionIdentity`。当前 `ApplyFill` 创建 undo 记录时没有赋这两个字段，而现有撤销入口会拒绝身份为空的记录。
5. 增加真实回归：“项目 A 预览 → 切换项目 B → 点击写入”，必须 0 写入、0 marker、0 学习流水。

### R2. “组件组原子”与“SF 阻断但普通行照常写”互相冲突

**原设计位置**：§4.9.3、§4.10.3、§4.10.3 末段、验收 7/11。

原设计一方面规定：

- 组件组为原子单位；
- 组内任意行被选中且组首勾选时，整组写入；
- `CollectFullyWrittenNameDrivenGroups` 的整组闭合口径不变。

另一方面又规定：同级找不到设备购置费条目时，阻断 `SF` 行，但同组普通行照常写入。

这两种语义不能同时成立。后一种行为会形成残缺组件；现有 `CollectFullyWrittenNameDrivenGroups` 也不会把残缺组回流为 `accepted`，于是出现“业务表已经部分写入、学习库没有接受该组件”的分叉。

**需要用户重新确认的业务选择**：

- **建议方案 A：整组阻断。** 只要组内任意 `SF` 无法找到合法改道条目，整个组件组不写入、不插 marker、不产生 `apply-accept`。这与现有“组件组原子”规则一致，风险最低。
- 方案 B：允许 `SF` 特例拆组。如果保留“普通行照常写”，原设计必须删除“组件组始终原子/整组一次写完”的绝对表述，并完整定义：部分成功提示、marker 数量、撤销边界、失败补偿和“不产生 accepted”的学习语义。

在该选择重新定稿前，不应实施写入路径。

### R3. SQL 熔断时不可能退化为“全部学习库”

**原设计位置**：§4.7.1、验收 21。

当前推荐关系是 SQL-only。`LoadSmartLearningSnapshot` 在熔断或 SQL 异常时返回空快照；`BuildPreview_SmartFill` 检测到 `BySignature` 为空后结束预览。项目规则又禁止回退 `mapping-boxes.jsonl` 或本机 pending 数据。

因此“学习库熔断，正在显示全部学习库”在现架构下不成立：此时没有任何全库学习关系可供显示。

**必须拆成两个状态**：

1. **SQL 正常，但当前分区没有专业分类数据**：
   - 当前分区的学习关系已成功加载；
   - 不做专业范围过滤，等价于“全部学习库”；
   - 显示“当前版本尚无专业分类数据，正在显示当前分区全部学习关系”。
2. **SQL 熔断、连接失败或学习快照为空**：
   - 停止推荐；
   - 禁用写入；
   - 显示“学习库不可用，未生成推荐”；
   - 不得声称正在显示全部学习库。

建议把 `LoadSmartLearningScopes` 从单纯返回 `List<SmartLearningScope>` 改为带状态的结果，例如 `ScopeLoadResult`，至少能区分 `SuccessWithScopes`、`SuccessWithoutScopes`、`CircuitOpen`、`Error`。不能只凭“下拉里没有专业节点”推断原因。

## 3. 高风险实现缺口

### R4. 混合组件写入不是一个事务，可能留下半组

当前 `ApplyFill` 先在 SQL 事务内复制项目内/跨库整行并提交，随后才对 `libraryItems` 调宿主原生粘贴。原生粘贴无法加入前面的 SQL 事务。

因此即使采用 R2 的整组原子语义，以下情况仍会产生半组：

1. 普通定额直接复制成功并提交；
2. `SF` 导航或原生粘贴失败；
3. 普通行已经落库，`SF` 未落库；
4. 整组又不会产生 accepted。

原设计中的“建议先写普通行再写 SF 行”不能解决该问题。

**建议补充**：

- 写入前对整个组件组做完整预检：目标条目、目标单元、定额来源、数量、当前版本单位、SF 改道目标、原生输入编号可用性全部通过后才进入执行；
- 明确原生粘贴失败后的补偿策略：删除本批已确认新增的直接复制行和 marker，或把该组件组报告为可撤销的部分失败并立即提供补偿操作；
- 不得把“没有产生 accepted”等同于“没有产生业务写入”；
- 增加失败注入验收：普通行成功后模拟 SF 导航失败/粘贴 0 行，最终数据库不得残留半组（若选择允许拆组，则按方案 B 的专门语义验收）。

### R5. SF 导航会改变宿主当前条目，写完后没有恢复

SF 原生粘贴需要导航到同级设备购置费条目。成功后宿主树可能停在设备购置费节点，用户下一次点击“写入当前条目”时目标已经变化。

应在写入开始前保存：

- 原选中 `TreeNode`；
- 原条目编号/序号；
- 当前单元身份。

SF 写入完成或失败后，在 `finally` 中尽力恢复原条目，并再次核对当前单元。如果无法恢复，应明确提示并禁用旧预览继续写入。

### R6. SF 动态阻断状态没有可逆状态机

原设计既说“向 `Status` 追加 SF 冲突文案”，又新增 `SfEntryBlocked/SfEntryBlockReason`，但没有说明树节点变化后如何删除旧 SF 状态。

若直接改写 `Status`，容易出现：

- 从错误条目切到正确条目后仍残留 SF 阻断；
- 重复切换时同一文案不断追加；
- 为清除 SF 文案误删单位、公式、数量等固有状态。

**建议**：

- `Status` 只保存预览固有状态；
- SF 冲突只保存在 `SfEntryBlocked/SfEntryBlockReason`；
- 颜色、勾选和写入闸门综合判断两类状态；
- 树变化时重新计算并覆盖 SF 动态字段，不拼接旧值；
- 增加“普通条目 → 设备购置费条目 → 普通条目”往返测试。

### R7. 当前条目解析不应原样复用旧的四级回退顺序

原设计直接复用 `ResolveChapterNo`。但该方法优先读取宿主属性表/结果表，之后才读 `SelectedNode.Tag`。在 `AfterSelect` 回调时，宿主属性表可能尚未刷新，可能得到上一次选中的条目。

对“写入当前条目”这一新场景，建议使用更强的节点一致性口径：

1. 以 `tree.SelectedNode` 自身的条目序号/`Tag` 为第一证据；
2. 必要时用 `BeginInvoke` 等宿主刷新后再次读取；
3. 同时核对节点条目序号、数据库查询所得条目序号和条目编号；
4. 不要只用 `where 条目编号=@bh` 的行数证明“当前节点是可写叶条目”；
5. 增加父级节点、懒加载节点、快速连续切换节点测试。

### R8. 公式分片合并的时机和数据结构不完整

原设计要求用“目标单位 + 公式模板 + 有序操作数签名/单位”作为内容身份合并分片。但当前加载顺序是：

1. 读取 `QuantityFormulaRule`，立即加入 `FormulaByKey`；
2. 再读取 `QuantityFormulaOperand`，补到规则对象。

在步骤 1 时操作数尚未加载，无法生成原设计所述身份。此外，当前 `SmartFormulaRule.EntryCode` 是单个字符串，而原设计要求保存“命中过的条目集合”。

**建议明确为两阶段加载**：

1. 先按 `rule_hash` 加载所有规则和操作数；
2. 操作数加载完成后，在读取副本上执行 consolidation；
3. 内容身份必须定义规范化规则、操作数排序和空值规则；
4. 合并对象保存 `EntryCodes` 集合或按条目保存样本明细；
5. 专业范围过滤应先确定命中的条目分片，再计算该范围内的 `SampleCount`，不能把其他专业的样本数合并后带入当前专业排序；
6. 合并后的歧义判定比较内容身份，不能继续只比较原始 `RuleHash`；
7. 当前写入门禁要求公式 `entry_code` 非空，不建议让空 `entry_code` 作为全专业通配。

### R9. `entry_source` 没有从反馈对象传到 `BindingLog.extra` 的路径

原设计写 `flat["entry_source"] = "user-selected"`，但 `flat` 是 `LearningDbFeature` 写库时临时创建的局部字典，现有 `MappingFeedbackGroup/MappingFeedbackTarget` 没有该字段。

建议增加 target 级审计字段并贯通：

- 普通目标：`entry_source=user-selected`；
- SF 自动改道：`entry_source=sf-sibling-redirect`。

target 级比 group 级更准确，因为一个混合组件中的普通目标和 SF 目标来源不同。

### R10. SF “同级且最近”算法缺少严格定义

原设计没有定义：

- `0101-2` 与 `0101-10` 是按字符串还是数字比较；
- 更深后代是否算同级；
- 非标准编号如何处理。

建议规则固定为：

1. 按 `-` 分段；
2. 候选与当前条目段数必须相同；
3. 除最后一段外全部完全相同；
4. 最后一段按整数比较，选择“大于当前且差值最小”的候选；
5. 末段不能解析为数字时阻断并提示，不使用模糊 `StartsWith` 或字符串排序。

### R11. 初次预览可能因为 DataGridView 默认选择而意外进入写入集合

启用 `FullRowSelect` 后，`FillGrid()` 可能默认选择第一行。如果组首又默认勾选，用户尚未主动选行时，“选中行 ∩ 勾选行”就不是空集合。

建议：

- `FillGrid()` 或局部重建完成后显式 `grid.ClearSelection()`；
- 初次计数必须为 0 组/0 条；
- 预览刷新、候选切换和局部更新后都验证不会自动扩大用户选择；
- `btnCheckSelected` 只影响用户明确选中的组件组。

## 4. 验收口径需要修正

### A1. `BindingLog` 不是“每个组件一行”

当前写库逻辑是每个 target 插入一行 `BindingLog`，同一反馈组件共享 `group_key`。原验收“整组产生 1 条 apply-accept”会误判。

建议改为：

- 产生 1 个反馈组；
- 同一 `group_key`；
- `BindingLog` 行数等于组件目标数；
- 每行 `source=plugin:apply-accept`；
- 普通目标的 `entry_code` 为用户选择条目；
- SF 目标的 `entry_code` 为同级设备购置费条目；
- `SignatureBoxMap.weight` 对该次 accepted 只按既定口径增加一次，不因 target 行数重复加整组权重。

### A2. “分别撤销任一批”超出现有撤销能力

当前撤销栈是 LIFO，只能撤销最后一批。原验收 23 若表示任意选择历史批次，不可执行。

建议改为：

1. 同一条目连续写入批次 A、B；
2. 第一次撤销只删除 B 的定额和 marker；
3. 第二次撤销只删除 A 的定额和 marker；
4. 当前方案不承诺任意选中历史批次撤销。

### A3. 真实 UI 验收的人机边界需写清

验收 9、22、25、29 会真实追加 `BindingLog`、改变聚合权重，不能由代理直接执行 SQL 修改业务库，也不能由代理代替用户点击插件写入。

建议每个真实 UI 用例固定为：

1. 代理只读记录前置基线；
2. 用户在软件界面选择项目、条目并点击写入/绑定/扶正；
3. 代理只读核对业务表、学习流水、聚合增量和界面结果；
4. 使用一次性唯一工程量名称或独立测试学习库，避免重复运行污染正式权重；
5. 若必须写正式学习库，先说明具体用例、预期新增行和不可自动回滚影响，等待用户明确同意。

### A4. 自动测试、综合测试和实机测试应分层

原设计一方面要求全部 `Test-*.ps1` 全绿，另一方面承认 `Test-TemplateFillNameMatch.ps1` 在非交互 WinForms 环境可能卡住，两者矛盾。

建议拆为：

- **必跑自动测试**：编译、范围过滤、公式合并、连接身份、组件选择集合、SF 状态机、学习回流结构；
- **带超时综合测试**：明确超时、精确进程归属和“综合回归未完成”的报告口径；
- **真实 UI 验收**：树节点切换、原生输入、SF 跨条目导航、撤销、计算刷新；
- 不得用“源码中不存在某字符串”替代关键行为测试。

### A5. 2020 新绑定后的专业下拉刷新时机未定义

原验收只说新绑定后专业下拉随之出现，但没有定义自动刷新、重新预览、重新开窗还是点击刷新。

建议选定一种明确行为。若不准备增加实时刷新，验收应写成：“关闭并重新打开推荐定额窗口后，专业下拉出现对应专业”，避免实现隐含需求。

### A6. 精确 SQL 语句数量缺少测量方案

“单次开窗 SQL 语句由 9 条降到 5 条”没有计数器、日志或 trace 方法。应补测量方法和基线，否则删除精确数字，只验收“已停止读取 EntryQuota/SignatureEntryMap/条目 BindingLog 聚合”。

## 5. 文档状态和执行流程问题

### D1. E5 前置状态自相矛盾

原设计第 5、22、518、577 行对 E5 的状态描述不一致：一处要求开工前关闭 E5，一处说其中两项已确认、另外两项被本设计替代，而正式回写又放在实施后阶段 7。

建议增加“阶段 0：纯文档关门”：

- 明确乘系数、智能指令助手已验证；
- 纯辅助过滤因新决定作废；
- 规格误配由精确/模糊路径边界替代；
- 将 E5 标记为“已完成或被本批正式替代并关闭”；
- 阶段 0 完成后才能开始源码修改。

### D2. Git 状态描述已过期

原设计称 `main` 与 `origin/main` 同步，但审核时实际为：

- `HEAD/main=8b0a0f4`；
- `origin/main=1062a0d`；
- 本地领先 2 个文档提交。

这不妨碍只读评审，但构建、发布和推送前必须按当时的真实状态重新核验，不能继续引用 2026-08-11 的快照。

原阶段前置仍写“83 个未提交文件先落成提交”，又与风险章节的“已解决、剩 7 项非源码改动”冲突，应删除过期文字。现有无关工作树变化必须保留，不得还原、顺带提交或混入构建。

### D3. 从“修改源码”到“干净提交构建”缺少提交门禁

阶段 1–7 会修改源码和测试，阶段 8 又要求从已确认提交生成干净快照，但中间没有提交步骤。

建议流程改为：

1. 阶段 1–7 完成并通过离线测试；
2. 复核 `git diff`，确认只含本任务源码、测试和文档；
3. 用户/实施者确认差异；
4. 单独提交本任务文件；
5. 从该确认提交生成仅含 `tools/RecoExpandPanel` 构建输入的干净快照；
6. `BuildOnly` 隔离验证；
7. 确认宿主进程为 0；
8. 再执行受控部署；

### D4. 不建议把无关死代码清理混进本批

原设计阶段 1.6 顺带删除 SQL-only 切换遗留的本地壳代码。该清理与“人工选择目标条目”不是同一个行为目标，会扩大回归面。

建议本批只删除因条目自动推理下线而必然失去调用方的代码；其他历史死代码另立小任务处理。这样更符合精准修改原则，也便于出现问题时定位。

## 4. 发现

### 4.1 🟡 `prior.Targets` 会跨同名 desired 组重复累加

**位置**：`LearningDbFeature.cs:275-359`

`byGroupKey` 是**整个方法共享**的字典，而查询是**按每个 desired 组**执行的，过滤条件里含 `quantity_name=@quantity`：

```csharp
foreach (MappingFeedbackGroup desired in desiredGroups) {
    ... SELECT ... WHERE ... AND quantity_name=@quantity ...
    while (reader.Read()) {
        if (!byGroupKey.TryGetValue(groupKey, out prior)) { prior = new ...; byGroupKey[groupKey] = prior; }
        prior.Targets.Add(new MappingFeedbackTarget { ... });   // ← 已存在的 prior 也会继续 Add
    }
}
```

**触发条件**：两个 desired 组的 `QuantityName` 相同——同一个工程量名出现在多行 Excel，是常见情形。第二次查询返回同一批 `BindingLog` 行，`TryGetValue` 命中已有的 `prior`，于是**同一个目标被重复 Add 一次**。N 个同名 desired 组 ⟹ 目标重复 N 份。

**后果**（已逐条核对，不会炸但会脏）：

| 环节 | 影响 |
|---|---|
| `BuildAutomaticRebindTargetSet` | 用 `HashSet`，自动去重 ✅ |
| `IsPositiveAutomaticBindingAggregate`（`:361-372`） | 显式 `GroupBy(...).Select(First())` 去重 ✅ |
| `UpsertBindingGroupAggregates`（`:1114-1118`） | 同样去重，聚合权重不受影响 ✅ |
| **`BindingLog` 流水插入**（`:185-260`） | ❌ 按 `group.Targets.Count` 逐条 insert，**落下 N 倍重复的 rejection 行**。`event_hash` 含 `targetIndex`，不会撞 `UX_BindingLog_event_hash`，所以不报错、静默写入 |
| `Rebuild-Aggregates.ps1` 全量重算 | ✅ **已核实不受影响**（二审补验）：`:38-70` 把 `$g.Targets` 存成按 `kind:code` 索引的哈希表，同目标覆盖；`:257-260` 的 `accepted/corrected/rejected` 按 `group_key` **取一次**而非逐行累加 |

**真实危害**（二审收窄）：不会算错任何权重，危害集中在两点——

1. **流水取证失真**。`BindingLog` 是排障时的主要证据来源（08-22 那次审查在写入路径还没有日志时，正是靠数 `BindingLog` 行数推断"某批写了 15 条"）。目标被重复 N 份后，同样的数法会把 5 条数成 15 条，直接得出错误结论；
2. **表体积按 N 倍膨胀**，以及 `Get-LearningStats.ps1` 一类统计口径失真。

**建议**：在跑查询前去重，**但去重键不能只用 `quantity_name`**（二审更正）。SQL 谓词里的可变部分是五项，去重键必须与之一致：

```
NormalizeLearningDbMethod(desired.Method) + software_partition + NormalizeLearningMethodNo(desired.MethodNo)
+ project_id + quantity_name
```

两点补充：

- 键里的 method / method_no 要用**归一化后**的值（与 `cmd.Parameters` 传入的一致），否则同义写法会退化成重复查询；
- 去重必须放在方法开头那道 `desired == null / QuantityName / Workbook / Worksheet / ExcelRow+SourceCell` 门禁**之后**。

可再按完整目标身份做一次防御性去重，但**不得借此合并同码不同名称/单位的辅助码身份**（`AGENTS.md` 的辅助码身份规则）。

**测试缺口**：新增的 `Test-BindingLearningImmediate` 用例直接构造 `priorGroups` 调 `BuildAutomaticRebindFeedbackGroups`，**没有覆盖 `LoadPriorAutomaticBindingGroups` 的累加过程**，所以这条漏网。

### 4.2 🔵 待观察：写事务内 N 次带 `HOLDLOCK` 的只读查询，且索引不匹配

**位置**：`LearningDbFeature.cs:290-296`（每个 desired 组一次）、`:377-388`（每个 prior 组一次）

一次批量绑定的查询次数 = `desired 组数 + prior 组数`，全部在同一个写事务里，且都带 `WITH (HOLDLOCK)`。批量绑定几十上百行时就是几十上百次往返，范围锁持续到 commit。

**索引也对不上**。查询谓词是 `source IN (...) AND software_partition=@ AND method=@ AND method_no=@ AND project_id=@ AND quantity_name=@`，而 `tools/RecoLearning/schema.sql` 里最接近的是：

```sql
CREATE INDEX IX_BindingLog_partition_source
  ON dbo.BindingLog(software_partition, source, target_kind, id)
  INCLUDE(project_id, target_code, method_no);
```

只能 seek 前两列，`quantity_name` 不在索引里（也不在 INCLUDE 里），要逐行回表过滤。学习库长大后这是明显的热点。

**具体失败模式**（这是该风险真正兑现时的样子）：`LoadPriorAutomaticBindingGroups:292` 与 `IsPositiveAutomaticBindingAggregate:379` 都设了 `cmd.CommandTimeout = 5`。单次查询一旦超过 5 秒就抛 `SqlException` → 整个事务回滚 → **这一批绑定的学习全部没写进去**（业务绑定本身不受影响，学习失败不阻断绑定），批次转入 outbox 重试，重试同样超时后进死信。也就是说：学习库越大，越容易把整批学习丢掉。

**处理口径**（二审更正，原建议的两条已作废）：

1. ~~去掉 `HOLDLOCK`~~ —— **不做**。初审称"最坏只是少纠偏一次，不会写错数据"，这句话过头了：两个自动绑定批次并发时，若都读到同一个仍为正权重的旧子集，会各发一次 rejection，对一个已累积多次 accepted 的子集就是**多扣一次权重**（如 accepted=5、weight=50，正确应到 40，实际到 30）。旧组件读取、correction/rejection 流水与聚合更新是有意放在同一事务内的，改隔离级别必须先补并发验收标准。
2. ~~追加覆盖索引~~ —— **不能按原样加**。`schema.sql` 里 `software_partition NVARCHAR(10)` / `method_no NVARCHAR(100)` / `project_id NVARCHAR(200)` / `quantity_name NVARCHAR(1000)`，键宽 `20+200+400+2000 = 2620` 字节，**超过 SQL Server 非聚集索引键 1700（旧版 900）字节上限，`CREATE INDEX` 会直接失败**。若日后确有实测证据，应改用更窄的上下文键 + 包含列，或对 `quantity_name` 做持久化哈希列建索引，并以真实执行计划验证。
3. ✅ **可以现在做的只有一件**：按 4.1 的完整查询身份去重。它把 N 次往返降到去重后的次数，**不改变任何隔离语义**，是当前唯一零风险的缓解。

在拿到实测（执行计划、行数、等待统计、超时记录）之前，本条只作为**待观察风险**登记，不列为待办改动。

### 4.3 ❌ 已推翻：`CanAutoSelect` 与实际候选错位——当前调用链不可达

**位置**：`SmartFillFeature.cs:1299`

```csharp
AttachSmartCandidateOptions(active, candidates, !CanAutoSelectSmartMapEntry(scores));
```

`CanAutoSelectSmartMapEntry` 的结论来自 `scores[0]` 与 `scores[1]` 的分差（`:1169-1185`），但 `active` 克隆自 `candidates[0]`——即"**第一个产出了条目的**候选"。当 `scores[0]` 产不出条目时，`candidates[0]` 其实对应更低分的 entry，于是拿 scores[0] 的分差结论去自动勾选了另一个组件。

> **二审结论：该场景不可达，本条作废，不需要任何改动。** 触发它要求 `scores[0]` 产出 0 个条目，而 `RankSmartMapEntries:1147-1148` 已把这类 entry 挡在 `scores` 之外（验证链同 2.1）。初审提出本条时只看了 `AttachSmartCandidateOptions` 的调用点，没有回溯 `scores` 的构造，属于漏查前置过滤。
>
> `candidateItems.Count == 0` 的保底 `continue` 保留即可，但它防的是理论情形，不是现存缺陷。

### 4.4 ✅ 自动勾选路径的 `AlignNote` 文案变化——已确认为预期

老路径：`baseNote + "，" + BuildSmartCandidateLabel(scores[0])`。
新路径：`baseNote + "，候选：" + label`，多候选时再追加 `"已按最高分勾选，可下拉切换完整组件"`。

多出来的提示语是本次的目的；**自动勾选行的备注从"<label>"变成"候选：<label>"**是顺带的用户可见文案变化。

> **二审结论**：属预期改动，保留现状。自动勾选后仍需让用户看出"源行定额"列存在可切换的完整组件候选，"候选："前缀与该目标一致（Codex 8.5，本方 9.1 认可）。

### 8.2 对 4.1 的判定：问题真实，但后果被放大

`LearningDbFeature.cs:278-354` 的 `byGroupKey` 在整个方法内共享，而 SQL 查询按每个 desired 组执行。两个 desired 组若具有相同查询条件，第二次会读回同一批 `BindingLog` 行，并继续向已有 `prior.Targets` 追加，确实会形成重复目标。之后写流水时，`LearningDbFeature.cs:185-258` 按 `Targets.Count` 插入，`event_hash` 又包含 `targetIndex`，因此会留下额外的原始 `BindingLog` 行。

但前文关于“全量重算会放大 rejection 权重”的判断不成立：

- `IsPositiveAutomaticBindingAggregate`（`LearningDbFeature.cs:364-370`）会先按目标键去重；
- `UpsertBindingGroupAggregates`（`LearningDbFeature.cs:1114-1118`）同样会按目标键去重；
- `Rebuild-Aggregates.ps1:38-85` 按 `group_key` 聚成一次事件，并用 `Targets` 哈希表去重同一目标；
- `Rebuild-Aggregates.ps1:257-265` 每个事件组只读取一次 `accepted_count` / `corrected_count` / `rejected_count`。

因此当前已核实的影响是：**多余查询、原始流水重复和数据体积/审计噪声；不会改变当前增量聚合，也不会在现有全量重算脚本中把 rejection 权重乘以重复目标行数。**

若实施修复，查询去重不能只使用 `quantity_name`。正确去重身份至少应包含 SQL 谓词中的：

`software_partition + method + method_no + project_id + quantity_name`

否则同一批数据中若存在同名但分区、办法或项目不同的组，只按名称去重会漏读。可再按完整目标身份做一次防御性精确去重，但不得借此合并同码不同名称/单位的辅助码身份。

### 8.3 对 4.2 的判定：性能担忧合理，建议方案不可直接采用

当前确实存在“不同 desired 查询条件各查一次 `BindingLog`，每个 prior 组再查一次正权重聚合”的往返模式，学习库增长后可能成为热点。但目前没有实际执行计划、行数、等待统计或超时证据，不能把它直接定性为已发生的性能故障。

不建议直接删除 `HOLDLOCK`。旧组件读取、correction/rejection 流水和聚合更新被有意放在同一个 SQL 事务中；删除读锁提示会改变并发写入时的可见性和串行化语义。若要调整，必须先补并发场景的验收标准和测试，证明不会出现两个自动绑定批次互相读取旧状态并产生错误纠偏。

前文建议的索引也不能原样加入：`schema.sql` 中 `software_partition`、`method_no`、`project_id`、`quantity_name` 分别是 `NVARCHAR(10/100/200/1000)`，建议键最大宽度至少为 `20 + 200 + 400 + 2000 = 2620` 字节，超过 SQL Server 常见的 900/1700 字节索引键限制。尤其 `quantity_name NVARCHAR(1000)` 本身最大即 2000 字节。

若后续有真实性能证据，应另行评估：先按完整查询身份去掉重复查询，再按共同分区/办法/项目批量读取；索引则使用更窄的上下文键、包含列或持久化哈希方案，并用实际执行计划验证，不能直接采用前文所列宽键索引。

### 8.4 对 4.3 与前文 2.1 的判定：当前路径不可达

`RankSmartMapEntries` 在形成 `scores` 前调用 `IsSmartMapEntryUsableInCurrentProject`（`SmartFillFeature.cs:1141-1156`）。后者先过滤空编号目标，再调用 `IsSmartTargetSetRecommendable`；`SmartFillFeature.cs:1006-1010` 明确要求有效目标数量大于 0。

`AppendSmartItems`（`SmartFillFeature.cs:1624-1765`）遍历的是同一内存 entry 的目标，并为每个非空编号目标追加一个预览项。因此在当前调用链和当前 entry 未被外部并发修改的前提下，进入 `scores[0]` 的组件不可能因“目标全为空编号”而产生零个 `candidateItems`。

所以：

- 4.3 描述的“用原始 `scores[0]` 的分差去自动勾选另一个实际候选”当前不可达；
- 前文 2.1 所称“老路径会让工程量凭空消失、此次顺带修掉旧 bug”也没有成立的输入路径；
- `candidateItems.Count == 0` 的保底判断可以保留，但不能据此认定已经修复了一个可复现旧 bug，也无需为 4.3 再改自动勾选逻辑。

### 8.5 对 4.4 的判定：确认属于预期改动

## 1. 问题清单与设计决策

### P1 主路径"接受推荐"完全不回流(最高优先级)

**现状**:只有右键重绑走 `FeedbackNameMatches`(correction+1 / rejection+1)。
主路径 `TemplateFillPanel.OnApply` → `TemplateFillFeature.ApplyFill` 全程不产生学习事件。
违反 `AGENTS.md`:"用户点击'复制勾选内容'视为接受推荐,应提高对应样本权重"。

**后果**:推荐正确时权重不涨 → 28 个多候选签名的权重差永远拉不开 → 同一个名称反复人工确认。

**决策(v2 修订)**:在 `ApplyFill` 写入成功后回流 `accepted=1`,`source="apply-accept"`,
但必须满足以下约束:

1. **整组成功才学习**。只对**整个 `TargetRow` 组件组全部目标写入成功**的组记录 accepted。
   *(v1 的"`newId > 0` 即加入"是错的:三行组件只成功两行时,
   `PrepareLearningGroupsForOutbox` 会按这两行的目标集合算出一个新的 `box_id`,
   等于凭空学出一个残缺组件框。)*
2. 库内原生粘贴分支与跨库/项目内整行复制分支**统一采用"整组成功才学习"**,
   不得只对其中一条路径生效。原生粘贴以 `IsInsertGroupFullyConfirmed` 为准。
3. **每个完整 `TargetRow` 组件组记一次 accepted**;组件内每个目标仍按现有协议
   各写一行 `BindingLog`,共享同一 `group_key`。
4. **幂等**:`MappingFeedbackRecorded` 目前只能表达"已记录",无法区分
   "本机 mapping-boxes 已加票"与"SQL/Outbox 已持久化"。必须二选一:
   - 拆成两个状态位(本机已记 / 远端已持久化),或
   - 设计稳定幂等键(如 `预览会话Id + TargetRow + 目标集合哈希`)由写入端去重。

   否则 SQL 永久失败时,同一预览重复点写入会让本机 jsonl 反复加票。
5. 学习写入失败只记日志,**不得**改变 `ApplyFill` 的返回文案或抛出。
6. 列锚点模式(`!IsNameDriven`)不产生任何事件。
7. **必须与 P7 同批落地**。P1 给 Apply 增加了一次同步学习库访问,
   没有熔断时离线场景会给写入再叠约 6 秒卡顿。

**验收(v2 修订)**:不能写成"`BindingLog` 行数 = 名字驱动组数",应验证:

- `DISTINCT group_key` 数量 = 成功的名字驱动组件组数;
- 每个 `group_key` 下的流水行数 = 该组件的目标数;
- 残缺写入组(部分目标失败)不产生任何 accepted 事件。

### P2 自动采纳判定过严(v2:改为保守分阶段放开)

**现状**(`CanAutoSelectSmartMapEntry`,`defc8bb` 后仍是原样):

```csharp
if (!top.CurrentTargetsValid || !top.HasCurrentMethodMapping || !top.HasEntry || !top.HasCurrentContext) return false;
if (scores.Count == 1) return true;
SmartMapCandidateScore second = scores[1];
if (!second.CurrentTargetsValid) return true;
return topWeight - secondWeight >= 20;
```

问题依然成立:判定时只看 `second.CurrentTargetsValid`,不看它是否有当前办法/上下文证据;
绝对 20 分门槛对小样本过苛(2 次 vs 1 次差 10,不通过);
`top.HasCurrentMethodMapping` 是硬前提,锁死 83 组空办法关系。

**但 v1 的放开方式过猛**:`top.HasCurrentMethodMapping && !second.HasCurrentMethodMapping → 直接采纳`
会让 1 次 accepted(weight 10)无条件压过空办法的 10 次 accepted(weight 100)。

**决策(v2)**:分两阶段,本批只做阶段一。

**阶段一(本批)**——引入最低正反馈门槛:

```
定义 净证据分 = 10*accepted + 20*corrected - 10*rejected   (即去封顶后的 weight)
定义 最低正反馈门槛 = accepted >= 2 或 corrected >= 1

前提:top.CurrentTargetsValid && top.HasCurrentMethodMapping && top.HasEntry && top.HasCurrentContext

① 唯一候选                                                         → 采纳
② second 缺 CurrentTargetsValid                                    → 采纳
③ top 有当前办法证据 && second 没有 && top 达到最低正反馈门槛      → 采纳
④ top 有唯一当前上下文 && second 没有 && top 达到最低正反馈门槛    → 采纳
⑤ 净证据分之差 >= 20                                               → 采纳
⑥ top净分 >= 2 * second净分 && 差 >= 10                            → 采纳
否则 → 出候选下拉,人工确认
```

- ⑥ 的措辞用"净证据权重比较",不写"2 次对 1 次"——`corrected`(20)与 `rejected`(−10)
  分值不同,按次数描述会误导。
- 一旦加载 `AcceptedCount`/`CorrectedCount`/`RejectedCount` 到 `SmartMapEntry`,
  就**必须在判定中真正使用**(③④ 的门槛、⑥ 的净分),不允许新增字段后仍只比较 `Weight`。

**阶段二(暂缓,待 P1 积累真实 accepted 数据后再评估)**——空办法关系的自动采纳。

v1 提出"唯一空办法候选 + 当前办法唯一条目证据即可自动采纳",**主体暂缓**,理由成立:
`SignatureEntryMap` 主键是 `(signature, target_code, method, entry_code)`,
是**目标级**证据,不能证明整个组件框正确。

**但保留一个收窄的特例(本批可实施)**:

> 当该组件框**只有一个 `quota` 目标**时,目标级证据 ≡ 组件框级证据。
> 此时"唯一空办法候选 + 当前办法唯一条目证据 + 目标在当前版本定额库有效单位"
> 三条同时满足,可自动采纳。

多目标框一律走阶段二,不在本批放开。P1 上线后用户确认写入会自然产生当前办法映射,
先靠正反馈形成办法级证据,再评估是否放宽多目标框。

### P3 权重封顶 100 让否定反馈失效

**现状**:写入端 `UpsertBindingGroupAggregates`、本机 jsonl 端 `ExcelLinkFeature`、
重算端 `Rebuild-Aggregates.ps1:211` 三处都是 `clamp(..., 0, 100)`。
一个被接受 20 次的框再被否定 3 次仍是 `170 → 100`,扶正对排序零效果。

**决策**:去掉上限,只保留下限 0:`weight = MAX(0, 10*acc + 20*cor - 10*rej)`,三处同步。
读取端加载三个计数进 `SmartMapEntry` 供 P2 使用。

**v2 增补的必改项**:

1. `MergePendingLocalMappingsIntoSmartSnapshot` 里
   `localEntry.Weight = Math.Max(sample.Max(...), 1000)` 的 `1000` 是排序魔数,
   必须改成 `SmartMapEntry.PendingLocal` 布尔并进入排序键。
2. **但不能只是删掉 `Math.Max(..., 1000)`**。`localEntry` 在 `existing != null` 时
   就是快照里那个 SQL 条目对象,直接赋值会用**较小的本机 weight 覆盖共享 SQL weight**
   (现在被 1000 兜住看不出来)。必须写成:
   ```csharp
   localEntry.Weight = Math.Max(existingSqlWeight, localWeight);
   localEntry.PendingLocal = true;
   ```
3. `SmartMapCandidateScore` **不要**新增重复的 `PendingLocal` 字段;
   排序直接读 `score.Entry.PendingLocal`。

**验收(v3 修订)**:不要用"`weight > 100` 的行数必须 > 0"作门禁。改为**逐行核算**:

```sql
SELECT COUNT(*) FROM dbo.SignatureBoxMap
WHERE weight <> (CASE WHEN 10*accepted_count+20*corrected_count-10*rejected_count < 0
                      THEN 0 ELSE 10*accepted_count+20*corrected_count-10*rejected_count END)
-- 期望 0；必须在 P8 全量重算之后核对，否则历史行仍是旧封顶值
```

当前(去上限前)该库 `MAX(weight)=100`、`weight>100` 为 0、按**封顶**公式核算完全一致,
说明历史聚合已按现公式收敛 —— 因此 P3 落地后**必须再次全量重算**,历史权重才会按新公式展开。

### P4 模糊打分对已命中行也全量执行(7/23 改造引入的性能回归)

**现状**:改造前精确命中后 `continue`;改成 `matched` 标志后,
`BuildMatchTextFeatures` + `NameFeatures` 全量循环 + `scored.Sort` 留在了
`if (!matched)` **之外**,每一行都要跟全部名称签名打一遍分。

**决策**:把这三段移到**精确、同名、全库精确、全库同名四档都未命中之后**才执行。

**v2 措辞更正**:v1 写"外层还套着两遍扫描,代价是 `2 × 行数 × 全部名称签名`"——
不准确。第二遍只在第一遍产生了前缀投票时才跑(`if (preferredPrefixes.Count == 0) break;`),
"两遍全量扫描"是**存在签名级证据时的常见/最坏情况,不是所有场景都必然执行**。

这是本批风险最低、收益最明确的一项,应独立优先实施。

### P5 专业范围内的模糊候选压过全库精确命中

**现状**:全库兜底条件是 `!matched && fuzzyCandidates.Count == 0 && scoped`。
只要选定专业里凑出哪怕 1 个模糊候选,就不再看全库的精确签名命中。
模糊候选只能人工双击选择,精确命中却可能自动采纳——与目标相反。

**决策**:改为固定优先级链,前一档命中即停:

```
① 范围内 精确签名
② 范围内 名称兼容
③ 全库   精确签名
④ 全库   名称兼容
⑤ 范围内 模糊候选
⑥ 全库   模糊候选
```

理由:现有专业范围本来就是"专业优先、全库兜底"的**软范围**,不是硬隔离;
强精确证据不应被弱模糊候选抢先。

③④⑥ 仅在 `scoped` 时与 ①②⑤ 有区别;`All` 范围时自然短路。
③④ 命中必须保留醒目的"全库兜底"提示。
**新增要求**:增加跨专业同名冲突的行为测试,验证该场景下是否允许自动勾选。

### P6a 学习库查询优化(本批实施)

**v2 性能数字全部更正。** v1 写"`EntryQuota` 全量 116,418 行"是**错的**——
现有查询本来就有 `WHERE method = @method AND target_kind = 'quota'`。只读实测:

| method 分区 | 按办法行数 | 半连接后 |
|---|---|---|
| `101-estimate` | 25,456 | 1,867 |
| `2020` | 68,427 | 5,159 |
| `2024` | 22,535 | 3,072 |

仍值得优化(降约 86–92%),但**不得写成"116,418 降到数百行"**。

本批采纳四项:

1. `EntryQuota` 半连接下推(语义无损:候选定额只可能来自组件框目标):
   ```sql
   SELECT quota_code, entry_code, entry_name, project_count FROM dbo.EntryQuota q
   WHERE q.method=@method AND q.target_kind='quota'
     AND EXISTS (SELECT 1 FROM dbo.QuotaBoxTarget t
                 WHERE t.target_code = q.quota_code AND t.target_kind = 'quota')
   ```
   `EXISTS` 内**必须**带 `t.target_kind='quota'`(否则材料码会把无关定额号带进来)。
2. 合并 `LoadSmartLearningSnapshot` 中重复的 `ChapterEntry` 查询
   (11,996 行,当前查 2 遍)。
3. `EngineeringTemplate` 查询只取 `box_id, entry_code`,去掉
   `LEFT JOIN dbo.ChapterEntry` 与 `ISNULL(c.entry_name,'')`;条目名由独立的
   `ChapterEntry` 结果统一填充。
4. 保持现有 `method` 过滤不变。

### P6b 快照缓存(暂缓,需重新设计)

v1 提出按 `method + 变更令牌` 缓存快照。**本批暂缓**,v1 方案有五个洞:

1. 令牌(`MAX(BindingLog.id)` + `COUNT(SignatureBoxMap)` + `MAX(last_used_at)`)
   **没有覆盖** `QuotaBoxTarget`、`QuantityAlias`、`EngineeringTemplate`、`ChapterEntry`、
   `QuantityFormulaRule/Operand`、`EntryQuota`、`SignatureEntryMap` 的变化。
2. `Rebuild-Aggregates.ps1` 可能在 `SignatureBoxMap` 行数与 `MAX(last_used_at)` 都不变的情况下
   **改变权重**(例如只改公式或 clamp 规则时)。
3. `Import-JsonlLibraries.ps1` 会直接重载 `ChapterEntry`、`EntryQuota`,
   却**不一定新增 `BindingLog`**,令牌完全感知不到。
4. `MemberwiseClone` 浅拷贝不安全:`FilterSmartHitsByScope` 会修改嵌套的 `HashSet`
   (见 P11),浅拷贝仍会污染缓存。
5. `LoadSmartLearningScopes` 的显示名**优先取当前项目条目名**,
   不能只按 `method` 缓存最终结果,否则不同项目会串名。

**如果 P6a 落地后实测仍慢,再按以下方向单独设计**:

- 学习库增加统一的 `LearningRevision`(单行版本表);
- 插件增量双写、`Rebuild-Aggregates`、`Import-JsonlLibraries` 三条写入路径
  **均在各自事务内递增 revision**;
- 缓存键 = `method + revision + outbox 文件状态(mtime+length)`;

### P7 离线时的连接阻塞(v2:补全覆盖面)

`Connect Timeout=3` + `TryWriteLearningDbBatch` 的 `attempt < 2` 重试,
服务器不可达时一次绑定阻塞约 6.1 秒;预览路径再叠一次。P1 落地后 Apply 也会新增一处。

**决策**:进程内共享熔断。**必须覆盖全部五个入口**:

1. `TryWriteLearningDbBatch`
2. `LoadSmartLearningSnapshot`
3. `LoadSmartLearningScopes`
4. 推荐定额窗口初始化时的专业范围加载
5. Outbox replay

设计要求:

1. **只对明确的网络/连接/超时类错误**开启熔断(−2、53、121、258、10053、10054、10060、
   10061、10065、11001,以及明确的连接类非 `SqlException`)。
2. `1205`(死锁)、`2601`/`2627`(唯一键)**不开启熔断**。
3. **不要把所有非 `SqlException` 都当连接故障**。
4. 第一次明确网络失败后**直接返回 `RetryableFailure`**,不再立即做第二次三秒连接;
   死锁等仍可继续短重试。(阻塞从约 6.1 秒降到约 3 秒。)
5. 熔断状态用锁或 `Interlocked.Read`/`Exchange`(存 ticks 的 `long`),
   **不得无保护读写静态 `DateTime`**。
6. **只有完整快照全部加载成功后才清除熔断**,不能在 `conn.Open()` 成功时就清。
7. 熔断期间 Outbox 仍正常落盘,**不得改变** dead-letter、队头保留和幂等语义。

熔断窗口:60 秒。

### P8 全量重算收敛(v3:归一化已收敛,但 P3 后仍须再算一次)

`095948a` 已完成两端归一化源码统一,**源码侧无待办**。

**v3 状态更新**:只读复测显示历史聚合与当前(封顶)公式完全一致、`weight>100` 为 0,
**归一化历史聚合目前看起来已经重算收敛**(期间很可能执行过一次全量重算,
但具体时间与来源未确认,不写成确定事实)。

**因此 P8 的剩余理由变为**:P3 去除权重上限后,历史权重仍停留在旧的封顶值,
必须在维护窗口**再次执行一次全量重算**,使历史权重按新公式(无上限)展开。
否则新写入的关系分数可以超过 100、历史关系永远停在 100,两者排序不可比,
P2 的净证据分比较会失真。

**v2 必须注明的运维事实**:

1. **`-DryRun` 不是无影响的普通只读检查**。它同样获取 `BindingLog` 的
   `TABLOCKX` 独占锁,并在事务内照常执行 `TRUNCATE`/`BulkCopy`,最后才回滚。
   对并发绑定是完全阻塞的。
2. **`-DryRun` 与正式执行都必须在维护窗口进行**。
3. 两次之间如果仍有新流水,两次行数**不保证相同**。
4. 应记录并比较 `MAX(BindingLog.id)` 水位;**只有写入被冻结且水位一致时**,
   才比较两次聚合行数。
5. 正式执行数据库重算前**仍需用户明确确认**。

### P11(新增)`FilterSmartHitsByScope` 就地修改快照

**这是现存 bug,不是缓存引入的风险。**

```csharp
HashSet<string> codes = null;
bool hasCodes = snapshot.ScopeEntriesByBox.TryGetValue(entry.BoxId ?? "", out codes) && codes.Count > 0;
if (entry.LocalContextKeys != null) {
    foreach (string key in entry.LocalContextKeys) {
        ...
        if (codes == null) codes = new HashSet<string>(StringComparer.OrdinalIgnoreCase);
        codes.Add(code);          // ← TryGetValue 成功时，codes 就是快照集合的引用
        hasCodes = true;
    }
}
```

`TryGetValue` 成功时 `codes` 指向 `snapshot.ScopeEntriesByBox[boxId]`,
`codes.Add(code)` **直接改了快照**。今天就会发生:

- 两遍扫描中,第二遍看到的是被第一遍污染过的范围集合;
- 同一窗口反复预览会持续累加;
- 一个本应归"未归类"的组件框,在第一次遇到带本机上下文的行之后就变成已归类,
  后续 `Unclassified` 范围再也筛不到它。

已核对 `defc8bb` 后代码未变。

**决策**:先复制再合并,不得触碰快照集合:

```csharp
HashSet<string> scopeCodes;
HashSet<string> merged = snapshot != null && snapshot.ScopeEntriesByBox.TryGetValue(entry.BoxId ?? "", out scopeCodes)
    ? new HashSet<string>(scopeCodes, StringComparer.OrdinalIgnoreCase)
    : new HashSet<string>(StringComparer.OrdinalIgnoreCase);
// 之后只往 merged 里加本机上下文条目
```

优先级:与 P5 同批(同属范围过滤链路),**先于 P6b 缓存**。

## 3. 风险与回滚

| 改动 | 风险 | 回滚 |
|---|---|---|
| P1 接受回流 | 一次写入 N 组 = N 个 accepted 事件,权重上涨快 | 事件只进 `BindingLog`,可按 `source='plugin:apply-accept'` 剔除后重算 |

| P3 去封顶 | 覆盖共享 SQL weight;魔数 1000 失效 | `Math.Max` 保护 + `PendingLocal` 布尔;重算脚本同步 |
| P6a 半连接 | `EXISTS` 漏 `target_kind` 会带进材料码 | 条件已写死;逐 method 比对行数 |
| P7 熔断 | 抖动后 60 秒内不重试 | Outbox 照常落盘;完整加载成功即清 |
| P11 复制集合 | 每行多一次 `HashSet` 复制 | 集合规模为单个 box 的条目数,可忽略 |
| P8 全量重算 | 聚合表 TRUNCATE 重填;`-DryRun` 同样持独占锁 | 单事务;`BindingLog` 不动;须在维护窗口 + 用户确认 |

## 4. 验收标准

1. **P1**:写入后 `BindingLog` 出现 `source='plugin:apply-accept'`;
   `DISTINCT group_key` 数 = 成功的名字驱动组件组数;
   每个 `group_key` 的流水行数 = 该组件目标数;残缺组不产生 accepted。
2. **P1+P7**:断网时点写入,不出现新增的约 6 秒卡顿,且事件全部进 outbox。
3. **P2 阶段一**:对同一多候选签名累计 2 次 accepted 后,该行由"请确认组件"变为自动勾选;
   1 次 accepted 时**不得**压过空办法高权重候选。
4. **P2 单目标特例**:单 quota 目标 + 唯一空办法候选 + 当前办法唯一条目证据 → 自动勾选;
   多目标框同条件下**仍需确认**。
5. **P3**:在 P8 全量重算**之后**,逐行核算
   `weight = Max(0, 10*a+20*c-10*r)` 不一致行数为 0。
   **不以 `weight>100` 的行数作为门禁**(该指标随数据变动,且 v3 已撤回相关推断)。
6. **P4+P6a**:精确命中的行不再执行模糊打分;
   `EntryQuota` 单次加载行数按 method 从 68,427/25,456/22,535 降到 5,159/1,867/3,072 量级。
7. **P5**:选定专业后,库内存在精确签名命中的行不再被降级成模糊候选;

## 5. 测试策略(v2 新增)

**不再以源码字符串搜索为主要验收手段。** v1 的验收步骤大量是
"断言源码中含某字符串",只能证明代码里有这几个字,证明不了行为。
本批必须增加反射调用或纯函数级的行为测试,至少覆盖:

1. 三行组件只成功两行时**不产生** accepted。
2. 完整组件成功时只产生**一个** accepted `group_key`,其下流水行数 = 目标数。
3. 本机已学习但 SQL 永久失败时,同一预览**不会**重复给本机加票。
4. 当前办法的弱证据(1 次 accepted)**不能**无条件压过空办法高权重候选。
5. 两次 accepted / 一次 corrected / 同权 / 被 rejected 四种组合的判定结果。
6. 唯一空办法候选:**多目标框仍需确认**,单目标框 + 当前办法唯一条目证据可自动采纳。
7. 范围内弱模糊与全库精确同时存在时,**全库精确先执行**。

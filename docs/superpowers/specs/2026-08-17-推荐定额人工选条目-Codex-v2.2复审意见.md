## 1. 总体结论

v2.2 已经正确完成上一轮最重要的架构纠正：

- 辅助代码禁止退回“编号 + 数量”的原生输入；
- `SF` 改为完整业务行复制，并在无完整源行时整组阻断；
- 区分“项目业务表 SQL 复制写入”与“学习库 SQL 回流”；
- 普通行、`SF` 行和 marker 同事务的方向正确；
- 真实 UI 验收已经移到新 DLL 部署之后；
- 发布范围已经收敛到 `RecoExpandPanel.dll`。

但 v2.2 **仍不适合直接进入源码实施**。当前可以执行的仍只有“阶段 0：纯文档修订”。主要原因不是总体方向错误，而是以下实现契约还没有闭合：

1. 完整源行的查找、身份复核、候选回退和后续可复用链路不完整；
2. 正式编号原生兜底 B 路径仍只是需求清单，没有可编码状态机；
3. 事务究竟覆盖一个组件还是一次 Apply 未定，且失败返回值仍可能被当作可提交的“跳过”；
4. `SmartPreviewContext` 没有覆盖全部预览输入，undo/redo 又被要求核对了不应核对的导航状态；
5. 可写叶条目的实际判定条件仍未选定；
6. 正文、阶段任务、测试表和关闭表仍保留多处已作废的 v2.1 语义。

建议先修订为 v2.3，通过一次只读一致性复审后再编码。

## 2. P0：源码实施前必须闭合

### P0-1. “完整源行”查找链仍会漏目标、错候选或无法跨项目复用

#### 已核实的现状

1. v2.2 §4.10.0.1（设计第 700 行）要求调用 `GetLearningTargetIdentityKey(...)`，但当前真实 helper 名是 `BuildLearningTargetIdentityKey(...)`（`ExcelLinkFeature.cs:2778`）。照文档实施会先遇到不存在的方法名。
2. 当前跨库来源 SQL 在 `SmartFillFeature.cs:776-778` 固定 `target_kind='quota'`。因此即使正式材料具有可复制的完整历史行，也不会进入该来源索引；v2.2 声称 A/B 同时覆盖“正式材料”，但来源加载链没有覆盖。
3. 当前 `IsSmartMapEntryUsableInCurrentProject`（`SmartFillFeature.cs:977-993`）会拒绝非 `quota` 目标，并要求每个目标都能在**当前项目**的定额集合中找到名称、单位匹配的行。只有跨库完整源行、当前项目尚无同目标的纯辅助组件，可能在到达新写入路径之前就被过滤掉。
4. v2.2 第 686 行写“当前项目已有该目标，按 `target_code` 命中即可”，与当前实现不符。`BuildSmartCurrentQuotaKey`（`SmartFillFeature.cs:961-965`）对上下文敏感代码已经使用“类型 + 编号 + 名称 + 单位”身份；模板侧当前项目来源也按编号、名称、单位分组。这里不能倒退成裸编号。
5. v2.2 要求“同身份多条取 id 最大者”。但最新候选对应的项目库可能已删除、不可访问、源行已删除或字段不完整。只保留一个“最新”候选会把本来存在的较早有效来源误判成无来源。
6. `LoadCrossDbQuotaRow`（`SmartFillFeature.cs:1410-1449`）当前只按数据库名和行号读取，返回后没有再次核对实际行的编号、名称、单位和必要业务字段；数据库同名、来源端点变化或行号复用时可能静默取错。
7. `MappingFeedbackTarget`（`ExcelLinkFeature.cs:2323-2332`）没有源数据库身份、源行序号或本次新插入行序号。新产生的 `plugin:apply-accept` 即使推荐关系学习成功，也没有明确办法成为下一项目可复制的完整源行。

#### v2.3 应写成的可执行契约

1. 用统一 helper 名 `BuildLearningTargetIdentityKey(kind, code, name, unit)`；不要在文档中创造第二个同义函数。
2. 来源查询覆盖设计允许复制的全部目标类型，至少明确 `quota` 与正式 `material` 如何识别；辅助代码仍按完整身份隔离。
3. 把单值字典改为按身份保存**有序候选列表**，例如：

   ```text
   CrossSourceByTargetIdentity
     -> List<SmartQuotaSourceCandidate>
   ```

   候选按事件时间/流水 id 降序，但逐个尝试；最新无效时继续较早候选。
4. 候选至少保存不含密码的来源端点身份、数据库名、源行序号、流水 id。仅有 `SourceDb` 不足以区分两个端点上的同名数据库。
5. 源行读出后必须再次核对：目标类型、完整编号、规范化名称、规范化单位和来源身份；任何不一致都拒绝该候选并尝试下一候选。
6. 在文档中列出“完整源行必要字段”的**确定清单或逻辑字段组**。验收 41 目前写“设计列明的其他必要业务字段”，但设计没有实际列明，属于循环验收。至少要覆盖编号、名称、单位、价格字段、目标单元、条目序号、顺号、工程数量，以及宿主计算和显示依赖的业务字段。
7. 新写入成功后，把可复用且不含秘密的来源信息写入 target 级学习流水：建议记录当前项目非秘密身份和本次新插入的 `定额序号`。后续来源加载必须说明是否读取 `plugin:apply-accept`，否则新接受关系只能学习推荐，不能学习完整行来源。
8. 当前项目来源与跨库来源使用同一身份规则，不允许一边按完整身份、一边按裸编号。

#### 必加验收

- 正式材料有完整历史行时能进入 A 路径；
- 最新候选已删除、较早候选有效时能自动回退；
- 来源端点或数据库身份不一致时拒绝候选；
- 编号相同但名称/单位不同的 `SF`、`SH` 各自取得自己的源行；
- 源行缺任一必要字段时不进入 A 路径；
- 项目 A 接受并写入的新辅助目标，在项目 B 能通过记录的来源身份取得正确完整行。

### P0-2. B 路径仍是“应当做什么”，不是可编码的状态机

v2.2 第 663-671 行列出了数据库差异确认、延迟落库、补偿、撤销和禁止学习等要求，方向正确，但仍缺以下实现参数与状态转换：

- 轮询间隔、总超时、连续几次结果稳定才算确认；
- 预期 2 行而只确认 1 行、先读到 0 后延迟出现 1 行、超时后又落库等分别进入什么状态；
- 结构化返回类型及每个状态是否允许继续 SQL、写 marker、压 undo、学习；
- 补偿按哪些已确认 ID 执行、是否使用项目业务表事务、补偿后如何再次确认；
- 补偿失败时 undo 在何时压栈，避免异常先返回而记录尚未保存；
- 纯原生组件没有可供 SQL marker 克隆的源行时，marker 从哪一行构造；
- 原生业务行成功但 marker 失败时如何补偿；
- 失败注入 seam 如何启用，并证明不会进入生产行为。

当前真实 `ExecuteAgentInsertGroup`（`AgentExecutor.cs:2356-2407`）返回一段字符串，固定等待 1200ms；检测到 0 行时明确提示“该部分插入暂不支持撤销”。它不能直接承载 v2.2 的 B 路径承诺。

建议二选一，并在 v2.3 明确拍板：

#### 方案 B1（推荐，缩小首批范围）

本批只实施完整源行 A 路径。任何目标缺完整源行都整组阻断；正式定额/正式材料的原生兜底另立后续设计和验收。这样不违反“只有正式编号才**允许**原生兜底”的能力边界，只是不在首批启用它。

#### 方案 B2（保留本批 B 路径）

必须补出可编码状态机，例如 `NotStarted / Submitted / Confirming / Confirmed / PartiallyConfirmed / Compensating / Compensated / CompensationFailed / Indeterminate`，并为每个状态写死：是否启动后续 SQL、是否写 marker、是否学习、是否压 undo、界面最终文案。返回值应是结构化对象，不能继续用字符串推断成功。

无论选哪一种，用“裸 `SF` 原生输入不会成功”的验收都应放在一次性测试项目中，由用户主动操作，代理只做前后只读核对；不能污染正式项目后不说明清理边界。

### P0-3. 事务单位和失败条件没有唯一语义

v2.2 第 710 行写“一次组件写入只有一个事务”，第 713 行又按“本批目标条目”写 marker；现有 `ApplyFill` 则对一次 Apply 中所有 selected 行使用一个事务和一个 undo 批次。三者不是同一边界。

这会直接影响：

- 同一次 Apply 选中 3 个组件时，是 1 个事务还是 3 个事务；
- 第 3 个组件失败时，前 2 个是否保留；
- 同一目标条目中 2 个组件写几个 marker；
- undo 一次撤销整个 Apply 还是一个组件；
- 学习回流在每组件提交后进行，还是整个 Apply 提交后进行。

**建议收敛为最接近现有实现的一种语义**：一次 Apply 的全部 A 路径组件使用一个项目业务事务、每个实际目标条目一个 marker、提交后形成一个 undo 批次；任一目标或 marker 失败则整次 Apply 回滚；事务提交成功后才逐组件学习。若 Claude 认为必须按组件分别提交，也可以，但必须同步重写 marker、undo、部分成功文案和全部验收。

另外，v2.3 必须把以下情况写成**抛错并回滚**，不能继续“计入 skipped 后提交”：

- 完整源行返回 `null`；
- marker 插入 ID `<= 0`；
- 业务行插入 ID `<= 0`；
- 预期行数与实际插入数不一致；
- 顺号分配或目标条目复核失败。

当前 `TemplateFillFeature.cs:1158-1170` 和 `1183-1191` 对 ID `<=0` 只是增加 `skipped`，随后仍在 `1194` 提交。设计必须明确修改这一行为，否则“任一行失败整体回滚”不会自然成立。

跨库源行目前在目标事务已经开始后才加载（`TemplateFillFeature.cs:1105-1120`）。v2.3 应要求：先在事务外完成整组 preflight、远端源行加载、身份/完整性复核并冻结内存副本；确认当前项目身份仍一致后，再开启短项目业务事务。不要让目标数据库事务跨越远端连接和网络等待。

### P0-4. `SmartPreviewContext` 没有覆盖全部预览输入，undo/redo 又过度绑定导航状态

v2.2 第 565 行只明确保存项目连接、项目身份、单元、软件分区和办法，遗漏了会改变预览结果或执行集合的输入：

- 推荐学习库范围 `scope kind/code`；
- Excel 工作簿**完整路径**；
- 工作表；
- 数量列/目标列；
- 当前预览版本或不可变预览对象本身。

当前 `OnSmartLearningScopeSelected`（`TemplateFillPanel.cs:587-595`）只修改下拉字段，不清空旧预览。用户可以先按“全部”预览，再把下拉切到 `0305`，然后对旧的“全部”结果点击 Apply。

v2.3 应二选一：

1. 任一预览输入变化即清空预览、清空 `SmartPreviewContext`、禁用 Apply；或
2. Apply 比较全部快照字段，不一致时拒绝旧预览。

推荐使用第 1 种作为 UI 主行为，第 2 种作为最终安全门禁。`BuildPreview_SmartFill` 也应返回结构化的预览结果和加载状态，不应继续依赖 `List + warning string` 组合推断。

同时修正 v2.2 第 717 行：

- **Preview/Apply** 必须核对连接对象、`DataSource|Database`、单元、分区、办法、范围和 Excel 来源；
- **undo/redo** 只应硬核对记录中的连接对象和 `DataSource|Database`。撤销使用已记录的行 ID，用户写入后正常切换单元或章节树不应导致无法撤销。除非源码另有必须依赖当前单元的证据，不要把预览时单元、分区和办法设成 undo/redo 门禁。

### P0-5. “可写叶条目”仍没有实际谓词

v2.2 第 551 行仍写“如节点自身的 Tag 层级/类型标记，或定额输入可挂载性”，这是候选方向，不是已经选定的判定规则。第 555 行随后又把 `章节表 where 条目编号=@bh` 恰好一行作为前置，并继续暗示点在“章”上会得到 0 或多行；唯一编号只能证明数据库中唯一，不能证明宿主当前节点是可输入定额的叶节点。

阶段 0 必须先用只读方式核实宿主真实树节点，选定一个可实现谓词并写入文档，例如：

- 哪个 `Tag` 字段或节点类型明确区分章、节、可写费用条目；
- 是否还要结合宿主当前定额表的绑定状态；
- 懒加载未展开节点如何判断；
- 数据库三方核对只承担“身份一致”，不承担“叶节点可写”证明。

在谓词未定之前，不应把阶段 3/4 视为可编码任务。

### P0-6. 学习来源回流与“完整成功后学习”还需明确提交顺序

v2.2 已正确规定学习库失败不回滚业务写入。但完整闭环还需写清：

1. 项目业务事务提交并形成 undo；
2. 由实际插入结果重建“完整成功组件”，不能只沿用预览计划；
3. 为每个 target 填入实际写入条目、实际新行 ID、来源身份和 `entry_source`；
4. 再调用学习库 SQL 回流；
5. 学习库失败仅报告“业务成功、学习失败”，不得把业务行补偿删除；
6. A 路径任何一个目标/marker 未确认完整时，整个组件不得产生 `apply-accept`。

特别需要补的是“新插入行如何成为下一项目的完整源行”，否则 v2.2 只解决了旧 `import:excel-links` 流水的取错问题，没有闭合未来学习来源。

## 3. P1：文档内部仍需清除的冲突和任务遗漏

以下不是措辞美化，而是会让实施者按不同章节写出不同代码。

### P1-1. 仍有已作废的 SF 原生路径残留

- 第 738 行仍用“普通行成功提交后模拟 SF 导航失败或粘贴 0 行”作为验收；应删除并改为 A 路径普通行/SF 行/marker 的事务失败注入。
- 第 822 行仍声称“原生粘贴无法并入前面的 SQL 事务”，出现在 SF 整组语义之后；这只可能属于 B 路径，不能继续描述 SF。
- 第 824-847 行的 helper 示例仍调用禁止复用的 `ResolveChapterNo`；第 847 行仍写“SF 改道也需要导航”。与第 807-809、1133、1181 行直接冲突。
- 第 950 行仍写“多个取编号大且最近”；第 1041-1045、1114、1179 行却规定“恰好一个才用，多个阻断，不比较大小”。
- 第 976 行真实 UI 验收仍列“SF 跨条目导航”。SF SQL 完整行复制不应导航宿主树。
- 第 1172 行仍保留“候选全小于时阻断”，与第 1179 行唯一候选不比较大小冲突。

建议全文检索并逐处归类：

- `SF` + `导航/粘贴/原生`：除“明确说明禁止或旧方案作废”外应为 0；
- `ResolveChapterNo`：新写入路径的示例调用应为 0；
- `大且最近/全小于`：SF 同级选择现行规则中应为 0；
- `SF 跨条目导航`：现行任务和验收中应为 0。

### P1-2. 阶段任务没有覆盖正文要求

正文已经发现第三道门禁，但阶段 6 只列：

- `IsSmartTargetSetRecommendable`；
- `IsLearningGroupRecommendable`；
- 安全网与规格闸门。

没有把 `IsEngineeringScopeLearningTarget` 列成实际任务。应新增独立任务和行为测试，不能只在修订摘要与验收 47 中提及。

同样，§4.10.0.1 的来源索引重建、正式材料来源、候选列表回退、源行身份复核、必要字段验证和新来源回流，也没有对应到阶段 1-7 的明确代码任务。必须补一组任务和产出，否则正文“要求”不会进入实施清单。

### P1-3. 旧测试“保持绿”与新业务行为仍冲突

v2.2 第 1108 行仍把 `Test-LearningDbIncrementalAggregate` 等列为“本批不改写入身份，应保持绿”。但当前：

- `Test-LearningDbIncrementalAggregate.ps1:348` 明确断言纯 `SH` 不得进入增量聚合；
- `Test-QuantityFormulaLearning.ps1:368` 明确断言纯 `SH` 不得独立进入普通推荐；
- `Test-SmartFill.ps1:299` 仍断言历史纯辅助聚合框应被过滤。

这些旧断言必须按新决定改写，不可能原样保持绿。测试表应逐个列出“保留的安全断言”和“被新业务决定替换的断言”，不要整脚本笼统标成保持绿。

### P1-4. 自动测试矩阵仍不可直接复制执行

第 970-978 行说明了测试分层，但没有给出：

- 生成干净源码快照的具体命令；
- 编译新 DLL 的具体命令和输出路径；
- 建立隔离 NPOI 运行目录的具体命令；
- `RECO_EXPAND_DLL` 的精确赋值；
- 必跑脚本完整清单和顺序；
- 综合测试的数值超时；
- 如何精确确认并只终止本轮启动的进程；
- 每类 PASS/SKIP/超时/未完成的汇总格式。

如果文档宣称“可复制执行矩阵”，这些命令必须出现。否则改称“测试要求”，并在实施计划中另建可执行脚本。

### P1-5. 构建、部署、UI 验收、发布包更新顺序自相矛盾

- 阶段 8.5（第 1013 行）要求在真实 UI 之前更新发布包；

## 4. 建议新增或重写的验收

在 v2.2 的 49 条基础上，至少补齐以下行为级验收：

1. **正式材料来源**：正式材料存在完整历史业务行时进入 A 路径；不存在完整行时按最终 B1/B2 决定处理。
2. **候选回退**：最新来源项目不可访问或源行已删，能继续选择较早的有效同身份候选。
3. **源行二次核验**：实际读取行的编号、名称、单位或来源身份任一不符时拒绝，不得写入。
4. **必要字段门禁**：分别缺名称、单位、价格和选定的必要业务字段，均不得进入 A 路径。
5. **新来源可复用**：项目 A 的成功写入与接受回流，能为项目 B 提供有身份、有行号、可复核的完整来源。
6. **事务失败闭合**：完整源行 `null`、marker ID=0、业务行 ID=0、插入数不符时均整次事务回滚。
7. **远端预取**：项目业务事务开始前已完成远端源行读取；失败时目标项目没有活动写事务和新增行。
8. **一次 Apply 边界**：一次选中多个组件时，按文档最终决定精确验证事务数、marker 数、undo 批次数和失败影响范围。
9. **范围变化使预览失效**：按“全部”预览后切到 `0305`，旧结果不能 Apply；更换工作簿、工作表或数量列同理。
10. **撤销不受正常导航影响**：业务写入后切换单元/条目，仍能在同一项目连接上按 ID 撤销；切换项目连接后拒绝。
11. **可写叶节点谓词**：真实父级节点、真实叶条目、懒加载节点、Tag/数据库身份不一致分别命中确定结果。
12. **纯辅助全链路**：推荐读取、写入、`BindingLog`、聚合、`EngineeringTemplate` 和跨项目完整源行复用逐段通过，而不是只测“界面能看到”。
13. **B 路径状态机**（若保留）：稳定确认、部分确认、延迟出现、补偿成功、补偿失败、结果不确定逐状态验证 marker、undo 和学习均符合表格。
14. **结构化加载状态**：SQL 不可用、无专业分类、当前范围 0 关系三种提示和 Apply 状态互不混用。

不要用“源码中不存在字符串”代替上述事务、身份、回流和 UI 失效行为测试。

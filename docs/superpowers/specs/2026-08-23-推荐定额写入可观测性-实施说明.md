## 1. 批次 A：写入路径补结构化日志

### 1.1 问题

`038434d` 删除 L3 原生链时，把该链原有的全部诊断日志一并删除，未补等价物。

现状：`TemplateFillFeature.cs` 全文仅剩 5 处 `Log()`，且**全部位于与写入无关的失败分支**——`:505` 工作簿跳过、`:862` 章节名加载、`:1040` 隐藏列、`:1331` / `:1558` 学习回流失败。

**`ApplyFillToSelectedEntry`（`:1186`）主写入路径，成功与失败都不出声。**

后果已经真实发生：2026-08-22 的实施审查无法从 `RecoExpandPanel.log` 判断实机写入是否成功，只能绕道查学习库 `RecoLearning.BindingLog` 间接取证；而**学习回流只在整批完整成功时产生**——一旦写入失败或整组阻断，将不留任何痕迹，现场排障失去依据。

### 1.2 日志设施（不需要新建）

沿用 `FormPanel.Log(string)`（`FormPanel.cs:384`）：写入 DLL 同目录 `RecoExpandPanel.log`，UTF-8，带 `yyyy-MM-dd HH:mm:ss` 前缀，已有 `RotateLogIfNeeded` 轮转与 `LogLock` 串行化。

**不要**新增日志文件、日志级别、配置开关或异步队列。一次写入约产生 3–5 行，轮转机制足够。

### 1.3 统一前缀

全部使用 `Smart fill apply` 前缀，便于 `rg "Smart fill apply"` 一次捞全链路：

| 事件 | 行格式 |
|---|---|
| 进入 | `Smart fill apply begin: unit=<单元编号>#<单元序号> entry=<条目编号>#<条目序号> items=<n> groups=<n>` |
| 选路结果 | `Smart fill apply plan: L1=<n> L2=<n> sf=<n> entries=<条目编号:条数, ...>` |
| 成功 | `Smart fill apply ok: unit=<单元编号>#<单元序号> business=<n> marker=<n> undoRows=<n> firstId=<id> lastId=<id> elapsedMs=<n>` |
| 阻断（返回错误文案） | `Smart fill apply blocked: entry=<条目编号> <原样的返回文案>` |
| 事务失败 | `Smart fill apply failed: entry=<条目编号> <异常类型>: <异常消息> elapsedMs=<n>` |
| 界面侧拒绝 | `Smart fill apply rejected: <原因>` |
| 用户取消 | `Smart fill apply canceled: entry=<条目编号> items=<n>` |

### 1.4 `TemplateFillFeature.ApplyFillToSelectedEntry`（`:1186`–`:1337`）

**（1）进入日志**：放在 `groups` 算出之后、`groups.Count == 0` 判断之前，使阻断批次也有 begin 行。

**（2）阻断日志用局部委托收口**，避免六处散落的 `Log()` 与返回文案漂移：

```csharp
Stopwatch applyWatch = Stopwatch.StartNew();
Func<string, string> blocked = reason =>
{
    Log("Smart fill apply blocked: entry=" + (entryNo ?? "") + " " + reason);
    return reason;
};
```

把下列六处 `return "..."` 改为 `return blocked("...")`，**返回文案一个字都不许改**（离线测试与界面提示都依赖原文）：

| 行 | 文案 |
|---|---|
| `:1196` | `没有同时被选中且勾选的定额。` |
| `:1198` | `选中的组件存在数量、单位、公式或 SF 条目阻断，整组未写入。` |
| `:1211` | `组件数量无效，整组未写入：` + … |
| `:1234` | `定额缺少完整名称或单位，整组未写入：` + … |
| `:1241` | `当前项目没有可用于构造完整定额行的业务结构，整组未写入。` |
| `:1313` | `项目业务事务已整体回滚，未学习。失败原因：` + `ex.Message` |

`:1313` 那处除 `blocked(...)` 外，还要在 `catch (Exception ex)` 内先写一条 `failed` 行，带异常类型与耗时（`ex.Message` 已在返回文案中，日志里补 `ex.GetType().Name`；有 `InnerException` 时附加其 `Message`，不写整段堆栈）。

**（3）选路结果日志**：`prepared` 循环结束后、构造 `AgentUndoRecord` 之前，聚合统计后写一行。**逐条目分组统计是关键**——`ChosenItemSeq` 分组同时给出 SF 改道后的真实落点，也是批次 C 跨单元取证的依据：

```csharp
int l1 = prepared.Count(p => p.Layer == SmartFillWriteLayer.L1);
int l2 = prepared.Count(p => p.Layer == SmartFillWriteLayer.L2);
int sf = prepared.Count(p => p.Item != null && p.Item.SfRedirect);
string entryBreakdown = String.Join(", ", prepared
    .GroupBy(p => p.Item.ChosenItemNo ?? "")
    .Select(g => g.Key + ":" + g.Count().ToString(CultureInfo.InvariantCulture)).ToArray());
Log("Smart fill apply plan: L1=" + l1 + " L2=" + l2 + " sf=" + sf + " entries=" + entryBreakdown);
```

**（4）成功日志**：放在 `succeeded = true`（`:1335`）之前。`firstId` / `lastId` 取 `undo.Rows` 中 `QuotaSequence` 的最小值与最大值，`undoRows` 取 `undo.Rows.Count`（= marker + 业务行）。

日志必须写在**学习回流 try/catch 之后**——回流失败不影响业务写入成功的事实，但要能从日志上区分两者（回流失败已有 `:1331` 的 `Apply accept feedback failed`）。

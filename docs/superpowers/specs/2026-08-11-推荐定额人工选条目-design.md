## 1. 问题现象

「推荐定额」把目标条目当成**推荐系统必须推理出来的输出**：

1. `SmartFillFeature.cs:1036` `ResolveSmartTargetEntry` 从三层证据（`SignatureEntryMap` 权重 10000+sample、`EntryQuota` 与 `BindingLog` 聚合权重 1000+n）反推该写进哪个条目。
2. 推不出来 → `SmartFillFeature.cs:2136` 给 `Status` 追加「缺条目」→ `TemplateFillPanel.cs:1206` `IsNameQuotaHardStatus` 判为硬状态 → `:1218` 标 `MistyRose` 红 → `TemplateFillFeature.cs:1078-1082` 的写入闸门永久排除该行。
3. 条目多义 → `SmartFillFeature.cs:1269` `ResolveSmartTargetEntryCombinations` 做笛卡尔积（上限 `MaxEntryCombinations = 16`），每个组合生成一个候选组，用户必须在下拉里选条目组合。

用户实际使用中，这三条都在增加操作成本而不是降低：明明知道该写哪个条目，却要等系统猜、猜错还要标红拦住。

## 2. 根因

**条目编号跨编制办法同编号异义是真实的**（0805 设计 §3.3 本地实测，2020 内部 30 号文与 101 号文估算之间也存在）。这导致：

- 条目证据必须按 `(software_partition, method_no)` 精确隔离，不得跨办法回退；
- 隔离后仍然多义，于是不得不做笛卡尔积组合器让用户选；
- 用户选组合的操作成本，已经等于甚至超过直接点条目。

**推理链的复杂度来自"系统要替用户决定条目"这个前提。取消这个前提，整条链路可以删除。**

#### 4.8.3 改法 B：读取时合并同内容分片

人工点条目后，同一条公式会被写进很多不同条目、各自 `sample_count=1`，会频繁误触发「多套同权重公式」歧义闸门，导致行被莫名取消勾选。

**必须两阶段加载（v2.0 修正，审核 R8）**：v1.x 说「落 `FormulaByKey` 时把 key 改成公式本体身份」——**做不到**。当前顺序是 `SmartFillFeature.cs:650` 读 `QuantityFormulaRule` 时立即落快照，`:657` 才用第二条 SQL 补 `QuantityFormulaOperand`。落 key 的那一刻**操作数还没加载**，算不出「有序(操作数签名@单位)」。另外 `SmartFormulaRule.EntryCode`（`:114`）是单个 `string`，装不下「命中过的条目集合」。

改为：

1. **阶段一**：按 `rule_hash` 把全部规则与操作数读进临时字典（保持现有两条 SQL），**先不落** `FormulaByKey`；
2. **阶段二**：操作数补齐后，在**读取副本**上执行 consolidation（AGENTS.md:83：快照视为只读，排序与过滤只能操作副本）；
3. **内容身份** = `规范化(TargetUnit) + "\n" + 规范化(Template) + "\n" + 操作数按 index 升序拼接的 (规范化签名@规范化单位)`，须明确空值与规范化规则；
4. 合并对象保存 **`EntryCodes` 集合**（或按条目保存样本明细），`SmartFormulaRule.EntryCode` 相应改类型；
5. **专业范围过滤必须先于样本数合并**——先按 `SelectedScope` 筛出命中的条目分片，再对**该范围内**的分片求 `SampleCount`；不得把其他专业的样本数合并后带进当前专业排序；
6. 合并后的歧义判定比较**内容身份**，不再比较原始 `RuleHash`；
7. 写入门禁仍要求公式 `entry_code` 非空，**不得**把空 `entry_code` 当「全专业通配」——§4.8.2 里的 `String.IsNullOrWhiteSpace(rule.EntryCode)` 分支只兼容历史行，不是新语义。

合并规则：`SampleCount` 在范围内求和、`LastSeen` 取最大、`EntryCodes` 并集（仅审计）。歧义判定于是变成「**模板真的不同**才算歧义」。

**不做**：不改 `schema.sql`、不改公式哈希函数、不改 `Rebuild-Aggregates.ps1`、不重跑全量重建。

#### 4.10.1.1 写入前整组预检与原生粘贴失败补偿（审核 R4）

**问题**：`ApplyFill` 在 `TemplateFillFeature.cs:1194` 先 `transaction.Commit()` 提交 SQL 侧的项目内/跨库整行复制，**之后**才对 `libraryItems` 调宿主原生粘贴（`:1214`）。原生粘贴无法并入该事务。因此即使采用整组阻断语义，仍可能出现：普通行已提交落库 → SF 导航或粘贴失败 → 半组留在业务表，而整组又不产生 `accepted`。

**必须补充的三段设计**：

1. **写入前对整个组件组做完整预检**，全部通过才进入执行阶段：目标条目存在且唯一、目标单元一致、定额来源可解析（`ChosenQuotaSeq` 或跨库 `SourceDbQuotaSeq`，或库内定额编号可原生输入）、数量非空、当前版本单位可解析、SF 改道目标已确定。任一项不过 ⟹ 整组不进入执行。
2. **调换执行顺序，把补偿窗口从高概率侧移到低概率侧（v2.1，对审核 R4 的优化）**。

   审核建议「失败后删除已提交的直接复制行与 marker」。但**删除是破坏性动作**，且补偿本身也可能失败（AGENTS.md:170 对删除数据一贯谨慎）。更好的办法是**别让它先发生**：

   | | v1.x / 审核方案 | v2.1 |
   |---|---|---|
   | 顺序 | ① SQL 事务写直接复制行 → `Commit()` ② 原生粘贴库内定额/SF | ① 原生粘贴库内定额/SF ② SQL 事务写直接复制行 → `Commit()` |
   | 失败点 | 步骤 ② 失败 ⟹ ① 已提交，**必须删除补偿** | 步骤 ① 失败 ⟹ SQL 侧**尚未提交任何行**，直接回报，**无需补偿** |

   理由：原生粘贴依赖 UI 自动化、懒加载树、剪贴板与宿主菜单，失败率远高于一次本地 SQL 插入。把它放在前面，最脆弱的一步失败时代价最小。

   **诚实说明残余风险**：这是把补偿窗口**缩小**而非消除——「原生粘贴成功、随后 SQL 提交失败」仍会留下半组。该窗口概率低得多，此时才执行删除补偿（`undo.Rows` 中 `Kind == "I"` 的行已记录新增标识，可定点删除）。补偿也失败时，必须把该组件组报告为「部分失败、可撤销」并立即给出补偿入口。

   > 实施注意：调换顺序后，SQL 侧写入用的 `条目序号` 在预检阶段就已解析完毕，不受步骤 ① 的树导航影响；但步骤 ① 结束后必须按 §4.10.3 恢复原选中条目，再进入步骤 ②。
3. **不得**把「没有产生 `accepted`」等同于「没有产生业务写入」——这是两件事，结果文案必须分别说明。

**验收**：失败注入——普通行成功提交后模拟 SF 导航失败或粘贴 0 行，数据库不得残留半组；补偿也失败时界面必须给出明确的可撤销提示。

#### 4.10.3 SF 自动改道（决定 6）

**同级定义**：条目编号去掉最后一段后的前缀相同。`0101-01` 的父前缀是 `0101`，同级候选是 `0101-02`、`0101-03`…

**同级判定与「大于且最近」的严格定义（审核 R10）**：

1. 当前条目编号与候选均按 `-` 分段；
2. 候选与当前条目**段数必须相同**（更深的后代**不算**同级）；
3. **除最后一段外全部逐段完全相同**；
4. 最后一段按**整数**比较（`0101-2` < `0101-10`，不得用字符串排序或 `StartsWith`）；
5. 末段无法解析为整数时**不参与候选**；若因此无合法候选，按规则 D 处理。

**改道规则（v2.1 按真实数据修正）**：

| 情形 | 处置 |
|---|---|
| **A. 恰好 1 个**同级设备购置费条目 | SF 行改道写入它，**不比较编号大小** |
| **B. 多个**（真实数据中不存在，防御性分支） | 取最后一段整数**大于**当前条目、且**差值最小**者；若全部小于当前条目，取**差值最小的较小者** |
| **C. 0 个 / 无合法候选** | **整组阻断** |

> **v2.1 修正依据（2026-08-16 `ChapterEntry` 11,996 行只读实测）**
>
> - 277 个「设备购置费」条目（30号文 136、`TB 10801—2024` 141），深度分布 2/3/4/5 段分别为 2/99/154/22；
> - **同一 `(method_no, 父前缀, 段数)` 桶内出现两个及以上设备购置费条目的数量为 `0`** —— 277 个桶全部唯一；
> - 276/277 存在同深度兄弟，唯一例外是 `TB 10801—2024` 的 `0719-03-04-01`（无任何同深度兄弟），按 C 阻断，占比 0.4%，安全；
> - 真实结构高度规整：`Ⅰ.建筑工程费` / `Ⅱ.安装工程费` / `Ⅲ.设备购置费` / `Ⅳ.其他费` 依次为 `-01`/`-02`/`-03`/`-04`。
>
> **因此 v1.x「取编号大于当前且最近」是错的，必须降级为防御性兜底：**
>
> 1. 用户 2026-08-11 举的例子「同级有 `0101-02` 和 `0101-03` 两个设备购置费条目」**在真实数据中不存在**，该 tiebreak 永不触发；
> 2. 更严重的是「大于」会**误伤**——设备购置费固定在 `Ⅲ(-03)`、其他费在 `Ⅳ(-04)`。站在 `0101-04` 写 SF 时 `03 < 04`，按旧规则判定无候选 ⟹ 整组阻断，而实际存在唯一合法的 `0101-03`；
> 3. 同理，v1.x「候选全部小于当前条目时按 0 个处理」也随之作废——那正是站在 `其他费` 上的常见情形。
>
> **新口径**：唯一即取，不看大小；只有真出现多个（未观测到）才用大小做 tiebreak。

> **v2.0 修正（审核 R2，用户 2026-08-16 改判）**：v1.x 规定「阻断 SF 行、**同组普通定额行照常写入**」，与「组件组为原子单位」「整组一次写完」直接冲突，且会形成**残缺组**——业务表已部分写入，而 `CollectFullyWrittenNameDrivenGroups`（`TemplateFillFeature.cs:1292`）不会为残缺组产生 `accepted`，学习库与业务表就此分叉。
>
> **现改为整组阻断**：只要组内任一 `SF` 找不到合法改道条目，**整个组件组不写入、不插 marker、不产生 `apply-accept`**。组首复选框置只读，状态列给出原因。用户先在软件里建好设备购置费条目，再回来写这一组。
>
> 这样「组件组原子」在全设计中保持唯一语义，无需定义部分成功、补偿或残缺组学习口径。

**SF 导航后必须恢复原条目（审核 R5）**：SF 走库内定额原生粘贴时要 `TryNavigateToAgentItem` 导航到设备购置费条目，`tree.SelectedNode` 会被改写。写入开始前保存原 `TreeNode`、原条目编号/序号与当前单元身份，**在 `finally` 中尽力恢复**；恢复失败时明确提示并禁用旧预览继续写入（避免用户下一次点「写入当前条目」时目标已悄悄变成设备购置费条目）。

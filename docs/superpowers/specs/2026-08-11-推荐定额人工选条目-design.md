#### 为什么把 v2.2 的 A/B 二分改成三层

v2.2 按 F4 规定「`SF` 必须复制完整历史业务行，取不到就整组阻断」。2026-08-17 只读实测表明**这条路走不通**：

| 实测项 | 结果 |
|---|---|
| `quota_sequence`（跨库源行的必要字段）的来源 | **只有 `import:excel-links` 651 行有**；`plugin:excel-bind-batch` 253、`plugin:name-match` 104、`plugin:apply-accept` 84 **全部为 0** |
| 推荐目标的源行覆盖率 | 297 个不同编号中 197 个有（66%）；**2020 分区仅 50%** |
| 辅助码跨库源行 | `SH` 81、`SF` 36、`TLF` 10、`ZLF` 8 —— 且**不会增长** |
| `QuotaBoxTarget` 名称+单位完整度 | **633/659（96%）** |
| `extra` 中的价格字段 | `price`/`单价`/`base_price`/`unit_price` **全部 0 命中** |

结论：**日常绑定与接受回流永远不会变成可复制的完整源行**（没记源行号），所以 F4 的覆盖率不但不增长，还会随推荐目标增多而下降；而学习库**已经**有 96% 的名称+单位，只差单价一个字段。

因此改为三层：

| 层 | 适用 | 存在理由 |
|---|---|---|
| **L1 整行复制** | 任何目标，只要有完整源行 | 字段最全（费用类型、定额调整、单重、各费用列全带过来） |
| **L2 学习字段构造行** | **辅助码**（`SF`/`SH`/`ZLF`/`LF`/`TLF`…）无源行 | 辅助码本来就不在定额库里，无从原生补齐；学习库已有名称+单位，补上单价即可构造。**覆盖率与取错问题一并解决** |
| **L3 正式编号原生输入** | **正式定额/材料**无源行 | 宿主会从**当前版本定额库**查出**当期正确价格**——比复制别的项目的陈旧价更正确。这不只是兜底，对正式定额是**更优解** |

> L2 同时解决了 v2.2 的两个遗留：`CrossSourceByQuota` 裸编号取错（L2 不读它），以及下述「第四道门禁」。

#### 新增实证发现（复审未覆盖）：第四道门禁

复审 P0-1.3 指出 `IsSmartMapEntryUsableInCurrentProject` 要求每个目标能在当前项目找到。往下再看一层，`LoadCurrentSmartQuotaMetadata`（`SmartFillFeature.cs:941`）从定额索引补齐时写着：

```csharp
if (!requiredCodes.Contains(code) || indexed == null || IsContextSensitiveLearningCode(code)) continue;
//                                                     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 辅助码直接跳过
```

**辅助码的元数据只能来自 `LoadProjectQuotas`——即必须已在当前项目的 `定额输入` 中。** 叠加 `:988` 要求每个目标 `TryGetCurrentSmartQuota` 成功且单位非空，结论是：

> 纯辅助组件**只有在该材料已经在当前项目里时才会被推荐出来**；而一旦已在项目里，`ChosenQuotaSeq` 直接可用，根本不需要跨库源行。

也就是说 **F4 的跨库路径对辅助码不可达**，而决定 8（纯辅助开放）在最需要它的场景下形同虚设。这是第四道门禁（前三道见 §4.7.0）。

**处置**：辅助码没有版本相关含义（其身份就是 `编号+名称+单位`，学习记录自带），不需要用当前版本定额库做 `LY-192` 式校验。改为分流——普通定额继续按当前版本校验；**辅助码改用 L2 的学习字段自身校验**，不要求已在当前项目。

#### 新增的实证发现（本版最重要，复审未覆盖）

**`CrossSourceByQuota` 按裸编号索引，辅助码完整源行会静默取错。**

`SmartFillFeature.cs:790` 写的是 `snapshot.CrossSourceByQuota[quotaCode] = ...`，键是**裸目标编号**；加载 SQL 按 `ORDER BY id`，**后写覆盖先写**。而 2026-08-17 只读实测：

| 目标编号 | 跨库源行数 | 不同 `target_name` 数 |
|---|---|---|
| `SH` | 81 | **58** |
| `SF` | 36 | **19** |
| `TLF` | 10 | — |
| `ZLF` | 8 | — |

`SH` 底下是「门禁系统一键释放联动接入」「FAS 联动接入」「弃土消纳费」「电缆沟」等 58 种不同材料，全部塌进 `CrossSourceByQuota["SH"]` 一个槽。**要写「弃土消纳费」会拿到 `id=968` 的「门禁系统一键释放联动接入」整行**，名称/单位/价格全错且静默。

这正是 AGENTS.md:84 禁止的「通用辅助代码只按编号聚合」。

**因此**：F4 的完整源行复制**不能**直接建在现有 `CrossSourceByQuota` 上。必须先把该字典按 `BuildLearningTargetIdentityKey(kind, code, 规范化名称, 规范化单位)` 重新索引（§4.10.0.1）。这是纯辅助开放（决定 8）真正可用的前提，也是 F4 可实施的前提。

## 1. 问题现象

「推荐定额」把目标条目当成**推荐系统必须推理出来的输出**：

1. `SmartFillFeature.cs:1036` `ResolveSmartTargetEntry` 从三层证据（`SignatureEntryMap` 权重 10000+sample、`EntryQuota` 与 `BindingLog` 聚合权重 1000+n）反推该写进哪个条目。
2. 推不出来 → `SmartFillFeature.cs:2136` 给 `Status` 追加「缺条目」→ `TemplateFillPanel.cs:1206` `IsNameQuotaHardStatus` 判为硬状态 → `:1218` 标 `MistyRose` 红 → `TemplateFillFeature.cs:1078-1082` 的写入闸门永久排除该行。
3. 条目多义 → `SmartFillFeature.cs:1269` `ResolveSmartTargetEntryCombinations` 做笛卡尔积（上限 `MaxEntryCombinations = 16`），每个组合生成一个候选组，用户必须在下拉里选条目组合。

用户实际使用中，这三条都在增加操作成本而不是降低：明明知道该写哪个条目，却要等系统猜、猜错还要标红拦住。

## 2. 根因

**条目编号跨编制办法同编号异义是真实的**（0805 设计 §3.3 本地实测，2020 内部 30 号文与 101 号文估算之间也存在）。这导致：

- 条目证据必须按 `(software_partition, method_no)` 精确隔离，不得跨办法回退；
- 隔离后仍然多义，于是不得不做笛卡尔积组合器让用户选；
- 用户选组合的操作成本，已经等于甚至超过直接点条目。

**推理链的复杂度来自"系统要替用户决定条目"这个前提。取消这个前提，整条链路可以删除。**

### 4.6 条目相关标红与阻断（决定 5）

**唯一改动**：删除 `SmartFillFeature.cs:2134-2140` 给 `Status` 追加「缺条目」及其 `AlignNote` 的整段。

`TemplateFillPanel.cs` 的硬软状态机制（`1195-1223`）、颜色规则、`ConfirmExactNameFromCheck`（`1120`）、`GetUnsafeNameQuotaCandidateReason`（`1187`）**一行都不改**——「缺条目」不再产生，自然不再标红不再阻断；§3.4 的其余状态照常工作。

**SF 冲突不走 `Status`（v2.0 修正，审核 R6）**：v1.x 曾说「往 `Status` 追加 SF 冲突文案即可」，这会出问题——`Status` 是 `；` 分隔的多段串（`SplitNameQuotaStatus`），而 SF 冲突是**随树节点变化而变化的动态状态**。直接拼接会导致：切到正确条目后仍残留旧 SF 文案；反复切换时同一文案不断追加；为清除 SF 文案而误删单位/公式/数量等固有状态。

正确划分：

| 状态类别 | 载体 | 生命周期 |
|---|---|---|
| **预览固有状态**（缺当前定额单位、待确认计数单位1:1、公式参数缺失或歧义、缺跨量纲换算系数） | `Status` | 预览时确定，树节点变化不影响 |
| **SF 动态冲突** | `SfEntryBlocked` / `SfEntryBlockReason` | 每次树选中变化**重新计算并整体覆盖**，绝不拼接旧值 |

颜色、`sel` 只读、写入闸门三处**综合判断两类状态**。必须有「普通条目 → 设备购置费条目 → 普通条目」的往返测试，验证 SF 状态能被正确清除且不污染 `Status`。

| 写入/学习 | `ExcelLinkFeature.cs:2802-2807` `IsLearningGroupRecommendable` | 同一判定，不满足则整组不产生学习回流 |

**实测被挡掉的知识量**（2026-08-11）：96 条纯辅助签名关系中，`SF` 14 条本就放行，**被挡 82 条**（`SH` 72、`ZLF` 7、`TLF` 3）。其中绝大多数是高价值的「工程量表叫法 → 软件费用项名称」映射：

**决定：读取与学习两侧一并开放。**

2. `IsLearningGroupRecommendable`（`ExcelLinkFeature.cs:2802-2807`）同步取消，使新的纯辅助绑定能继续积累。**只改读取不改写入是错的**——存量可用、增量冻结，过一阵就过时；

#### 4.7.1 范围无数据时退化为全库（用户拍板）

§3.5.1 实测：2020 分区当前 `EngineeringTemplate` 为 0 行，专业范围下拉只有「全部学习库」与「未归类」。学习库熔断（`SmartFillFeature.cs:495`）时同理。

**v2.0 修正（审核 R3）**：v1.x 把「无专业数据」与「学习库熔断」当成同一种退化，**这在 SQL-only 架构下不成立**——熔断时 `LoadSmartLearningSnapshot`（`SmartFillFeature.cs:495`）直接抛「学习库熔断中」，`BuildPreview_SmartFill`（`:2210`）检测 `BySignature.Count == 0` 后结束预览，**根本没有任何关系可以显示**，「正在显示全部学习库」是假话。必须拆成两个互斥状态：

| 状态 | 判定 | 行为 | 提示 |
|---|---|---|---|
| **① SQL 正常，当前分区无专业分类数据** | 快照加载成功（`BySignature.Count > 0`），但 `EngineeringTemplate` 查得 0 行 ⟹ 专业下拉只剩「全部学习库」「未归类」 | 不做专业过滤，等价于全部学习库；**正常预览、正常写入** | 「当前版本尚无专业分类数据，正在显示当前分区全部学习关系。在本软件中新建绑定后专业目录会逐步建立。」 |
| **② SQL 熔断 / 连接失败 / 快照为空** | `IsLearningDbCircuitOpen()` 为真，或加载抛异常，或 `BySignature.Count == 0` | **停止推荐**；预览结果为空；**禁用「写入当前条目」** | 「学习库不可用，未生成推荐。」**不得**声称正在显示全部学习库 |
| **③ SQL 正常、范围有效，但过滤后 0 条关系**（v2.3 新增，复审 P1-7） | 快照加载成功且专业范围有数据，但 `FilterSmartHitsByScope` 后无任何命中 | 预览为空；**禁用写入** | 「当前范围暂无学习关系。」**不得**说成「学习库不可用」 |

三种状态**都由结构化状态字段决定，不依赖警告字符串**。

**实现要求**：`LoadSmartLearningScopes`（`SmartFillFeature.cs:377`）当前在熔断时返回 `[全部学习库, 未归类]`，与状态 ① **完全同形**，调用方无法区分。必须改为带状态的返回值，**不得靠「下拉里没有专业节点」反推原因**。

> **v2.1 简化（对审核 R3 的优化）**：审核建议四态枚举 `SuccessWithScopes` / `SuccessWithoutScopes` / `CircuitOpen` / `Error`。但前两者可由 `Scopes.Count(专业节点) > 0` 直接导出，单独建枚举值会制造「状态字段与列表内容不一致」的新失效模式。
>
> 改为**三态 + 列表**：
>
> ```csharp
> private sealed class SmartScopeLoadResult
> {
>     public SmartScopeLoadStatus Status;   // Success / CircuitOpen / Error
>     public List<SmartLearningScope> Scopes = new List<SmartLearningScope>();
>     public string Message;                // 供顶部提示直接使用
> }
> ```
>
> 状态 ① = `Success` 且专业节点数为 0；状态 ② = `CircuitOpen` 或 `Error`。判定逻辑集中在一处，不散落到 UI。

提示是**信息性**的，不进 `Status`、不标红；但状态 ② 额外禁用写入按钮。

> 不采用「用 `ChapterEntry` 补专业目录」：`ChapterEntry` 只是条目字典，能列出专业但过滤不了——`SignatureBoxMap` 没有 `entry_code`，2020 缺少 `EngineeringTemplate` 的 box→entry 映射，选了也不起作用，反而更困惑。

#### 4.8.3 改法 B：读取时合并同内容分片

人工点条目后，同一条公式会被写进很多不同条目、各自 `sample_count=1`，会频繁误触发「多套同权重公式」歧义闸门，导致行被莫名取消勾选。

**必须两阶段加载（v2.0 修正，审核 R8）**：v1.x 说「落 `FormulaByKey` 时把 key 改成公式本体身份」——**做不到**。当前顺序是 `SmartFillFeature.cs:650` 读 `QuantityFormulaRule` 时立即落快照，`:657` 才用第二条 SQL 补 `QuantityFormulaOperand`。落 key 的那一刻**操作数还没加载**，算不出「有序(操作数签名@单位)」。另外 `SmartFormulaRule.EntryCode`（`:114`）是单个 `string`，装不下「命中过的条目集合」。

改为：

1. **阶段一**：按 `rule_hash` 把全部规则与操作数读进临时字典（保持现有两条 SQL），**先不落** `FormulaByKey`；
2. **阶段二**：操作数补齐后，在**读取副本**上执行 consolidation（AGENTS.md:83：快照视为只读，排序与过滤只能操作副本）；
3. **内容身份** = `规范化(TargetUnit) + "\n" + 规范化(Template) + "\n" + 操作数按 index 升序拼接的 (规范化签名@规范化单位)`，须明确空值与规范化规则；
4. **快照保存不可变的原始分片，不在加载期合并（v2.2 修正，P0-6）**。v2.1 说「合并对象保存 `EntryCodes` 集合」——集合**存不下**各条目分别贡献的 `SampleCount` 与 `LastSeen`，而第 5 条要求按范围过滤后再求和，没有 per-entry 明细就算不出来。且 `LoadSmartLearningSnapshot` 根本不接收范围，`snapshot.SelectedScope` 是加载完成后才赋值的。

   正确模型：
   - 快照里存**原始分片列表**，每个分片至少保存 `EntryCode`、`SampleCount`、`LastSeen`、目标单位、公式模板与有序操作数；
   - `SelectContextualSmartFormulaRules` 先在**副本**中按当前 `SelectedScope` 过滤分片；
   - **再**对过滤后的分片按内容身份合并与排序；
   - 合并结果是**临时视图**，不回写快照（AGENTS.md:83）。
5. **专业范围过滤必须先于样本数合并**——先按 `SelectedScope` 筛出命中的条目分片，再对**该范围内**的分片求 `SampleCount`；不得把其他专业的样本数合并后带进当前专业排序；
6. 合并后的歧义判定比较**内容身份**，不再比较原始 `RuleHash`；
7. 写入门禁仍要求公式 `entry_code` 非空，**不得**把空 `entry_code` 当「全专业通配」——§4.8.2 里的 `String.IsNullOrWhiteSpace(rule.EntryCode)` 分支只兼容历史行，不是新语义。

合并规则：`SampleCount` 在范围内求和、`LastSeen` 取最大、`EntryCodes` 并集（仅审计）。歧义判定于是变成「**模板真的不同**才算歧义」。

**不做**：不改 `schema.sql`、不改公式哈希函数、不改 `Rebuild-Aggregates.ps1`、不重跑全量重建。

`MultiplierFeature.cs:1149-1175` 的顺序是：属性表 → 结果表 → `node.Tag["条目编号"]` → 按 `条目序号` 查 `章节表`。**属性表排在最前**。在 `AfterSelect` 回调时刻，宿主属性表可能尚未刷新，会返回**上一次选中**的条目——对旧场景（乘系数、智能指令）无妨，对「写入当前条目」是致命的。

新场景改用更强的节点一致性口径：

1. **以 `tree.SelectedNode` 自身的 `Tag["条目序号"]` / `Tag["条目编号"]` 为第一证据**，而不是属性表；
2. **两条路径必须区别对待（v2.1，对审核 R7 的修正）**：审核建议「必要时 `BeginInvoke` 等宿主刷新后再次读取」，但这条不能笼统套用——
   - **`OnApply` 路径**：是同步的点击响应，**不得**引入 `BeginInvoke`，否则整个写入流程要改成异步，复杂度和失效模式都陡增。`SelectedNode.Tag` 本身是同步且始终最新的，直接作为第一证据即可，**不需要等任何刷新**；
   - **`AfterSelect` 刷新 `lblCurrentEntry` 路径**：可以 `BeginInvoke` 延后一拍，避开宿主自身的刷新竞态。标签只是提示，晚一拍无害。
3. **三方核对**：节点条目序号、按序号查库所得条目编号、按编号查库所得条目序号，三者必须自洽；
4. **不得**只用 `where 条目编号=@bh` 的行数证明「当前节点是可写叶条目」——那只证明编号在库里唯一，既不证明它就是当前节点，也不证明该节点可输入定额。必须给出**宿主可写叶节点**的可靠证据（如节点自身的 `Tag` 层级/类型标记，或 `定额输入` 可挂载性），不能以 SQL 唯一行数代替；
5. **所有**「当前节点」判断必须复用**同一个**解析结果（v2.2，P0-7）。v2.1 新增的 `IsAgentTreeStandingOnItem`（§4.10.4）内部又调了旧的 `ResolveChapterNo`，属性表滞后时会误判「已站在目标条目」，与本节的口径自相矛盾。该 helper 必须改用本节的解析结果，或直接比较 `SelectedNode` 的 `Tag` 身份；
6. 必须覆盖父级节点、懒加载未展开节点、属性表滞后、快速连续切换节点四种测试。

**写入前置校验**（属「目标是否物理存在」，不受决定 3 限制）：三方核对通过后，`select 条目序号, 工程或费用项目名称 from 章节表 where 条目编号=@bh` 仍须**恰好 1 行**；0 行或多行（用户点在"章"上）→「当前树节点不是可写入的条目，请选中具体条目后重试」，不写入。

#### 4.9.4 项目连接身份门禁（v2.0 新增，审核 R1）

**问题**：v1.x 只要求 `OnApply` 重读当前条目，**不足以防止用户在「预览完成后、点击写入前」切换项目**。旧预览里的定额、单位、公式和目标元数据会被写进新项目；只要新项目恰好存在同编号条目，「条目恰好一行」的校验也拦不住。这与 AGENTS.md 的连接借用条款直接冲突——该条明确要求预览、执行、撤销、重做**同时保存并核对连接对象引用与不含密码的 `DataSource|Database` 身份，项目切换后拒绝旧计划**。

#### 4.10.0 写入路径三分类（v2.2，按 F1–F5 重建）

> |---|---|---|

> | **L2** | **辅助码**无源行 | 用学习库的 `名称 + 单位 + 单价` 构造行 |
> | **L3** | **正式定额/材料**无源行 | 原生输入编号+数量，宿主按当前版本定额库补齐 |

##### L1. 完整源行事务路径（默认）

对**单个目标**能取得完整源行时适用，包括 `SF`/`SH`/`ZLF`/`LF`/`TLF` 等辅助目标。一个组件可同时含 L1 与 L2 目标；两层统一进入一次 Apply 的项目业务事务。

1. 写入前完成**整组**预检（§4.10.1）；
2. 为每个目标解析完整源行及来源身份（§4.10.0.1）；
3. 确定普通目标条目与 `SF` 的设备购置费目标条目；
4. 在当前项目连接上开启**一个**项目业务表 SQL 事务；
5. 同一事务内复制全部业务行并写入本批全部 marker；
6. 任一行、任一 marker 或顺号分配失败 ⟹ **整个事务回滚**；
7. 提交成功后形成**带项目连接身份**的 undo 记录；
8. 整次 Apply 的 L1/L2 及可能存在的 L3 全部确认成功后，才执行学习库 SQL 回流。

> 混合组件中的普通行与 `SF` 行即使落到**两个不同条目**，只要都有完整源行，也必须在**同一个**项目业务表 SQL 事务内完成。现有 `ApplyFill` 的事务本就按 `条目序号` 逐行赋值，天然支持跨条目。

##### L2. 辅助码按学习字段构造行（v2.3 新增，用户拍板）

4. **缺名称或缺单位** ⟹ 无法构造 ⟹ **整组阻断**（与 AGENTS.md:84 身份完整性一致）；
5. **缺单价** ⟹ 允许构造，单价写 0，状态列给信息性提示（**不阻断**——很多辅助费本来就现场议价）。

##### L3. 正式编号原生输入（独立非事务）

**仅**适用于取不到完整源行、但宿主能按编号完整补齐的**正式定额或正式材料**。**任何辅助代码都不得进入该路径**（F1：敲 `SH` 回车宿主查不到任何数据，只会留下名称/单位/价格全空的壳行）。

> **L3 不只是兜底**：正式定额的价格**应当**来自当前版本定额库，而不是从别的项目复制的陈旧价。所以对正式定额，L3 在价格正确性上**优于** L1。选层顺序仍是 L1 优先（字段最全），但 L3 不是"退而求其次"。

该路径**不具备**数据库事务原子性，不得再用「同一 SQL 事务完成整组」描述。不得依靠提示字符串判断成功，统一返回结构化结果。

**结构化状态机（实施口径）**：

```csharp
private enum NativeInsertState
{
    NotStarted, Submitted, Confirming, Confirmed,
    PartiallyConfirmed, Compensating, Compensated,
    CompensationFailed, Indeterminate
}
```

结果对象至少包含：`State`、`ExpectedCount`、`ConfirmedIds`、`RemainingIds`、`TargetItemSeq`、项目连接对象与无密码身份、开始/结束时间和错误原因。任何后续逻辑只看结构化状态与 ID 集合，禁止解析提示字符串。

**确认参数写死**：发送原生粘贴后每 **250ms** 只读一次目标条目的 `定额输入` ID 集合，总超时 **10s**；新增集合与目标编号/名称/单位核对结果连续 **3 次完全相同**且数量等于预期才进入 `Confirmed`。0 行继续等待；少于预期进入 `PartiallyConfirmed`；多于预期、身份不符、项目连接对象或 `DataSource|Database` 改变、超时后集合仍变化，均进入 `Indeterminate`。轮询期间 Apply 保持 busy，禁止重入。

**一次 Apply 的固定顺序**：

1. 写入前保存每个 L3 目标条目的 ID 基线并复核预览上下文；
2. 按目标条目执行 L3 原生输入并轮询到稳定结果；
3. 任一 L3 未 `Confirmed`：对本 Apply 已确认属于插件提交的新增 ID 进入 `Compensating`；使用原项目同一借用连接开启短事务定点删除并再次确认；成功为 `Compensated`，失败为 `CompensationFailed`；项目身份已变化时不得借新项目连接删除，直接 `Indeterminate`；
4. 全部 L3 `Confirmed` 后，冻结其实际新增 ID 和完整业务行；再开启**一个**项目业务事务写 L1/L2、所有目标条目的 marker。纯 L3 条目的 marker 从该条目已确认新增行克隆结构后覆盖 marker 字段；
5. L1/L2 或 marker 事务失败：先回滚事务，再补偿本 Apply 的全部 L3 新增 ID；
6. 补偿完全成功时不压 undo；补偿失败或结果不确定时，必须在返回前把仍确认存在的 ID 压入绑定原连接对象与身份的 undo 记录；
7. 只有 L3 全部 `Confirmed` 且 L1/L2/marker 事务提交成功，才形成一个完整 undo 批次并允许逐组件学习。

**归属确认**：前后差集中的行还必须按本次计划的目标条目、正式编号和预期数量逐一核对；不能把同期间不属于本计划的新增行纳入补偿或 undo。失败注入测试直接驱动状态转换和集合确认逻辑，不在生产行为中保留可由普通用户触发的测试开关。

组件同时含「有完整源行的目标」与「需原生兜底的正式目标」时，**整组标记为非事务执行计划**，固定顺序：先执行并确认全部正式编号原生目标 → 再用一个项目业务表 SQL 事务写入其余完整源行与全部 marker。任一原生目标失败 ⟹ 补偿此前已确认的原生行，后续 SQL 不启动；后续 SQL 事务失败 ⟹ 先回滚事务，再补偿已确认的原生行。补偿未完全成功 ⟹ 进入可撤销的部分失败状态，**且始终不学习**。**不得**把其中的 SQL 子集成功称作「整个组件事务原子」。

> 辅助目标缺完整源行时转 L2，不得阻断也不得进入 L3；只有缺源目标是宿主可识别的正式定额/正式材料时才进入 L3。

##### 学习库回流（成功后的独立步骤）

- 只有组件**全部**业务行与 marker 完整成功，才生成 `apply-accept`；
- 业务写入失败、原生部分成功、补偿中或最终状态不确定 ⟹ **均不学习**；

- `BindingLog` 仍按**每 target 一行、同一 `group_key`** 的既有口径。

#### 4.10.0.2 事务、marker 与撤销边界（P0-2）

0. **事务边界 = 一次 Apply（用户 2026-08-17 拍板，复审 P0-3）**。v2.2 第 710 行写"一次组件写入一个事务"，第 713 行又按"本批目标条目"写 marker，现有 `ApplyFill` 则是"一次 Apply 一个事务 + 一个 undo 批次"——三者边界不一致。**统一为**：
   - 一次 Apply 的**全部 L1/L2 目标**共用**一个**项目业务表 SQL 事务；
   - **每个实际写入的目标条目** 1 条 marker（与现有 `markerInserted` 按 `itemSeq` 去重一致）；
   - 提交成功后形成**一个** undo 批次；
   - **任一目标或 marker 失败 ⟹ 整次 Apply 回滚**（选中 5 个组件、第 5 个失败，前 4 个也回滚）；
   - 事务提交成功后**才**逐组件执行学习库回流。
   > 因为写入前已做整组预检（§4.10.1），能进事务的组件都已通过校验，剩余失败都是意外错误——此时全回滚最安全，也最贴合现有实现。

1. ~~完整源行路径的一次组件写入只有一个项目业务表 SQL 事务~~ **（已由第 0 条取代）**；
2. 事务覆盖普通行、跨条目 `SF` 行与本批**全部** marker；
3. 任一目标失败即回滚，回滚后应为 **0 新业务行、0 marker、0 `apply-accept`**；
4. **marker 数量写死**：**每个本批实际写入的目标条目写 1 条**，与同批 undo 绑定。混合普通/`SF` 跨两个条目时**预期 2 条**，不再用含糊的「整批 1 条」。
   > 与现有代码一致：`TemplateFillFeature.cs:1101` 的 `markerInserted` 就是按 `itemSeq` 去重的，天然每条目 1 条。
5. SQL 事务失败**不产生**撤销记录（没有已提交行）；提交成功后才产生完整批次 undo；
6. L3 的 undo 按**实际确认新增 ID** 建立，并处理补偿失败与结果不确定场景；
7. **undo/redo 只硬核对连接对象引用与 `DataSource|Database`**（v2.3 修正，复审 P0-4）。v2.2 要求 undo/redo 还核对当前单元、`software_partition`、`method_no` —— **过度绑定**：撤销用的是已记录的行 ID，用户写完后正常切换单元或章节树**不应该**导致撤销失效。Preview/Apply 的门禁另见 §4.9.4。

8. **以下情况必须抛错并回滚，不得"计入 skipped 后提交"**（复审 P0-3）：
   - 完整源行返回 `null`；
   - marker 插入 ID `<= 0`；
   - 业务行插入 ID `<= 0`；
   - 预期行数与实际插入数不一致；
   - 顺号分配或目标条目复核失败。

   > 现状 `TemplateFillFeature.cs:1158-1170`、`1183-1191` 对 ID `<= 0` **只是 `skipped++`**，随后 `:1194` 照常 `Commit()`。不改这一行为，「任一行失败整体回滚」根本不成立。

9. **远端源行必须在事务开始前预取（复审 P0-3）**。现状跨库源行在目标事务已开始后才加载（`TemplateFillFeature.cs:1105-1120`），让目标库事务跨越远端连接与网络等待。改为：事务外完成整组 preflight、远端源行加载、身份与完整性复核并**冻结内存副本** → 复核当前项目身份仍一致 → 再开启**短**项目业务事务。

#### 4.10.3 SF 自动改道（决定 6）

**同级定义**：条目编号去掉最后一段后的前缀相同。`0101-01` 的父前缀是 `0101`，同级候选是 `0101-02`、`0101-03`…

**同级判定与「大于且最近」的严格定义（审核 R10）**：

1. 当前条目编号与候选均按 `-` 分段；
2. 候选与当前条目**段数必须相同**（更深的后代**不算**同级）；
3. **除最后一段外全部逐段完全相同**；
4. 最后一段按**整数**比较（`0101-2` < `0101-10`，不得用字符串排序或 `StartsWith`）；
5. 末段无法解析为整数时**不参与候选**；若因此无合法候选，按规则 D 处理。

**改道规则（v2.1 按真实数据修正）**：

| 情形 | 处置 |
|---|---|
| **恰好 1 个**同级设备购置费条目 | SF 目标改道写入它，**不比较编号大小** |
| **0 个 或 多于 1 个** | **整组阻断** |

> **v2.2 收敛（复审 §5 第 15 条）**：v2.1 保留了「多个时取大于且最近」的防御性 tiebreak，导致文档里同时存在「唯一即取」「取更大最近」「全部较小阻断」三套口径。复审指出：**中央学习库的结构统计不能证明当前项目一定唯一**（项目可能有自定义或复制来的条目），而**编号大小也不是可靠的业务语义**。
>
> 因此取消 tiebreak，收敛为**恰好一个才用，零个或多个都整组阻断**。多个时让用户自己点设备购置费条目——这与整个设计「歧义交给人」的哲学一致。

> **v2.1 修正依据（2026-08-16 `ChapterEntry` 11,996 行只读实测）**
>
> - 277 个「设备购置费」条目（30号文 136、`TB 10801—2024` 141），深度分布 2/3/4/5 段分别为 2/99/154/22；
> - **同一 `(method_no, 父前缀, 段数)` 桶内出现两个及以上设备购置费条目的数量为 `0`** —— 277 个桶全部唯一；
> - 276/277 存在同深度兄弟，唯一例外是 `TB 10801—2024` 的 `0719-03-04-01`（无任何同深度兄弟），按 C 阻断，占比 0.4%，安全；
> - 真实结构高度规整：`Ⅰ.建筑工程费` / `Ⅱ.安装工程费` / `Ⅲ.设备购置费` / `Ⅳ.其他费` 依次为 `-01`/`-02`/`-03`/`-04`。
>
> **因此 v1.x「取编号大于当前且最近」是错的，必须降级为防御性兜底：**
>
> 1. 用户 2026-08-11 举的例子「同级有 `0101-02` 和 `0101-03` 两个设备购置费条目」**在真实数据中不存在**，该 tiebreak 永不触发；
> 2. 更严重的是「大于」会**误伤**——设备购置费固定在 `Ⅲ(-03)`、其他费在 `Ⅳ(-04)`。站在 `0101-04` 写 SF 时 `03 < 04`，按旧规则判定无候选 ⟹ 整组阻断，而实际存在唯一合法的 `0101-03`；
> 3. 同理，v1.x「候选全部小于当前条目时按 0 个处理」也随之作废——那正是站在 `其他费` 上的常见情形。
>
> **v2.2 最终口径**：唯一即取，不看大小；**多个也阻断**（不再做 tiebreak）。实测数据证明「大于」规则会误伤，复审进一步指出中央库统计不能代表当前项目、编号大小也不是业务语义——两条论据合起来，只剩「恰好一个才用」这一种口径。

> **v2.0 修正（审核 R2，用户 2026-08-16 改判）**：v1.x 规定「阻断 SF 行、**同组普通定额行照常写入**」，与「组件组为原子单位」「整组一次写完」直接冲突，且会形成**残缺组**——业务表已部分写入，而 `CollectFullyWrittenNameDrivenGroups`（`TemplateFillFeature.cs:1292`）不会为残缺组产生 `accepted`，学习库与业务表就此分叉。
>
> **现改为整组阻断**：只要组内任一 `SF` 找不到合法改道条目，**整个组件组不写入、不插 marker、不产生 `apply-accept`**。组首复选框置只读，状态列给出原因。用户先在软件里建好设备购置费条目，再回来写这一组。
>
> 这样「组件组原子」在全设计中保持唯一语义，无需定义部分成功、补偿或残缺组学习口径。

**SF 写入不导航宿主树（v2.3，L1/L2）**：v2.1 的「SF 原生粘贴 → 导航到设备购置费条目 → `finally` 恢复原节点 → `suppressHostTreeSync` 抑制重入」整套设计已经作废。

`SF` 有完整源行时走 L1，无完整源行时按完整学习身份走 L2；两者都只需要解析出的**目标条目序号**，写入时直接把 `条目序号` 赋成设备购置费条目的序号即可。`SF` 永不进入 L3。

**因此 SF 的 L1/L2 写入不得主动切换宿主树节点**，也就不存在 SF 的恢复与重入问题。L3 正式编号原生输入允许定位到用户已经确认的目标条目，因为宿主原生补齐必须在该条目执行；目标恒为本次用户选定条目，无需恢复。`TryNavigateToAgentItem`/`ExpandAgentTreePath` 等方法仍被 L3、智能助手等功能使用，**不得因本批全局删除**。

**反向约束**（AGENTS.md:85 另一半）：用户点中的条目名含「设备购置费」时，非 SF 行标红不可勾并提示。

**判定时刻**：树选中变化时 + Apply 入口重算。
**判定数据**：条目名一律取当前项目 `章节表` 的 `工程或费用项目名称`——用户点的就是本项目节点，AGENTS.md:85 判定顺序第一档必然命中。

复用现有 `IsSmartTargetEntryCompatible`（`SmartFillFeature.cs:1368`，内部已有 `equipmentEntry` 判定）。`FillPreviewItem`（`TemplateFillFeature.cs:100-120`）新增 `SfRedirect` / `SfEntryBlocked` / `SfEntryBlockReason`。

SF 改道成功时整组一次写完（普通行进当前条目、SF 行进设备购置费条目）；改道失败时整组不写（规则 D）。两种情形下 `CollectFullyWrittenNameDrivenGroups`（`1292`）的整组闭合口径都**不用改**，AGENTS.md:79 原样成立。

> `SF` 只走 L1/L2，因此与同组普通 L1/L2 行处于一次 Apply 的同一个项目业务事务；只有组件内存在正式编号 L3 目标时，才需要 §4.10.0 的原生确认与补偿状态机。
